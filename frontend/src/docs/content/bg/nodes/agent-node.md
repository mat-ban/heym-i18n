# Agent Node

**AI Agent** node е LLM node с извикване на инструменти. Той може да изпълнява Python инструменти, да извиква свързани canvas nodes като инструменти, да се свързва към MCP сървъри, да използва skills, по избор да действа като orchestrator, който делегира на други agent nodes, да извиква други workflows като инструменти и да спира за [human review](../reference/human-in-the-loop.md).

## Преглед

| Свойство | Стойност |
|----------|-------|
| Входове | 1 |
| Изходи | 1, плюс опционален `review`, когато HITL е активиран |
| Изход | `$nodeLabel.text`, `$nodeLabel.fieldName` (когато JSON output е активиран), или pending HITL payload, докато се изчаква review |

## Основни параметри

### Удостоверение и модел

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `credentialId` | UUID | LLM удостоверение (API key) от Settings |
| `model` | string | Име на модел (напр. `gpt-4o`, `gemini-2.5-flash-lite`) |
| `fallbackCredentialId` | UUID (опционален) | Резервно удостоверение, когато основното се провали |
| `fallbackModel` | string (опционален) | Резервен модел, когато основният се провали |

Добавете удостоверения в раздела [Credentials](../tabs/credentials-tab.md). Списъкът с модели се зарежда от избраното удостоверение. Ако основното удостоверение или модел върнат грешка, node автоматично опитва отново с резервното удостоверение и модел, преди да се провали.

### Prompts

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `systemInstruction` | string | System prompt за AI. Поддържа [expressions](../reference/expression-dsl.md). |
| `userMessage` | string | Потребителско съобщение/prompt. По подразбиране: `$input.text` |
| `jsonOutputEnabled` | boolean | Структуриран JSON изход |
| `jsonOutputSchema` | string | JSON Schema за структуриран изход |
| `extraBodyEnabled` | boolean | Изпращане на специфични за доставчика параметри на заявката (по подразбиране: `false`) |
| `extraBody` | string | JSON обект, обединяван във всяка API заявка, която agent прави |

Използвайте `$input.text`, `$nodeName.field` и друг синтаксис на [Expression DSL](../reference/expression-dsl.md).

### Reasoning модели (o1, o3)

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `temperature` | number | 0.0–2.0 (по подразбиране: 0.7), за стандартни модели |
| `reasoningEffort` | `"low"` \| `"medium"` \| `"high"` | Дълбочина на reasoning за reasoning модели |

Когато използвате reasoning модел (напр. o1, o3), UI показва **Reasoning Effort** вместо Temperature. За стандартни модели **Temperature** контролира креативността.

**Пример за JSON изход:** Когато се нуждаете от структурирани данни от agent (напр. класификация, извличане), активирайте JSON output и предоставете schema. Agent връща JSON, съответстващ на schema; достъпвайте полетата по име на изхода на node:

```json
{
  "jsonOutputEnabled": true,
  "jsonOutputSchema": "{ \"type\": \"object\", \"properties\": { \"status\": { \"type\": \"string\", \"enum\": [\"APPROPRIATE\", \"INAPPROPRIATE\"] }, \"reason\": { \"type\": \"string\" } }, \"required\": [\"status\", \"reason\"] }"
}
```

Следващите nodes могат да използват `$agentLabel.status`, `$agentLabel.reason` и т.н. Същото поведение като JSON изхода на [LLM node](../nodes/llm-node.md).

## Human Review (HITL)

Използвайте HITL, когато agent може да се нуждае от одобрение в определени моменти преди важни действия.

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `hitlEnabled` | boolean | Добавя checkpoints за human review към agent |
| `hitlSummary` | string | Насоки за одобрение, които казват на agent кога е необходим human review |

Когато HITL е активиран, agent получава инструмент `request_human_review`. Използвайте system prompt и
това поле за насоки, за да обясните кои извиквания на инструменти, sub-agents, sub-workflows, MCP действия, skills
или странични ефекти изискват одобрение. Agent може да извика този инструмент само когато е необходимо, включително многократно
в рамките на едно изпълнение.

Обобщението, видимо за рецензента на публичната страница, се генерира от заявката за review на agent по
време на изпълнение. Ако agent не предостави обобщение изрично, Heym извлича такова от Markdown
тялото на review.

За MCP инструменти Heym иска от модела да интерпретира Вашите писмени HITL инструкции като един от три
обхвата: `always`, `once` или `never`. Това означава, че свободни формулировки като "за всяко извикване", "само
веднъж" или "никога не питай" се нормализират, преди да се приложи runtime gating.

Всеки HITL checkpoint създава еднократна публична връзка за review на `/review/{token}`. Рецензентът може да:

- **Accept** оригиналния Markdown текст на review
- **Edit & Continue** с модифициран Markdown
- **Refuse** и да продължи с `text: ""`

Когато HITL е активиран, node също така expose-ва `review` output handle на canvas. Свържете този
клон към Slack, email или други notification nodes, ако искате да разпространите review URL и обобщението веднага щом изпълнението спре.

Изпълнението преминава в `pending`, докато рецензентът отговори. Текстът на review е едно Markdown
тяло, а pending payload също включва текст на споделяема връзка за външно предаване. Nodes на `review`
клона се изпълняват незабавно, когато паузата бъде създадена; нормалният изходен път продължава само след одобрение. След одобрение Heym се възобновява от запазения execution snapshot и agent продължава с одобрения контекст. Ако по-късна стъпка също се нуждае от одобрение, agent може да създаде друг HITL checkpoint. Вижте [Human-in-the-Loop](../reference/human-in-the-loop.md) за формата на payload, поведението на review URL и семантиката на възобновяване.

HITL е наличен само за agent изход в текстов режим. Във v1 не може да се комбинира с `jsonOutputEnabled`.
## Режим на оркестратор

Когато е активиран, агентът може да делегира задачи на други agent nodes във workflow-а. Ако **режимът на оркестратор е деактивиран**, агентът **не може да създава връзки agent→agent** върху canvas.

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `isOrchestrator` | boolean | Когато е `true`, агентът получава инструмент `call_sub_agent` |
| `subAgentLabels` | string[] | Етикети на agent nodes, които този оркестратор може да извиква |

**Sub-agents** трябва да използват `$input.text` в своето User Message, за да получат prompt-а на оркестратора.

Когато оркестраторът извика няколко sub-agents в един ход, те се изпълняват паралелно. Вижте [Agent Architecture](../reference/agent-architecture.md) за подробности.

## Sub-Workflows

Когато е конфигуриран, агентът получава инструмент `call_sub_workflow` за изпълнение на други workflow-и.

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `subWorkflowIds` | string[] | ID-та на workflow-и, които този агент може да извиква като инструменти |

Изберете workflow-и в секцията Sub-Workflows на конфигурацията на агента. Агентът ще ги извиква с `workflow_id` и `inputs` (обект, съответстващ на входните полета на целевия workflow). Максимална дълбочина: 5 вложени извиквания на sub-workflow.

## Инструменти от canvas node

Може да свържете поддържан workflow node към handle-а **tools** на агента, така че агентът да може да извиква този node по време на изпълнение. Това превръща съществуващите действия и трансформации от canvas в извикваеми инструменти без писане на Python.

Използвайте инструменти от canvas node, когато искате агентът да решава кога да стартира конфигуриран node, като същевременно запазвате удостоверенията, статичните полета и специфичните за workflow-а настройки в UI-а на node-а.

### Полета, предоставяни от агента

Полетата на свързан tool node могат да бъдат маркирани с иконата на бот. Маркираните полета стават задължителни параметри на инструмента, които агентът трябва да предостави, когато извиква node-а. Немаркираните полета остават фиксирани и се четат от конфигурацията на node-а.

Например:

- Свържете Slack node към агент като инструмент
- Запазете удостоверението фиксирано в Slack node-а
- Маркирайте `message` като предоставяно от агента
- Агентът получава Slack инструмент, в който предоставя само съобщението по време на изпълнение

Ако node-ът не е свързан към агент като инструмент, иконата на бот е скрита и node-ът се държи като обикновена стъпка от workflow-а.

### Поведение по време на изпълнение

Когато агентът извика инструмент от canvas node, Heym временно обединява аргументите, предоставени от агента, в данните на този node, изпълнява node-а, връща изхода на node-а на агента и след това възстановява оригиналната конфигурация на node-а. Tool nodes не се изпълняват като обикновени стъпки от workflow-а чрез нормалното планиране; те се изпълняват само когато агентът ги извика.

Инструментите от canvas node са полезни с интеграционни nodes като Slack, Telegram, HTTP, Send Email и nodes за обработка на данни като [Set](./set-node.md). Trigger nodes, nodes за контрол на потока и терминални output mapper-и ([JSON output mapper](./json-output-mapper-node.md), [HTML output mapper](./html-output-mapper-node.md)) не могат да се използват като инструменти на агента.

## Python инструменти

Дефинирайте персонализирани инструменти, които агентът може да извиква. Всеки инструмент има:

| Поле | Тип | Описание |
|-------|------|-------------|
| `name` | string | Име на инструмента (напр. `count_characters`) |
| `description` | string | Описание за LLM-а |
| `parameters` | JSON Schema | Схема за function-calling на OpenAI (обектен формат) |
| `code` | string | Код на Python функция |

**Parameters** трябва да бъде JSON обект, а не низ:

```json
{
  "type": "object",
  "properties": {
    "text": { "type": "string", "description": "Text to count" }
  },
  "required": ["text"]
}
```

**Примерен инструмент:**

```python
def count_characters(text: str) -> int:
    return len(text)
```

> **Sandbox.** Python инструментите се изпълняват като ненадежден код в укрепен, изолиран Docker контейнер по подразбиране (без мрежа, без Docker socket, read-only файлова система, non-root). Импортирането е ограничено до allowlist от безопасни модули от стандартната библиотека. Вижте [Security → Python Tool Sandbox](../reference/security.md#python-tool-sandbox) за конфигурация (`HEYM_PYTHON_TOOL_SANDBOX`).

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `toolTimeoutSeconds` | number | Максимален брой секунди за изпълнение на инструмент (по подразбиране: 30) |
| `requestTimeoutSeconds` | number | Максимален брой секунди за изчакване на всеки отговор от модела преди изтичане на времето (по подразбиране: 60). Увеличете го за бавни или self-hosted доставчици (LiteLLM, vLLM, локални модели) и дълги многостъпкови изпълнения. |
## MCP връзки

Свържете се към [Model Context Protocol](https://modelcontextprotocol.io/) сървъри, за да предоставите техните инструменти на агента.

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `transport` | `"stdio"` \| `"sse"` \| `"streamable_http"` | Тип на връзката |
| `timeoutSeconds` | number | Време за изчакване за тази връзка (по подразбиране: 30) |
| `label` | string | Незадължително име за показване |

**stdio** (локален процес):

| Поле | Описание |
|-------|-------------|
| `command` | Команда за изпълнение (напр. `npx`) |
| `args` | JSON масив (напр. `["-y", "@modelcontextprotocol/server-filesystem", "--path", "/tmp"]`) |
| `env` | JSON обект с променливи на средата, инжектирани в процеса (напр. `{"GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_..."}`) |

Повечето stdio сървъри, използващи API ключове, се удостоверяват чрез променливи на средата, а не чрез аргументи на командата. Задайте `env` за всяка връзка поотделно, така че всеки agent node да може да използва различно удостоверение, без да засяга средата на хоста.

Стойностите на `env` поддържат [Expression DSL](../reference/expression-dsl.md), така че можете да подавате входни данни от workflow като удостоверения, вместо да вграждате тайни директно:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "$userInput.pat" }
}
```

Изразът `$userInput.pat` се разрешава по време на изпълнение спрямо входните данни на workflow преди стартирането на MCP процеса. Това Ви позволява да приемате token-и от trigger или входен node, вместо да ги вграждате в дефиницията на workflow.

Пример — GitHub MCP с твърдо зададен token:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxxxxxxxxx" }
}
```

Пример — GitHub MCP с динамичен token от входните данни на workflow:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "$userInput.pat" }
}
```

Пример — GitHub MCP с удостоверение за GitHub в Heym:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "$credentials.MyGitHubToken" }
}
```

Вграденото удостоверение за GitHub в момента е насочено към удостоверяване чрез PAT. Ако се нуждаете от достъп до организация, използвайте PAT с необходимите разрешения за организацията/хранилището.

Пример — Slack MCP:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-slack"],
  "env": { "SLACK_BOT_TOKEN": "xoxb-...", "SLACK_TEAM_ID": "T0123456" }
}
```

**SSE** (отдалечен сървър):

| Поле | Описание |
|-------|-------------|
| `url` | URL на SSE endpoint. Поддържа изрази (напр. `$userInput.serverUrl`). |
| `headers` | JSON обект за удостоверяване/персонализирани headers. Стойностите поддържат изрази. |

**Streamable HTTP** (отдалечен сървър):

| Поле | Описание |
|-------|-------------|
| `url` | URL на MCP endpoint (напр. `https://example.com/mcp`). Поддържа изрази. |
| `headers` | JSON обект за удостоверяване/персонализирани headers. Стойностите поддържат изрази. |

## Skills

Skills представляват инструкции във файл SKILL.md плюс незадължителни Python файлове и придружаващи ресурси. Те разширяват системния контекст на агента и могат да добавят Python инструменти.

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `name` | string | Име на skill |
| `content` | string | Съдържание на SKILL.md (инструкции) |
| `timeoutSeconds` | number | Време за изчакване за изпълнение на Python код на skill (по подразбиране: 30) |
| `driveFilesEnabled` | boolean | Активира помощната функция `heym_drive` по време на изпълнение за този skill (по подразбиране: false) |
| `files` | array | Незадължителни записи `{ path, content, encoding, mimeType }` (напр. `.py` скриптове или бинарни ресурси, съхранени като base64) |

Skills могат да се добавят чрез пускане на `.zip` или `.md` файл върху зоната Skills.
След като разгънете карта на skill, пуснете произволен файл върху този skill, за да прикачите или замените придружаващ файл, включително бинарни ресурси като PDF файлове и изображения.
Използвайте бутона за изтегляне на картата на skill, за да експортирате този skill като `.zip` архив за резервно копие или повторна употреба в друг workflow.

Активирайте **Drive files** за даден skill само когато неговият Python код трябва да чете файлове от Heym Drive. Активираните skills получават генерирана помощна функция `heym_drive.py` по време на изпълнение и могат да извикват `list_drive_files`, `get_drive_file`, `get_drive_file_path`, `read_drive_file`, `read_drive_text` или `read_drive_base64` с id на файл от Drive или точно име на файл. Търсенето по име на файл използва най-новото достъпно съвпадение. Деактивираните skills не получават помощната функция.

Всяка карта на skill има четири действия в реда под заглавието:

| Бутон | Описание |
|--------|-------------|
| **Edit with AI** | Отваря Skill Builder за преработка на skill чрез chat prompt |
| **Download** | Експортира skill като `.zip` архив |
| **Remove** | Изтрива skill от този agent node |
| **History** | Отваря историята на skill, получена от [Edit History](../reference/edit-history.md) |
### История на умението

Историята на умението **не** се съхранява отделно. Тя се извлича от snapshot-ите в Edit History на workflow-а: всяка запазена версия на workflow-а включва пълния масив `skills` на agent node-а.

От диалоговия прозорец History можете да:

- **Прегледате** минал snapshot (SKILL.md и списък с файлове)
- **Редактирате** — зарежда snapshot в редактора на умението, без да връщате целия workflow
- **AI Fine-tune** — отваря Skill Builder с този snapshot като начална точка
- **Върнете** — възстановява само това умение от минала версия (останалите nodes остават непроменени)

Историята следва същия 7-дневен срок на задържане като Edit History на workflow-а. Запазването на workflow-а след редакции на умението създава нови записи в историята.

Секцията Skills включва също **AI Build**:

- Натиснете **AI Build**, за да създадете ново умение от chat prompt
- Натиснете бутона с искрица върху съществуващо умение, за да го преработите с AI
- Пуснете файлове в composer-а на prompt-а, за да ги прикачите към коментара за fine-tune; тези файлове се запазват и като bundled assets на умението
- Модалният прозорец стриймва текста на асистента, докато показва preview на `SKILL.md` и `.py` файлове в реално време
- **Download ZIP** експортира текущия preview, без да го добавя към node-а
- **Save & Add** запазва генерираните файлове обратно чрез същия ZIP parsing flow, използван при ръчно качване

Когато редактирате с AI, Heym изпраща към builder-а само текстови `.md` и `.py` файлове на умението. Двоичните и други нередактируеми прикачени файлове се запазват и се споделят с builder-а като path metadata, така че генерираният Python код да може да поддържа правилни относителни препратки към файлове.
Изберете прикачен файл в десния панел и включете **Include this file in AI context**, когато AI трябва да прегледа bundled template. Текстови, PDF и DOCX файлове се извличат в контекста на prompt-а, когато е възможно; Heym не прилага отделно ограничение за размера на прикачените файлове в Skill Builder извън лимита за тяло на заявката на платформата.

## Extra Body

Някои доставчици приемат параметри на заявката, които стандартните OpenAI-съвместими полета не
покриват, като например изключване на режима на мислене на модел. Отметнете **Send extra request body** в
свойствата на node-а и въведете JSON обект.

```json
{
  "extraBodyEnabled": true,
  "extraBody": "{ \"thinking\": { \"type\": \"disabled\" } }"
}
```

- **Изключено по подразбиране.** Когато отметката е изключена, не се изпраща нищо допълнително.
- Прилага се към **всяка** заявка в цикъла за извикване на инструменти, не само към първия turn, плюс
  опита с fallback модел. Не се прилага към guardrail проверките, които използват отделен модел.
- Трябва да бъде JSON **обект**. Масив, скаларна стойност или неправилно форматиран текст провалят node-а с
  `Invalid extra body JSON`, вместо да бъдат тихо отхвърлени.
- `$` изразите се разрешават преди парсването. Тъй като това е текстова субституция, разрешена
  стойност, съдържаща двойна кавичка или нов ред, произвежда невалиден JSON и проваля node-а.

Същото поле и поведение като extra body на [LLM node](./llm-node.md).

## Guardrails

Включете **Guardrails** в свойствата на node-а, за да блокирате небезопасни потребителски съобщения, преди agent-ът да се изпълни. Вижте [Guardrails](../reference/guardrails.md) за пълната справка.

## Persistent memory (graph)

Опционална knowledge graph **за всеки agent node поотделно**, съхранявана в базата данни. Когато е включена, Heym добавя Markdown резюме на запомнените entities и relationships към **system instruction** преди всяко изпълнение (само ако графът не е празен). След **успешно** завършване на agent-а фонова задача извлича нови трайни факти от разговора и ги обединява в графа.

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `persistentMemoryEnabled` | boolean | Включва зареждане + фоново извличане за този canvas node |

**Sub-agents** поддържат **собствен** граф (ключован по техния node id), отделен от orchestrator-а.

Използвайте розовия контрол **brain** върху node-а (когато паметта е включена или редът на модела е показан), за да отворите редактора на графа и опционалното **memory sharing** (други workflow-и/agent-и). Пълно поведение, REST пътища и подробности за JSON експорт: [Agent Persistent Memory](../reference/agent-persistent-memory.md).

## Responses API и непрекъснатост на reasoning

Отметка **Use Responses API** насочва извикванията на модела на agent-а през
[Responses API](https://platform.openai.com/docs/api-reference/responses) вместо през Chat
Completions. По подразбиране е изключена.

Тя е най-важна при reasoning модел като `gpt-5` или серията `o`. Responses API връща
reasoning на модела заедно с всяко извикване на инструмент, а agent-ът подава тези reasoning items обратно
на следващия turn, така че моделът запазва веригата си на мисълта през многостъпков цикъл с инструменти, вместо
да я извежда наново след всеки резултат от инструмент. Целият цикъл работи по същия път, включително
[human review](#human-review-hitl) пауза и продължаване, [context compression](#context-compression)
и крайния отговор.

Самият разговор остава в Heym. Heym изпраща пълния вход при всеки turn и пренася
reasoning като криптиран blob, така че нищо не се задържа на страната на доставчика между извикванията.
Reasoning items в рамките на span, който context compression обобщава, се отхвърлят заедно с него, тъй като
криптиран blob не може да бъде обобщен.

Работи с OpenAI удостоверение и с персонализирано удостоверение, чийто gateway поддържа
endpoint-а. С Google удостоверение остава изключена.
## Компресиране на контекста

Когато даден агент изпълнява много итерации на инструменти с големи резултати (web scraping, четене на документи, изходи от под-workflow), натрупаната история на съобщенията може да достигне лимита на контекстния прозорец на модела. Heym автоматично компресира историята на разговора по време на изпълнение, за да предотврати препълване на контекста.

**Как работи:**

1. Преди всяка итерация на инструмент Heym изчислява текущия брой token-и (~4 символа на token).
2. Ако оценката надвиши **80%** от контекстния прозорец на модела, се задейства компресиране.
3. Историята на съобщенията се разделя на запазени и компресирани секции:
   - **Запазени**: system prompt, първото потребителско съобщение, най-скорошното потребителско съобщение
   - **Компресирани**: всичко между тях (turn-ове за разсъждение на асистента, извиквания на инструменти, резултати от инструменти)
4. Средната секция се обобщава с помощта на **същия модел и удостоверение** — не е необходима допълнителна конфигурация.
5. Компресираното обобщение замества средната секция като едно съобщение от асистента.

**Наблюдаемост:**

Събитията за компресиране се показват като записи `Context compressed (N messages → summary)` в:
- Списъка с извиквания на инструменти в **Debug panel** по време на изпълнение на живо
- Изгледа с детайли за изпълнение в **История на изпълненията**
- **Traces tab** като запис `context.compression` в трасинга

Компресирането е автоматично и винаги активно за Agent nodes. То **не** се прилага за LLM nodes, Chat tab или сесии на AI Assistant.
