# Heym

**Heym** node чете собствените данни на Heym: workflows, до които имате достъп, структурата на един workflow и историята на неговите изпълнения. Това е начинът, по който изграждате мета-workflows — инвентаризации на инстанции, обобщения на изпълнения и отчети за състоянието на самия Heym.

## Преглед

| Свойство | Стойност |
|----------|-------|
| Входове | 1 |
| Изходи | 1 |
| Операции | `listWorkflows`, `getWorkflow`, `getExecutionHistory` |
| Удостоверение | Не се изисква |

## Параметри

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `heymOperation` | Select | Кое четене да се извърши |
| `heymWorkflowId` | UUID | Целеви workflow. Задължителен за `getWorkflow` и `getExecutionHistory`. Поддържа изрази. |
| `heymLimit` | String | Максимален брой върнати редове. **Оставете го празно или въведете `0`, за да върнете всичко** — това е стойността по подразбиране. Поддържа изрази. |
| `heymStatus` | String | Незадължителен филтър по статус за `getExecutionHistory`. Поддържа изрази. |
| `heymSinceDays` | String | Незадължителен период на връщане назад в дни за `getExecutionHistory`. Поддържа изрази. |

Селекторът за workflow е падащо меню с търсене, което изброява всеки workflow, до който имате достъп.

## Обхват на достъп

Резултатите са ограничени до **собственика на workflow, в който се намира node** — не до този, който е стартирал изпълнението. Видимият набор е:

- workflows, които собственикът притежава,
- workflows, споделени директно със собственика,
- workflows, споделени с екип, към който собственикът принадлежи.

Ограничаването до собственика е това, което кара node да се държи идентично независимо дали изпълнението е стартирано ръчно, чрез cron, от портал или от събитие на платформата. Ограничаването до изпълнителя би върнало нищо при всяко изпълнение без надзор. Това е същото правило, което Heym вече използва за удостоверения и глобални променливи.

Workflow, до който нямате достъп, и workflow, който не съществува, връщат едно и също съобщение за грешка, така че node не може да бъде използван за проверка на workflow идентификатори.

## Операции

### List Workflows

Връща всеки workflow, до който собственикът има достъп, най-скоро актуализираните първи.

| Израз | Описание |
|------------|-------------|
| `$nodeLabel.workflows` | Масив от обобщения на workflows |
| `$nodeLabel.workflows[0].id` | UUID на workflow |
| `$nodeLabel.workflows[0].name` | Име на workflow |
| `$nodeLabel.workflows[0].description` | Описание или `null` |
| `$nodeLabel.workflows[0].active` | Дали workflow е активен |
| `$nodeLabel.workflows[0].folder_id` | UUID на папка или `null` |
| `$nodeLabel.workflows[0].updated_at` | ISO времеви печат на последното запазване |
| `$nodeLabel.workflows[0].node_count` | Колко nodes съдържа workflow |
| `$nodeLabel.total` | Пълен брой на достъпните **преди** прилагане на лимита |

`total` умишлено е неограниченият брой, така че `$inventory.total` все още отчита реалния размер, когато ограничите върнатите редове. Изчистването на **Limit** или задаването му на `0` връща всеки workflow — това е стойността по подразбиране.

### Get Workflow

Връща идентичността и структурата на един workflow.

| Израз | Описание |
|------------|-------------|
| `$nodeLabel.id`, `$nodeLabel.name`, `$nodeLabel.description` | Идентичност на workflow |
| `$nodeLabel.active`, `$nodeLabel.folder_id`, `$nodeLabel.updated_at` | Метаданни на workflow |
| `$nodeLabel.node_count` | Брой nodes |
| `$nodeLabel.nodes` | Масив от `{ id, type, label, position, data }` |
| `$nodeLabel.edges` | Масив от `{ id, source, target, sourceHandle, targetHandle }` |

`data` е **пълната конфигурация на node** — всяко поле, както е било запазено. Това прави одита възможен: не можете да сканирате workflow за API ключ, който някой е поставил в поле, ако node откаже да покаже полето.

Това не предоставя достъп, който извикващият вече не е имал. Node е ограничен до workflows, които собственикът така или иначе може да отвори в редактора, а запазените тайни на удостоверенията все още не са тук: данните на node съдържат само **идентификатори** на удостоверения, докато самите тайни живеят криптирани в таблицата с удостоверения.

### Сканиране за твърдо кодирани тайни

```
cron → heym (listWorkflows) → loop → heym (getWorkflow) → agent → slack
```

Дайте на agent `$detail.nodes` и го помолете да отбележи всяка стойност в `data`, която изглежда като активен ключ или token. Полетата, които си струва да се наблюдават, са тези със свободен текст — `curl` на HTTP nodes, `userMessage` и `systemInstruction` на LLM и Agent nodes, и телата на Python инструменти — защото идентификаторът на удостоверение е безобиден UUID, но поставен `sk-…` не е.
### Получаване на история на изпълненията

Връща записи от историята на изпълненията за даден workflow, най-новите първи.

| Израз | Описание |
|------------|-------------|
| `$nodeLabel.executions` | Масив от записи в историята |
| `$nodeLabel.executions[0].id` | UUID на изпълнението |
| `$nodeLabel.executions[0].status` | `success`, `error` и т.н. |
| `$nodeLabel.executions[0].started_at` | ISO времеви отпечатък |
| `$nodeLabel.executions[0].execution_time_ms` | Продължителност в реално време |
| `$nodeLabel.executions[0].trigger_source` | Какво е стартирало изпълнението, например `cron` или `heym_event` |
| `$nodeLabel.executions[0].recovered` | Дали изпълнението е било възстановено след срив |
| `$nodeLabel.executions[0].inputs` | Какво е получило изпълнението – trigger payload-ът или входните данни от извикващия |
| `$nodeLabel.executions[0].outputs` | Резултатът от workflow-а за това изпълнение |
| `$nodeLabel.workflow_id`, `$nodeLabel.workflow_name` | Workflow-ът, към който принадлежи историята |
| `$nodeLabel.total` | Общ брой съвпадащи изпълнения **преди** ограничението |
| `$nodeLabel.by_status` | Брояч по статус, например `{ "success": 41, "error": 3 }` |
| `$nodeLabel.since` | Начало на периода или `null` за цялата история |

Записите съдържат както `inputs`, така и `outputs` – какво е получило изпълнението и какво е върнало – но никога `node_results`: трасировката по възли е най-голямата колона в таблицата и би засенчила всичко след себе си. Извлечете отделно изпълнение чрез API, когато Ви е необходима пълната трасировка.

`total` и `by_status` винаги описват **цялата** съвпадаща история, дори когато **Limit** ограничава върнатите записи — така можете да извлечете петте най-скорошни изпълнения и въпреки това да отчетете точен брой на неуспехите.

Оставете **Since (days)** празно, за да обхванете всичко, **Status filter** празно, за да включите всеки статус, и **Limit** празно или `0`, за да върнете всеки запис.

## Примерен workflow

**Дневен дайджест на инстанциите**

```
cron → heym (listWorkflows) → loop → heym (getExecutionHistory) → llm → sendEmail
```

- **Heym** `listWorkflows` с етикет `inventory`
- **Loop** върху `$inventory.workflows`
- **Heym** `getExecutionHistory` с `heymWorkflowId`, зададен на `id` на елемента от цикъла, `heymSinceDays` със стойност `1` и `heymLimit` със стойност `5`
- **LLM** превръща събраните изпълнения и броячите по статус в четимо резюме

## Бележки

- Не е необходимо удостоверение; node-ът чете същата база данни, върху която работи Heym.
- **Limit** е едно и също поле за двете операции за изброяване и означава едно и също в двете: празно или `0` връща всичко.
- Node-ът приема нормален вход и може да бъде прикачен към Agent node като инструмент, така че агент може да отговаря на въпроси за Вашата Heym инстанция — или да я одитира.
- Payload-ите на `getWorkflow` растат заедно с workflow-а: дългите prompt-ове и телата на Python инструментите пътуват вътре в `data`.
- Комбинирайте го с [Heym Trigger](./heym-trigger-node.md), за да реагирате на промени в workflow-а в момента, в който се случат, вместо да правите проверки по график.
