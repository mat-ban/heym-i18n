# Heym Trigger

Възелът **Heym Trigger** стартира workflow, когато самата платформа Heym публикува събитие. Това е trigger възел с нулев вход за автоматизиране на Heym чрез Heym: одитни следи за промени, известия за внедряване и обобщения за състоянието на инстанцията.

## Преглед

| Свойство | Стойност |
|----------|-------|
| Входове | 0 |
| Изходи | 1 |
| Изход | `$nodeLabel.events`, `$nodeLabel.count`, `$nodeLabel.triggered_at` |
| Удостоверение | Не се изисква |

## Параметри

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `eventNames` | String array | Кои събития да се абонират. Оставете празно, за да получавате всяко събитие. |

## Събития

| Събитие | Публикува се, когато | Обхват |
|-------|----------------|-------|
| `heym.started` | Платформата Heym стартира | За цялата инстанция: всеки абонат го получава |
| `workflow.created` | Създава се workflow | Само абонатите на собственика на workflow |
| `workflow.updated` | Запазва се workflow | Само абонатите на собственика на workflow |
| `workflow.deleted` | Изтрива се workflow | Само абонатите на собственика на workflow |

Widget-ите на таблото се съхраняват вътрешно като workflows, но никога не генерират събития `workflow.*`.

## Доставянето е на партиди

Heym изпраща събития на всеки пет секунди. **Всяко събитие, заявено в един цикъл на изпращане, пристига в един единствен workflow run**, като масив.

- Създайте два workflow-а в рамките на пет секунди един от друг → **един** run с две събития.
- Създайте един workflow → **един** run с масив от един елемент.

Формата никога не се променя, така че последващите изрази никога не трябва да се разклоняват в зависимост от това дали е пристигнало едно събитие или много. Когато трябва да действате веднъж за събитие, поставете възел [Loop](./loop-node.md) върху `$nodeLabel.events`.

## Доставяне точно веднъж

Всяко събитие се заявява за всеки абониран възел чрез уникално ограничение в базата данни, преди да бъде доставено. Това важи за всеки uvicorn worker, всеки контейнер и всяка машина: стартирането на Heym на два сървъра не доставя събитие два пъти. Ако заявката не може да бъде записана, събитието не се доставя изобщо — дизайнът се проваля затворено, вместо да задейства два пъти.

Два различни възела `heymTrigger`, абонирани за едно и също събитие, го получават по веднъж; те не се конкурират за него.

## Прозорецът на изпращане

Диспетчерът разглежда само събития, публикувани през **последните пет минути**. По-старите събития остават в лога за преглед, но никога не се доставят. Това ограничава случващото се след престой: възстановяването на Heym след час офлайн не възпроизвежда нищо, вместо да задейства час натрупани събития наведнъж.

Събитията се пазят **7 дни** и след това се изтриват.

## Изходни полета

| Израз | Описание |
|------------|-------------|
| `$nodeLabel.events` | Масив от обекти на събития, най-старите първи. Винаги масив. |
| `$nodeLabel.events[0].id` | UUID на събитието |
| `$nodeLabel.events[0].name` | Име на събитието, например `workflow.created` |
| `$nodeLabel.events[0].payload` | Тяло на събитието |
| `$nodeLabel.events[0].workflow_id` | Id на съответния workflow или `null` за `heym.started` |
| `$nodeLabel.events[0].created_at` | ISO timestamp за момента на публикуване на събитието |
| `$nodeLabel.count` | Брой събития в тази партида |
| `$nodeLabel.triggered_at` | ISO timestamp за изпълнението на workflow |

### Форми на payload

`workflow.created`, `workflow.updated`, `workflow.deleted`:

```json
{
  "workflow_id": "…",
  "name": "Nightly report",
  "owner_id": "…",
  "actor_user_id": "…",
  "updated_at": "2026-08-11T09:30:00+00:00"
}
```

`heym.started`:

```json
{ "version": "1.4.2", "started_at": "2026-08-11T09:30:00+00:00" }
```

`workflow.deleted` носи името, записано непосредствено преди изтриването, тъй като редът на workflow вече го няма, когато прочетете събитието.

## Примерен workflow

**Одитна следа за промени по workflow**

```
heymTrigger → heym (getWorkflow) → slack
```

- **Heym Trigger** с етикет `platformEvents`, абониран за `workflow.created`, `workflow.updated`, `workflow.deleted`
- Възел **Heym** с `getWorkflow` и `heymWorkflowId`, зададен на `$platformEvents.events[0].workflow_id`
- Съобщение в **Slack**: `"$platformEvents.count workflow change(s), latest: $platformEvents.events[0].name"`

## Бележки

- `heym.started` се задейства **веднъж за стартиране на платформата**, а не веднъж за worker, въпреки че Heym изпълнява осем worker-а на контейнер. Контейнерите, които стартират на повече от пет минути един от друг, публикуват по едно събитие.
- Изпълненията, задействани по този начин, се появяват в историята с `trigger_source = "heym_event"`.
- Задайте **Events** на none, вместо да изброявате всичките четири, ако искате автоматично да получавате типове събития, добавени в бъдещи версии.
