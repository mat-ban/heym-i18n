# Постоянна памет на агента

Agent nodes могат да поддържат **граф на знанията за конкретен node**, съхранен в базата данни: обекти (с типове и свойства) и връзки между тях. Когато е активирано, Heym **инжектира резюме на този граф в системния prompt** при всяко изпълнение (ако графът не е празен). След успешно изпълнение **задача за извличане чрез LLM** обединява нови факти от разговора в графа на заден план.

Подагентите и оркестраторите използват по подразбиране графа, свързан с **техния собствен canvas node**. Може също да **предоставите на други агенти достъп за четене или четене/запис** до графа на този node (включително агенти в **други workflows**, които притежавате)—вижте [Споделяне с други агенти](#sharing-with-other-agents).

## Активиране

| Параметър | Тип | Описание |
|-----------|------|-------------|
| `persistentMemoryEnabled` | boolean | Когато е `true`, зарежда графа на този node в системния prompt и планира извличане след изпълнение за графа на този node |
| `memoryShares` | array (незадължителен) | Предоставя на други agent nodes достъп до графа на паметта на **този** node; вижте [Споделяне](#sharing-with-other-agents) |

Активирайте го в свойствата на Agent node (**Persistent memory (graph)**). Розова икона **мозък** върху node отваря редактора на графа, когато паметта е активирана (или когато е показан модел).

## Редактор на графа

Диалоговият прозорец визуализира обектите като анимиран, force-directed граф — цветни кръгове, оразмерени според броя връзки и групирани по тип обект — плюс редактиране и навигация (fit view, подредба на оформлението, клавишни комбинации). Може да **добавяте, редактирате или изтривате** nodes и ребра ръчно; селекторите за връзка Source/Target са с търсене за графи с много обекти. Избирането на node показва изходящите и входящите му връзки, като всяка е кликаема за преминаване към съответния node. Промените се прилагат само към графа на **този** агент (графът за canvas node, чийто мозък сте отворили).

## Споделяне с други агенти

В диалоговия прозорец на графа на паметта, **Share memory with other agents** Ви позволява да прикачите **peer** агенти, които могат да консумират този граф по време на изпълнение:

1. Изберете **workflow** (всеки workflow, който можете да отворите в редактора).
2. Изберете **agent** node в този workflow.
3. Задайте **Read only** или **Read & write**.

| Разрешение | Ефект |
|------------|--------|
| Read only | Когато **peer** агентът се изпълни, този граф се обединява в системния prompt на peer агента (ако има обекти). Няма извличане в този граф от изпълнението на peer агента. |
| Read & write | Същото поведение на prompt като при четене, и след **успешно** завършване на peer агента, обичайното извличане на памет може също да **се обедини в този (собственически) граф**, използвайки удостоверението на peer изпълнението. |

Peers се съхраняват за всеки собственически node като записи в `memoryShares` с `peerWorkflowId` и `peerCanvasNodeId` (и `permission`). По-стари workflows може да пропускат `peerWorkflowId` за peers в **същия** workflow; редакторът третира това като текущия workflow.

**Споделянето между workflows** се разрешава по време на изпълнение чрез сканиране на workflows, **които притежавате**. Изпълнения без удостоверен потребителски контекст разрешават само споделяния, дефинирани в JSON на **текущия** workflow (същия canvas).

## Поведение по време на изпълнение

### Собствен граф (`persistentMemoryEnabled`)

1. **Преди LLM извикването** — Ако графът има обекти, блок се добавя към системната инструкция, обясняващ, че това са факти от предишни изпълнения (може да са непълни; текущото потребителско съобщение има предимство при конфликт).
2. **След успешно завършване** — Фонова задача пита модела (със същото удостоверение като изпълнението на агента) за структуриран JSON (обекти + връзки). Този payload се обединява в базата данни (прилагат се дедупликация и почистване на връзки за някои типове, напр. ребра от тип заетост).

### Peer, получаващ споделени графи

Когато даден агент се изпълни, системата намира **собственически** nodes (във всеки от Вашите workflows, когато е възможно), чиито `memoryShares` сочат към workflow и canvas node на това изпълнение. За всяко съвпадение графът на този собственик се добавя като секция **shared memory** в системния prompt. Peers с **Read & write** допълнително планират цели за извличане за **собственическия** workflow/граф, когато изпълнението успее.

Извличането **не** се изпълнява, когато изпълнението завърши с грешка или в състояние на изчакване на HITL.

## Workflow JSON (`data` поле)

Съхранява се в agent node като други настройки:

```json
{
  "type": "agent",
  "data": {
    "label": "supportAgent",
    "persistentMemoryEnabled": true,
    "userMessage": "$input.text",
    "memoryShares": [
      {
        "peerWorkflowId": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
        "peerCanvasNodeId": "agent-peer-canvas-id",
        "permission": "read"
      }
    ]
  }
}
```

`permission` е `"read"` или `"write"`. Пропуснете `memoryShares` или използвайте `[]`, когато няма споделяне.

Вижте [Workflow Structure](./workflow-structure.md) за пълната форма на обекта node.
