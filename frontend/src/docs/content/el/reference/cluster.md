# Κατανομή Φόρτου

Κατευθύνετε ένα δεύτερο instance του Heym στην ίδια βάση δεδομένων PostgreSQL και αυτό εντάσσεται ως worker. Οι εκτελέσεις workflow στο παρασκήνιο μοιράζονται τότε μεταξύ των instances με ένα ποσοστό που ορίζετε, ώστε το μηχάνημα που εξυπηρετεί το UI και το API να μην είναι και το μοναδικό μηχάνημα που εκτελεί κάθε workflow.

Τα instances δεν επικοινωνούν ποτέ μεταξύ τους. Η Postgres μεταφέρει την εργασία, οπότε ένας worker δεν χρειάζεται ανοιχτή θύρα, πιστοποιητικό ή διαδρομή επιστροφής προς το κύριο instance — μόνο πρόσβαση στη βάση δεδομένων.

## Ρόλοι

Ένα instance είναι το **main**, καθορισμένο μέσω μεταβλητής περιβάλλοντος. Εξυπηρετεί το UI, το API, το MCP και την πύλη chat, και κατέχει την αποθήκευση αρχείων και τα εγκατεστημένα plugins. Κάθε άλλο instance είναι **worker**: έχει πρόσβαση μόνο στη βάση δεδομένων και εκτελεί εκτελέσεις στο παρασκήνιο.

```
HEYM_CLUSTER_ENABLED=true
HEYM_INSTANCE_ROLE=main       # or: worker
HEYM_INSTANCE_NAME=EU Main    # display label, editable later from Settings
HEYM_INSTANCE_ID=eu-main      # optional; derived from the name when empty
```

Ο ρόλος main είναι ξεχωριστός από την εκλογή leader. Το Heym εκλέγει ήδη έναν leader σε ολόκληρο το cluster για να κατέχει το cron, την αξιολόγηση ειδοποιήσεων και την ανάκτηση μετά από κατάρρευση· αν το main πέσει, η ηγεσία μεταφέρεται σε έναν worker μέσα σε λίγα δευτερόλεπτα και οι προγραμματισμένες εκτελέσεις συνεχίζουν να εκτελούνται. Ο ρόλος main δεν μεταφέρεται, επειδή η αποθήκευση αρχείων δεν μπορεί να μεταφερθεί μαζί του.

## Τι μπορεί να φύγει από το κύριο instance

Η τοποθέτηση αποφασίζεται από τους κόμβους του workflow πριν ξεκινήσει η εκτέλεση. Μια εκτέλεση παραμένει στο main όταν οποιοσδήποτε κόμβος της — συμπεριλαμβανομένων κόμβων μέσα σε sub-workflows που καλεί — αγγίζει κάτι που υπάρχει μόνο σε ένα μηχάνημα:

| Node | Γιατί παραμένει στο main |
|---|---|
| Codex, OpenCode Go | Ο χώρος εργασίας του coding-agent παραμένει στον τοπικό δίσκο ώστε μια συνέχεια να μπορεί να συνεχιστεί σε αυτόν |
| Agent με συνδεδεμένο skill | Ο κώδικας του skill διαβάζει και γράφει στο Heym Drive |
| Drive, Converter, Google Drive | Διαβάζουν και γράφουν παραγόμενα αρχεία |
| File Upload trigger | Το upload προσγειώνεται στον δίσκο του main |
| Send Email | Οι εταιρικοί SMTP relays συνήθως επιτρέπουν μία διεύθυνση προέλευσης |
| Plugin nodes | Ένα plugin είναι εγκατεστημένο στον δίσκο ενός instance |

**Όλα τα υπόλοιπα κατανέμονται** — συμπεριλαμβανομένων του Code node, του Playwright και των Agent Python tools. Κάθε instance εκτελεί το ίδιο image με το δικό του Docker socket, οπότε ένα sandbox δεν αποτελεί λόγο να παραμείνει μια εκτέλεση στο main, και αυτοί είναι οι πιο απαιτητικοί σε CPU κόμβοι του προϊόντος.

Ένα workflow του οποίου το sub-workflow επιλέγεται από έκφραση δεν μπορεί να επιθεωρηθεί εκ των προτέρων, οπότε παραμένει στο main.

## Επιλογή ποσοστών

Τα βάρη είναι ακέραιοι αριθμοί που ορίζονται στις **Settings → Instances**. Είναι **μερίδια όποιων instances μπορούν αυτή τη στιγμή να αναλάβουν εργασία**, όχι ποσοστά του 100: ο scheduler διαιρεί με το δικό του σύνολο αυτής της δεξαμενής.

Αυτή η διάκριση εμφανίζεται μόλις ένα instance βγει εκτός. Με `Main 41, Worker A 26, Worker B 33`, απενεργοποιώντας τον Worker B απομένει δεξαμενή 67, οπότε το Main λαμβάνει πραγματικά 41/67 = **61%** και ο Worker A 26/67 = **39%**. Το πάνελ εκτυπώνει την πραγματική κατανομή κάτω από τον πίνακα ακριβώς για αυτόν τον λόγο, και η αποθήκευση δεν μπλοκάρεται ποτέ επειδή οι αριθμοί δεν αθροίζουν σε 100 — απορρίπτεται μόνο μια κατανομή όπου κανένα ενεργοποιημένο instance δεν έχει βάρος.

Δύο ακόμη πράγματα είναι εύκολο να παρεξηγηθούν.

**Ένα ποσοστό δεν είναι μερίδιο της υπολογιστικής ισχύος.** Καλύπτει μόνο εκτελέσεις που περνούν από την ουρά. Η εξυπηρέτηση του UI και του API, οι εκτελέσεις streaming του editor και της πύλης, και ο χειρισμός των uploads αρχείων είναι όλα εργασία του main και τίποτα από αυτά δεν υπολογίζεται. Το main κάνει περισσότερα από όσα λέει ο αριθμός του.

**Το ποσοστό του main είναι ανώτατο όριο, όχι κατώτατο.** Οι εκτελέσεις που μπορούν να εκτελεστούν μόνο στο main χρεώνονται στο quota του, οπότε μόλις εξαντληθεί αυτό το quota οι υπόλοιπες κατανεμητέες εκτελέσεις πέφτουν στους workers. Το να ορίσετε χαμηλά τον αριθμό του main είναι ασφαλές — η εργασία που πρέπει να εκτελεστεί εκεί εκτελείται ακόμη. Το να τον ορίσετε υψηλά στερεί πόρους από τους workers.

Έτσι, με ένα ισχυρό main και έναν μικρότερο worker, ξεκινήστε πιο κοντά στο 60/40 παρά στην ακατέργαστη αναλογία των μηχανημάτων, και μετά συγκρίνετε πραγματικές διάρκειες εκτελέσεων στην καρτέλα Traces και προσαρμόστε.

Τα βάρη επανακανονικοποιούνται σε όλα τα instances που είναι αυτή τη στιγμή ενεργά και ενεργοποιημένα. Με `main=70, A=15, B=15`, αν ο A πάει offline η κατανομή γίνεται 70/85 και 15/85 μεταξύ main και B, και επιστρέφει σε 70/15/15 όταν ο A επανέλθει.

**Ένα instance που επανέρχεται δεν του οφείλονται οι εκτελέσεις που έχασε.** Ο χρόνος που πέρασε Offline, Disabled ή σε μη ταιριαστή έκδοση δεν υπολογίζεται εις βάρος του, οπότε ένας worker που πέρασε μια νύχτα μη διαθέσιμος επανεντάσσεται στην τρέχουσα θέση της δεξαμενής και η κατανομή διαβάζεται ξανά 70/30 από την πρώτη του εκτέλεση — δεν απορροφά κάθε εκτέλεση μέχρι να φτάσει τους υπόλοιπους. Ένας worker που ήταν διαθέσιμος όλη την ώρα εξακολουθεί να φτάνει τους υπόλοιπους, και αυτό είναι που κάνει το ποσοστό του main ανώτατο όριο.

### Ένα νέο instance εντάσσεται στο μηδέν

Ένα instance στο οποίο δεν έχει δοθεί ποτέ βάρος ξεκινά από το 0, το οποίο θα το άφηνε Live, Enabled και να μη λαμβάνει τίποτα. Η επιλογή **Give new instances a share automatically** — ενεργή από προεπιλογή, κάτω από τον πίνακα instances — το διορθώνει: στην επόμενη διέλευση του leader ο νεοεισερχόμενος λαμβάνει ίσο μερίδιο της δεξαμενής, και τα υπάρχοντα βάρη κλιμακώνονται προς τα κάτω διατηρώντας τις αναλογίες μεταξύ τους, ώστε ένα σκόπιμο 70/30 να διαβάζεται ακόμη ως περίπου 70/30 μετά. Το σύνολο παραμένει ακριβώς 100.

Αυτό εκτελείται **μία φορά ανά instance**. Τόσο η αυτόματη διέλευση όσο και η δική σας επεξεργασία σηματοδοτούν το instance ως configured, οπότε ένα instance που ορίσατε μόνοι σας δεν αλλάζει ποτέ πίσω από την πλάτη σας — συμπεριλαμβανομένου ενός που σκόπιμα ορίσατε σε 0. Απενεργοποιήστε τη ρύθμιση αν προτιμάτε κάθε νέο μηχάνημα να περιμένει εσάς.

Μόνο ενεργοποιημένα, ενεργά και συμβατά instances συμμετέχουν. Η παραχώρηση μεριδίου σε ένα μηχάνημα που δεν μπορεί να εκτελέσει τίποτα θα άφηνε αυτό το μερίδιο αδιάθετο.
### Όταν τα ποσοστά δεν μπορούν να βοηθήσουν

Ο πίνακας ρυθμίσεων αναφέρει πόσες από τις εκτελέσεις των τελευταίων 24 ωρών μπόρεσαν να εκτελεστούν μόνο στο main. Εάν ο αριθμός αυτός είναι υψηλός — ένας φόρτος εργασίας με πολλά Codex ή Drive — οι workers θα παραμείνουν αδρανείς ανεξάρτητα από το τι λένε τα βάρη, και η λύση είναι μια μεγαλύτερη κύρια instance παρά περισσότερες από αυτές.

## Διαστασιολόγηση PostgreSQL για ένα cluster

Οι συνδέσεις κλιμακώνονται με τις instances, όχι μόνο με τους χρήστες. Κάθε instance εκτελεί αρκετές διεργασίες uvicorn, και κάθε διεργασία διατηρεί ένα connection pool συν τέσσερις συνδέσεις `LISTEN` (ακύρωση, αφυπνίσεις ουράς, αποτελέσματα εκτελέσεων, ροές chat). Οι ανοιχτές ροές chat μοιράζονται τη μία σύνδεση chat, επομένως δεν προσθέτουν συνδέσεις βάσης δεδομένων. Ένα cluster τριών instances με την προεπιλεγμένη τιμή `max_connections = 100` εξαντλείται, και τότε το Heym αποτυγχάνει να προσεγγίσει τη δική του βάση δεδομένων.

Υπολογίστε χονδρικά `instances x processes x (async pool + sync pool + 4)` και ορίστε το `max_connections` πάνω από αυτό.

Μειώστε τα pools αντί να αυξήσετε μόνο το ανώτατο όριο. Μια μεμονωμένη εγκατάσταση έχει προεπιλογή 10+20 ασύγχρονες και 5+10 σύγχρονες συνδέσεις ανά διεργασία, που είναι γενναιόδωρο για ένα μηχάνημα και υπερβολικά πολύ για ένα cluster:

| Μεταβλητή | Μεμονωμένη instance | Cluster |
|---|---|---|
| `HEYM_DB_POOL_SIZE` | 10 | 3 |
| `HEYM_DB_MAX_OVERFLOW` | 20 | 5 |
| `HEYM_DB_SYNC_POOL_SIZE` | 5 | 2 |
| `HEYM_DB_SYNC_MAX_OVERFLOW` | 10 | 3 |

Το παράδειγμα αρχείου compose ορίζει αυτά και το `max_connections = 300`. Αυτό μειώνει ένα cluster δύο instances από ανώτατο όριο 768 συνδέσεων σε 192, με τρεις instances να παραμένουν κάτω από 300.

## Απαιτήσεις που το cluster δεν μπορεί να επιβάλει για εσάς

**Κάθε instance πρέπει να χρησιμοποιεί το ίδιο `SECRET_KEY` και `ENCRYPTION_KEY`.** Ένας worker με διαφορετικό `ENCRYPTION_KEY` δεν μπορεί να αποκρυπτογραφήσει διαπιστευτήρια, και κάθε εκτέλεση που χρησιμοποιεί διαπιστευτήρια θα αποτύγχανε με ένα σφάλμα που δεν κατονομάζει τίποτα χρήσιμο. Το Heym συγκρίνει ένα digest και των δύο κλειδιών σε κάθε heartbeat, μαζί με την έκδοση της εφαρμογής και την αναθεώρηση της βάσης δεδομένων, και επισημαίνει μια ασύμβατη instance ως **Mismatch** ώστε να μην λαμβάνει καθόλου εργασία. Ο φόρτος επιστρέφει στο main μέχρι να το διορθώσετε.

Αυτό καθορίζει επίσης τη σειρά αναβάθμισης. Η αναβάθμιση του main πρώτα επισημαίνει κάθε worker ως ασύμβατο· η εργασία επιστρέφει στο main, και κάθε worker επανεντάσσεται καθώς αναβαθμίζεται. Πιο αργό, ορατό και αναστρέψιμο.

**Κατευθύνετε το ingress μόνο στην κύρια instance.** Η κατανομή της κίνησης των χρηστών με round-robin σε όλες τις instances θα έστελνε μια μεταφόρτωση αρχείου σε ένα μηχάνημα και τη λήψη του σε ένα άλλο. Τίποτα στον κώδικα δεν το εμποδίζει, επειδή ένας worker εκτελεί το ίδιο image και θα απαντήσει σε οποιοδήποτε αίτημα λάβει.

**Κάθε instance χρειάζεται `FRONTEND_URL`, ορισμένο στην ίδια δημόσια διεύθυνση.** Μια εκτέλεση που διακόπτεται για ανθρώπινη αξιολόγηση δημιουργεί τον σύνδεσμο αξιολόγησής της στην instance που την εκτέλεσε, όχι στο main, και το ίδιο ισχύει για τους συνδέσμους παρακολούθησης του Codex και για τα URLs λήψης των παραγόμενων αρχείων. Ένας worker χωρίς αυτό δημιουργεί αυτούς τους συνδέσμους με βάση τη δική του τοπική διεύθυνση, και όποιος λάβει έναν από αυτούς δεν μπορεί να τον ανοίξει.

**Οι worker instances έχουν διαφορετική εξερχόμενη IP.** Οποιοδήποτε API επιτρέπει διευθύνσεις προέλευσης βλέπει τη νέα. Το Send Email εκτελείται στο main για αυτόν ακριβώς τον λόγο· για τον node HTTP, είτε δώστε στο cluster μία μοναδική διεύθυνση εξόδου NAT είτε επιτρέψτε κάθε instance.

## Προσθήκη worker σε άλλο μηχάνημα

Το `docker-compose.worker.yml` στη ρίζα του αποθετηρίου εκτελεί έναν worker στον δικό του host. Δεν έχει βάση δεδομένων και δεν έχει UI: προσεγγίζει την PostgreSQL της κύριας instance και λαμβάνει το μερίδιό του από τις εκτελέσεις υποβάθρου.

Συμπληρώστε ένα `.env` δίπλα του — image tag, host και διαπιστευτήρια βάσης δεδομένων, και τα δύο κλειδιά, και ένα instance id — και ξεκινήστε το. Το Compose αρνείται να ξεκινήσει μέχρι να οριστεί κάθε απαιτούμενη τιμή, αντί να ξεκινήσει με ένα placeholder που αποτυγχάνει αργότερα με τρόπο δύσκολο να διαβαστεί.

Το image tag πρέπει να είναι η έκδοση που εκτελεί το main, και τα δύο κλειδιά πρέπει να αντιγραφούν ακριβώς. Διαφορά σε οποιοδήποτε από τα δύο εμφανίζει τον worker ως Mismatch και δεν λαμβάνει εργασία.

## Ανάγνωση του πίνακα Instances

| Στήλη | Σημασία |
|---|---|
| Name | Επεξεργάσιμη ετικέτα· αποτυπώνεται σε κάθε εκτέλεση που εκτελεί αυτή η instance |
| Role | `main` ή `worker`, από το περιβάλλον |
| Status | **Live** με πρόσφατο heartbeat, **Offline** μετά από 30 δευτερόλεπτα σιωπής, **Mismatch** όταν η έκδοση, η αναθεώρηση της βάσης δεδομένων ή τα κλειδιά διαφέρουν από του main |
| ms | Χρόνος μετάβασης από αυτή την instance στη βάση δεδομένων, μετρημένος από την ίδια την instance |
| On | Αφαιρέστε έναν worker από την εναλλαγή χωρίς να τον σταματήσετε — οι εκτελέσεις που βρίσκονται σε εξέλιξη ολοκληρώνονται, δεν ανατίθενται νέες. Κλειδωμένο στο on για την κύρια instance: εργασία αρχείων, plugin και coding-agent εκτελείται εκεί ανεξάρτητα από το τι λέει ο διακόπτης |
| Weight | Το μερίδιό του από τις κατανεμημένες εκτελέσεις |

## Όρια ταυτοχρονισμού σε cluster

Το [όριο ταυτοχρονισμού](./webhooks.md#concurrency-limit-and-queued-runs) ενός workflow καταμετράται στην PostgreSQL, επομένως ισχύει σε κάθε instance και σε κάθε διεργασία: δύο instances δεν εκτελούν ποτέ περισσότερες εκτελέσεις ενός workflow από όσες επιτρέπει το όριο. Μια εκτέλεση που περίμενε για διαθέσιμη θέση τοποθετείται με τους ίδιους κανόνες όπως κάθε άλλη εκτέλεση κατά την εκκίνηση, έτσι ώστε μια εκτέλεση που πρέπει να παραμείνει στο main να παραμένει εκεί. Ο worker ουράς που εκτελεί αυτές τις εκτελέσεις ξεκινά τώρα σε κάθε εγκατάσταση, συμπεριλαμβανομένου ενός μεμονωμένου instance, όπου αναλαμβάνει μόνο τις εκτελέσεις που μπήκαν στην ουρά από το δικό του instance. Αυτό σημαίνει ότι ένα μεμονωμένο instance διατηρεί επίσης τη σύνδεση αφύπνισης ουράς `LISTEN` σε κάθε διεργασία, επομένως προϋπολογίστε τις συνδέσεις του με τον ίδιο τρόπο όπως σε ένα instance cluster.

## Ιστορικό εκτελέσεων

Κάθε εκτέλεση στο ιστορικό εκτελέσεων κατονομάζει την instance που την εκτέλεσε, και και οι δύο διάλογοι ιστορικού μπορούν να φιλτράρουν σε μία instance. Το φίλτρο ταιριάζει με το id της instance ενώ εμφανίζει το όνομά της, επομένως η μετονομασία μιας instance δεν ξαναγράφει αυτό που λένε οι παλιές εκτελέσεις.

Τίποτα από αυτά δεν εμφανίζεται σε μια εγκατάσταση μίας instance: τα πεδία είναι κενά, δεν εμφανίζεται ετικέτα και δεν προσφέρεται φίλτρο.
## Συμπεριφορά σε περίπτωση αποτυχίας

**Εάν ένας worker τερματιστεί κατά τη διάρκεια εκτέλεσης**, το heartbeat του καθίσταται stale και το υπάρχον recovery sweep του leader επανεκτελεί την εκτέλεση σε μια ενεργή instance. Η γραμμή της ουράς που είχε δεσμεύσει αποσύρεται ξεχωριστά: μόλις δεν υπάρχει ενεργή εκτέλεση για αυτήν και έχει παρέλθει περίοδος χάριτος δύο λεπτών, ο leader θέτει τη γραμμή σε κατάσταση αποτυχίας και αφυπνίζει όποιον ανέμενε το αποτέλεσμα. Η ηλικία από μόνη της δεν αποτελεί ποτέ το trigger, επομένως μια θεμιτά μακρά εκτέλεση δεν διακόπτεται· και η γραμμή τίθεται σε κατάσταση αποτυχίας αντί να επανατοποθετηθεί στην ουρά, διότι η recovery έχει ήδη αναλάβει την επανεκτέλεση και η επανατοποθέτηση στην ουρά θα εκτελούσε το ίδιο workflow δύο φορές.

**Εάν το main καταρρεύσει**, το cron συνεχίζει να ενεργοποιείται από έναν worker και οι distributable εκτελέσεις συνεχίζουν να εκτελούνται. Οι εκτελέσεις που απαιτούν το main εισέρχονται σε ουρά και αναμένουν, και εκτελούνται όταν αυτό επανέλθει — αλλά μόνο εντός του παραθύρου χάριτος misfire (`HEYM_CRON_MISFIRE_GRACE_SECONDS`, 600 δευτερόλεπτα από προεπιλογή). Οτιδήποτε παλαιότερο κλείνει ως skipped, με τον λόγο καταγεγραμμένο, αντί να αναπαράγεται ώρες εκκρεμών εκτελέσεων ταυτόχρονα.

Το UI, το API, το MCP και ο editor δεν είναι διαθέσιμα όσο το main είναι εκτός λειτουργίας, διότι τα ingress points βρίσκονται εκεί.
