# Ασφάλεια

Πρακτικές ασφαλείας και διαμόρφωση για την πλατφόρμα Heym.

## Πολιτική Κωδικών Πρόσβασης

Όλοι οι κωδικοί πρόσβασης — κατά την εγγραφή και κατά την αλλαγή του κωδικού σας — πρέπει να πληρούν τις ακόλουθες απαιτήσεις:

| Κανόνας | Απαίτηση |
|------|-------------|
| Ελάχιστο μήκος | 8 χαρακτήρες |
| Κεφαλαία | Τουλάχιστον ένα κεφαλαίο γράμμα (A–Z) |
| Πεζά | Τουλάχιστον ένα πεζό γράμμα (a–z) |
| Ψηφίο | Τουλάχιστον έναν αριθμό (0–9) |

Οι κανόνες αυτοί επιβάλλονται τόσο στο frontend όσο και στο backend (Pydantic validator). Ένα αίτημα με μη συμμορφούμενο κωδικό πρόσβασης απορρίπτεται με απόκριση `422 Unprocessable Entity` πριν από οποιαδήποτε εγγραφή στη βάση δεδομένων.

**Παράδειγμα έγκυρου κωδικού πρόσβασης:** `MyWorkflow7!`

## Διαχείριση Συνεδριών

- Τα access tokens αποθηκεύονται σε cookies **HttpOnly**, όχι στο `localStorage`. Αυτό αποτρέπει τη JavaScript (συμπεριλαμβανομένων των payloads XSS) από το να διαβάσει το token.
- Το refresh token περιορίζεται στη διαδρομή `/api/auth/refresh` και δεν μπορεί να αποσταλεί σε άλλα endpoints.
- Κάθε κλήση στο `/api/auth/refresh` **περιστρέφει** το refresh token: το παλιό token ανακαλείται αμέσως και εκδίδεται ένα νέο. Η επανάληψη ενός χρησιμοποιημένου refresh token επιστρέφει `401`.

## Περιορισμός Ρυθμού

Τα ακόλουθα endpoints υπόκεινται σε περιορισμό ρυθμού ανά IP:

| Endpoint | Όριο | Διάρκεια αποκλεισμού |
|----------|-------|--------------|
| `POST /api/auth/login` | 10 req / 60 s | 15 min |
| `POST /api/auth/register` | 5 req / 60 s | 10 min |
| `POST /register` (OAuth clients) | 5 req / 60 s | 10 min |
| Σύνδεση Portal | 3 προσπάθειες | 24 h |

Όταν έχει διαμορφωθεί το `REDIS_URL`, τα όρια ρυθμού κοινοποιούνται σε όλους τους backend workers. Χωρίς αυτό, τα όρια εφαρμόζονται ανά διεργασία worker.

## Κρυπτογράφηση Διαπιστευτηρίων

Όλα τα API keys, τα webhook URLs και τα bearer tokens που αποθηκεύονται στον πίνακα [Διαπιστευτήρια](../tabs/credentials-tab.md) κρυπτογραφούνται σε κατάσταση ηρεμίας χρησιμοποιώντας AES-256 (Fernet) πριν από την εγγραφή τους στη βάση δεδομένων. Το κλειδί προέρχεται από τη μεταβλητή περιβάλλοντος `ENCRYPTION_KEY`. Τα scripts `run.sh` και `deploy.sh` δημιουργούν αυτόματα μια ισχυρή τιμή όταν αυτή είναι κενή· η εφαρμογή αρνείται να εκκινήσει εάν το `ENCRYPTION_KEY` είναι κενό ή έχει παραμείνει σε γνωστό placeholder.

## MCP API Key

Το MCP API key χρησιμοποιείται για την επαλήθευση ταυτότητας εξωτερικών MCP clients που συνδέονται στο endpoint `/api/mcp/sse`. Όταν δημιουργηθεί η σύνδεση SSE, εκδίδεται ένα βραχύβιο (1 ώρας) session token και ενσωματώνεται στο URL του endpoint μηνυμάτων αντί του πραγματικού API key, αποτρέποντας την εμφάνιση του κλειδιού στα αρχεία καταγραφής πρόσβασης του διακομιστή. Ανατρέξτε στην [Καρτέλα MCP](../tabs/mcp-tab.md) για τη διαμόρφωση.

## OAuth / PKCE

Ο διακομιστής εξουσιοδότησης OAuth 2.0 (που χρησιμοποιείται για MCP clients) υποστηρίζει μόνο την εκχώρηση `authorization_code` με PKCE (`S256`). Η φόρμα συγκατάθεσης χρησιμοποιεί tokens CSRF HMAC-SHA256 που ισχύουν για 10 λεπτά. Όλες οι τιμές που εμφανίζονται στη σελίδα συγκατάθεσης διαφεύγουν σε HTML.

## Execution Tokens

Τα [Execution tokens](./execution-tokens.md) είναι JWTs με περιορισμένο πεδίο εφαρμογής για την κλήση του endpoint εκτέλεσης ενός workflow από εξωτερικά συστήματα. Σε αντίθεση με τα tokens συνεδρίας χρήστη, αυτά είναι:

- **Περιορισμένα σε ένα workflow** — ένα token απορρίπτεται για οποιοδήποτε άλλο workflow.
- **Ανεξάρτητα ανακλήσιμα** — η ανάκληση ενός token δεν έχει καμία επίδραση στη συνεδρία του χρήστη που το εξέδωσε.
- **Βραχύβια ή μακρόβια** — επιλέξτε TTL από 60 δευτερόλεπτα έως 10 χρόνια.

Τα tokens υπογράφονται με το ίδιο μυστικό της εφαρμογής (`SECRET_KEY`) και ελέγχονται σε κάθε αίτημα: υπογραφή, λήξη, αντιστοίχιση του claim `wid` και κατάσταση ανάκλησης. Ανατρέξτε στα [Execution Tokens](./execution-tokens.md) για τη διαμόρφωση και την αναφορά API.

## Ασφάλεια Περιεχομένου

Χρησιμοποιήστε τα [Guardrails](./guardrails.md) σε κόμβους LLM και Agent για να αποκλείσετε μη ασφαλή ή παραβατικά μηνύματα χρηστών πριν φτάσουν στο μοντέλο. Τα Guardrails υποστηρίζουν εννέα κατηγορίες περιεχομένου (βία, ρητορική μίσους, σεξουαλικό περιεχόμενο κ.λπ.) με διαμορφώσιμα επίπεδα ευαισθησίας.

## Sandbox Εργαλείων Python

Τα εργαλεία Python που ορίζονται από τον χρήστη στον [κόμβο Agent](../nodes/agent-node.md) εκτελούν μη αξιόπιστο κώδικα. Από προεπιλογή, το Heym εκτελεί κάθε εργαλείο μέσα σε ένα ενισχυμένο, προσωρινό Docker container με:

- καμία πρόσβαση δικτύου,
- ένα read-only root filesystem με έναν μικρό κατάλογο εργασίας `tmpfs`,
- έναν μη-root χρήστη με όλες τις δυνατότητες Linux να έχουν αφαιρεθεί και `no-new-privileges`,
- αυστηρά όρια CPU, μνήμης και PID, και
- **κανένα Docker socket** προσαρτημένο, ώστε ένα εργαλείο να μην μπορεί να προσεγγίσει τον Docker daemon του host.

Το backend εκτέλεσης ελέγχεται από τη μεταβλητή περιβάλλοντος `HEYM_PYTHON_TOOL_SANDBOX`:

| Τιμή | Συμπεριφορά |
|-------|----------|
| `auto` (προεπιλογή) | Εκτέλεση στο ενισχυμένο Docker container. Εάν το Docker δεν είναι διαθέσιμο, η εκτέλεση **αποτυγχάνει με ασφάλεια** — δεν εκτελεί σιωπηλά μη αξιόπιστο κώδικα χωρίς απομόνωση OS. |
| `docker` | Ίδιο με το `auto`, αλλά δεν κάνει ποτέ fallback. |
| `subprocess` | Εκτέλεση σε τοπική υποδιεργασία εντός της διεργασίας, φυλασσόμενη από allowlist εισαγωγών. Αυτό **δεν αποτελεί όριο ασφαλείας** και προορίζεται μόνο για αξιόπιστο κώδικα ή τοπική ανάπτυξη. Το `run.sh` το επιλέγει για native dev. |

Ορίστε το `HEYM_PYTHON_TOOL_IMAGE` για να καρφιτσώσετε το image του sandbox· όταν είναι κενό, το Heym ανιχνεύει αυτόματα το τρέχον backend image. Οι περιορισμοί εντός της διεργασίας (μια allowlist εισαγωγών συν φιλτράρισμα χαρακτηριστικών και ενδοσκόπησης) εφαρμόζονται ως άμυνα σε βάθος, αλλά το container είναι το πραγματικό όριο απομόνωσης — διατηρήστε την προεπιλεγμένη λειτουργία `auto` (ή `docker`) για αναπτύξεις πολλών χρηστών και παραγωγής.
## Sandbox Δεξιοτήτων

Οι δεξιότητες Python που είναι συνδεδεμένες σε έναν [node Agent](../nodes/agent-node.md) εκτελούν επίσης μη αξιόπιστο κώδικα — μια δεξιότητα μπορεί να φτάσει αυτούσια μέσα σε ένα κοινόχρηστο workflow ή σε ένα πρότυπο με ορατότητα `everyone` — επομένως οι δεξιότητες εκτελούνται μέσω του **ίδιου** διακόπτη `HEYM_PYTHON_TOOL_SANDBOX` με τα εργαλεία Python και αποτυγχάνουν κλειστά με τον ίδιο τρόπο. Το container δεξιοτήτων είναι θωρακισμένο πανομοιότυπα (non-root, όλες οι δυνατότητες αφαιρεμένες, `no-new-privileges`, read-only root filesystem, όρια CPU/μνήμης/PID και **χωρίς Docker socket**), με δύο σκόπιμες διαφορές επειδή οι δεξιότητες τις χρειάζονται νόμιμα:

- **Η δικτυακή έξοδος επιτρέπεται** (οι δεξιότητες καλούν APIs και εγκαθιστούν τις δικές τους εξαρτήσεις μέσω `uv`), και
- **ένας εγγράψιμος χώρος εργασίας είναι προσαρτημένος** ώστε οι δεξιότητες να μπορούν να παράγουν αρχεία εξόδου και να διαβάζουν αρχεία του Heym Drive.

Ο χώρος εργασίας είναι κοινόχρηστος με το εφήμερο αδελφό container μέσω του ίδιου ονομαστικού Docker volume που χρησιμοποιεί ο Codex runner (`heym-codex-workspaces`, προσαρτημένο στο `/app/data/codex-workspaces`). Μόνο ο δικός του υποκατάλογος αυτής της εκτέλεσης προσαρτάται στο αδελφό container — μέσω ενός `volume-subpath` ανά εκτέλεση — ώστε μια δεξιότητα να μην βλέπει ποτέ τα δεδομένα χώρου εργασίας άλλης εκτέλεσης ή του Codex. Το Docker Compose stack προσαρτά πάντα αυτό το volume· το single-container `docker run` πρέπει να περιλαμβάνει `-v heym-codex-workspaces:/app/data/codex-workspaces` για τις δεξιότητες Python καθώς και για τον Codex. Εάν το volume λείπει σε λειτουργία `auto`/`docker`, η εκτέλεση δεξιοτήτων **αποτυγχάνει κλειστά** αντί να εκτελεστεί στο backend. Επειδή οι προσαρτήσεις υποδιαδρομής ανά εκτέλεση απαιτούν **Docker Engine 25.0 ή νεότερο**, οι παλαιότερες μηχανές θα πρέπει είτε να αναβαθμιστούν είτε να εκτελούν αξιόπιστες δεξιότητες με `HEYM_PYTHON_TOOL_SANDBOX=subprocess`.

Μόνο μη απόρρητες, φορητές μεταβλητές περιβάλλοντος (ρυθμίσεις proxy και CA-bundle, locale) προωθούνται στο container· τα URLs βάσης δεδομένων, τα `SECRET_KEY`/`ENCRYPTION_KEY`, τα API keys παρόχων και τα OAuth secrets αποκλείονται από μια allowlist. Οι διαδρομές αρχείων δεξιοτήτων επικυρώνονται ώστε να παραμένουν εντός του χώρου εργασίας, και τα symlinks που έχουν τοποθετηθεί στον κατάλογο εξόδου (συμπεριλαμβανομένου του sentinel `_hitl_request.json`) δεν ακολουθούνται ποτέ. Παρακάμψτε τις προεπιλογές με τα `HEYM_SKILL_IMAGE`, `HEYM_SKILL_NETWORK`, `HEYM_SKILL_MEMORY`, `HEYM_SKILL_CPUS`, `HEYM_SKILL_PIDS` και `HEYM_SKILL_USER` εάν χρειάζεται.

Όπως με τα εργαλεία, η λειτουργία `subprocess` εκτελεί τη δεξιότητα στη διεργασία του backend και **δεν αποτελεί όριο ασφαλείας** — χρησιμοποιήστε την μόνο για αξιόπιστη χρήση από έναν μόνο χρήστη ή για τοπική ανάπτυξη (το `run.sh` την επιλέγει για native dev).

## Sandbox του node Code

Ο [node Code](../nodes/code-node.md) εκτελεί αυθαίρετο κώδικα Python του χρήστη μαζί με αυθαίρετες εξαρτήσεις τρίτων, επομένως είναι το αυστηρότερο από τα τρία sandboxes και το μόνο με **κανένα περιθώριο διαφυγής**: δεν διαβάζει καμία μεταβλητή λειτουργίας sandbox, δεν έχει λειτουργία `subprocess` και αποτυγχάνει κλειστά όταν δεν είναι προσβάσιμος κανένας Docker daemon. Δεν καταφεύγει ποτέ στην εκτέλεση κώδικα χρήστη στη διεργασία του backend.

Η εκτέλεση γίνεται με ένα ή δύο εφήμερα containers, και τα δύο θωρακισμένα όπως τα sandboxes εργαλείων και δεξιοτήτων (non-root, όλες οι δυνατότητες αφαιρεμένες, `no-new-privileges`, read-only root filesystem, όρια CPU/μνήμης/PID και **χωρίς Docker socket**):

- Με κενό `requirements.txt`, **ένα μόνο container με `--network none`** εκτελεί τον κώδικα. Ο runner φτάνει στο stdin payload του container, επομένως δεν προσαρτάται απολύτως τίποτα.
- Με εξαρτήσεις, ένα πρώτο container τις εγκαθιστά με δικτυακή πρόσβαση σε έναν κατάλογο `.deps` ανά εκτέλεση, και ένα δεύτερο container προσαρτά αυτό το υποδέντρο **read-only** και εκτελεί τον κώδικα. Το container εκτέλεσης δεν έχει δίκτυο εκτός εάν ενεργοποιηθεί η επιλογή `codeAllowNetwork` του node.

Οι εξαρτήσεις εγκαθίστανται με `uv`, επαναλαμβάνονται με `pip` και δεν αποθηκεύονται ποτέ στην cache μεταξύ εκτελέσεων. Όταν το backend εκτελείται σε container, ο κατάλογος ανά εκτέλεση βρίσκεται στο ίδιο volume `heym-codex-workspaces` που χρησιμοποιεί το sandbox δεξιοτήτων, προσαρτημένο μέσω ενός `volume-subpath` ανά εκτέλεση ώστε μια εκτέλεση να μην βλέπει ποτέ τα αρχεία μιας άλλης· αυτή η μορφή απαιτεί **Docker Engine 25.0 ή νεότερο**. Ένα native backend (`./run.sh`) δεν έχει τέτοιο volume και δεν το χρειάζεται — ο κατάλογός του ανά εκτέλεση είναι μια τοπική προσωρινή διαδρομή που προσαρτάται απευθείας στο αδελφό container. Σε κάθε περίπτωση ο κατάλογος διαγράφεται μετά από κάθε εκτέλεση ανεξάρτητα από το αποτέλεσμα.

Μόνο μη απόρρητες, φορητές μεταβλητές περιβάλλοντος προωθούνται στα containers — ρυθμίσεις proxy, CA bundles και locale, τα οποία χρειάζεται η εγκατάσταση εξαρτήσεων για να φτάσει στο PyPI πίσω από εταιρικό proxy. Τα URLs βάσης δεδομένων, τα `SECRET_KEY`/`ENCRYPTION_KEY`, τα API keys παρόχων και τα OAuth secrets αποκλείονται από μια allowlist, ώστε ένα νέο backend secret να απορρίπτεται εξ ορισμού αντί να διαρρέει μέχρι κάποιος να ενημερώσει μια denylist. Το `HOME` του backend δεν υπερισχύει ποτέ της δικής του εγγράψιμης διαδρομής του sandbox.

Το κουμπί **Format** χρησιμοποιεί το ίδιο sandbox. Το Ruff αναλύει και ξαναγράφει τον πηγαίο κώδικα αντί να τον εκτελεί, αλλά η εκτέλεσή του στον host του backend θα έδινε σε ένα μη αξιόπιστο αρχείο μια διεργασία που κληρονομεί ολόκληρο το περιβάλλον του backend, επομένως αποκτά το δικό του εφήμερο container `--network none` με τα ίδια όρια και το ίδιο περιβάλλον allowlist. Αποτυγχάνει κλειστά χωρίς Docker αντί να μορφοποιεί στον host.

Τα όρια του sandbox είναι σταθερές αντί για μεταβλητές περιβάλλοντος — 512 MB μνήμης, ένας CPU, 256 διεργασίες, χρονικό όριο εγκατάστασης 120 δευτερολέπτων και χρονικό όριο εκτέλεσης 60 δευτερολέπτων. Η εικόνα προκύπτει από την υπάρχουσα αλυσίδα `HEYM_PYTHON_TOOL_IMAGE` / `HEYM_CODEX_DOCKER_IMAGE`· ο node δεν εισάγει δική του διαμόρφωση.
