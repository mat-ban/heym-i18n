# 負荷分散

2 台目の Heym インスタンスを同じ PostgreSQL データベースに向けると、そのインスタンスは worker として参加します。バックグラウンドの Workflow 実行は、設定した割合に従ってインスタンス間で共有されるため、UI と API を提供しているマシンが、すべての Workflow を実行する唯一のマシンではなくなります。

インスタンス同士が通信することはありません。作業を運ぶのは Postgres であるため、worker には開いたポートも、証明書も、main インスタンスへの戻り経路も必要ありません。必要なのはデータベースへのアクセスのみです。

## ロール

1 つのインスタンスが環境変数によって **main** に固定されます。main は UI、API、MCP、チャットポータルを提供し、ファイルストレージとインストール済みプラグインを所有します。それ以外のすべてのインスタンスは **worker** です。worker はデータベースにのみ到達し、バックグラウンド実行を実行します。

```
HEYM_CLUSTER_ENABLED=true
HEYM_INSTANCE_ROLE=main       # or: worker
HEYM_INSTANCE_NAME=EU Main    # display label, editable later from Settings
HEYM_INSTANCE_ID=eu-main      # optional; derived from the name when empty
```

main ロールは leader election とは別のものです。Heym はすでにクラスタ全体で 1 つの leader を選出し、cron、アラート評価、クラッシュリカバリを担わせています。main がダウンした場合、リーダーシップは数秒以内に worker へ移動し、スケジュールされた実行はそのまま発火し続けます。main ロールは移動しません。ファイルストレージをそれとともに移動させることはできないためです。

## main インスタンスから移せるもの

配置は、実行が始まる前に Workflow のノードから決定されます。実行内のいずれかのノード（呼び出しているサブ Workflow 内のノードを含む）が、1 台のマシンにしか存在しないものに触れる場合、その実行は main に留まります。

| ノード | main に留まる理由 |
|---|---|
| Codex、OpenCode Go | コーディングエージェントのワークスペースがローカルディスクに留まるため、フォローアップをその中で再開できます |
| スキルをアタッチした Agent | スキルのコードが Heym Drive を読み書きします |
| Drive、Converter、Google Drive | 生成されたファイルを読み書きします |
| File Upload trigger | アップロードが main のディスクに着地します |
| Send Email | 企業の SMTP リレーは通常、1 つの送信元アドレスを allowlist に登録します |
| プラグインノード | プラグインは 1 つのインスタンスのディスクにインストールされます |

**それ以外はすべて分散されます** — Code ノード、Playwright、Agent Python ツールを含みます。すべてのインスタンスはそれぞれ自身の Docker ソケットを備えた同一のイメージを実行するため、サンドボックスは実行を main に留めておく理由にはならず、これらは製品内で最も CPU を消費するノードです。

サブ Workflow が式によって選択される Workflow は、事前に検査できないため main に留まります。

## 割合の選び方

重みは **Settings → Instances** で設定する整数です。これらは 100 に対する割合ではなく、**現在作業を引き受けられるインスタンス間での取り分**です。スケジューラはそのプール自身の合計で割ります。

この違いは、1 つのインスタンスが脱落した途端に現れます。`Main 41, Worker A 26, Worker B 33` の場合、Worker B をオフにするとプールは 67 になり、Main は実際には 41/67 = **61%**、Worker A は 26/67 = **39%** を受け取ります。パネルが表の下に実効的な配分を表示するのはまさにこの理由であり、数値が 100 にならないことを理由に保存がブロックされることはありません。拒否されるのは、有効なインスタンスが 1 つも重みを持たない配分だけです。

さらに、間違えやすい点が 2 つあります。

**割合はマシンパワーの取り分ではありません。** それはキューを通過する実行のみを対象としています。UI と API の提供、エディタおよびポータルの実行のストリーミング、ファイルアップロードの処理はすべて main の仕事であり、そのいずれもカウントされません。main はその数値が示す以上のことをしています。

**main の割合は上限であり、下限ではありません。** main でしか実行できない実行はそのクォータに対して課金されるため、そのクォータを使い切ると、残りの分散可能な実行は worker に流れます。main の数値を低く設定しても安全です — そこで実行しなければならない作業は依然として実行されます。高く設定すると worker を飢えさせます。

したがって、強力な main とより小さな worker がある場合、マシンの生の比率よりも 60/40 に近い値から始め、Traces タブで実際の実行時間を比較して調整してください。

重みは、現在ライブかつ有効なインスタンス間で再正規化されます。`main=70, A=15, B=15` の場合、A がオフラインになると配分は main と B の間で 70/85 と 15/85 になり、A が戻ると 70/15/15 に戻ります。

**復帰したインスタンスは、逃した実行を請求されません。** Offline、Disabled、またはバージョン不一致の状態で費やした時間はそのインスタンスに対してカウントされないため、一晩利用できなかった worker はプールの現在の位置で復帰し、最初の実行から配分は再び 70/30 と表示されます — 追いつくまで毎回の実行を吸収することはありません。ずっと利用可能だった worker は依然として追いつきます。これが main の割合を上限たらしめている理由です。

### 新しいインスタンスはゼロで参加します

一度も重みを与えられたことのないインスタンスは 0 から始まり、Live、Enabled でありながら何も受け取らない状態になります。**新しいインスタンスに自動で取り分を付与する** — インスタンス表の下でデフォルトでオン — がこれを修正します。leader の次のパスで、新規参入者にはプールの均等な取り分が与えられ、既存の重みは互いの比率を保ったまま縮小されるため、意図的な 70/30 はその後もおおよそ 70/30 と表示されます。合計は正確に 100 のままです。

これは **インスタンスごとに 1 回**実行されます。自動パスとご自身の編集の両方がそのインスタンスを設定済みとしてマークするため、ご自身で設定したインスタンスが背後で変更されることはありません — 意図的に 0 に設定したものも含みます。すべての新しいマシンにあなたの設定を待たせたい場合は、この設定をオフにしてください。

参加するのは、有効かつライブで互換性のあるインスタンスのみです。何も実行できないマシンに取り分を渡すと、その取り分が宙に浮いてしまいます。
### パーセンテージでは対応できない場合

設定パネルには、過去24時間の実行のうち main 上でのみ実行できたものが何件あったかが表示されます。この数値が高い場合 — Codex を多用するワークロードや Drive を多用するワークロードなど — は、重みがどうであれ worker は待機したままとなり、解決策は worker を増やすことではなく、より大きな main インスタンスを用意することです。

## クラスタ向けの PostgreSQL サイジング

コネクションはユーザー数だけでなく、インスタンス数に応じて増加します。各インスタンスは複数の uvicorn プロセスを実行し、各プロセスはコネクションプールに加えて4本の `LISTEN` コネクション（キャンセル、キューの起床通知、実行結果、チャットストリーム）を保持します。開いているチャットストリームは1本のチャットコネクションを共有するため、データベースコネクションは増加しません。デフォルトの `max_connections = 100` では3インスタンスのクラスタで枯渇し、Heym は自身のデータベースに到達できなくなります。

おおよそ `instances x processes x (async pool + sync pool + 4)` を見積もり、それを上回る `max_connections` を設定してください。

上限を引き上げるだけでなく、プールを縮小してください。単一デプロイではプロセスあたり async 10+20、sync 5+10 のコネクションがデフォルトであり、1台のマシンには十分すぎるほどですが、クラスタには過剰です：

| 変数 | 単一インスタンス | クラスタ |
|---|---|---|
| `HEYM_DB_POOL_SIZE` | 10 | 3 |
| `HEYM_DB_MAX_OVERFLOW` | 20 | 5 |
| `HEYM_DB_SYNC_POOL_SIZE` | 5 | 2 |
| `HEYM_DB_SYNC_MAX_OVERFLOW` | 10 | 3 |

サンプルの compose ファイルではこれらと `max_connections = 300` を設定しています。これにより、2インスタンスのクラスタは768コネクションの上限から192に削減され、3インスタンスでも300未満に収まります。

## クラスタが代わりに強制できない要件

**すべてのインスタンスが同じ `SECRET_KEY` と `ENCRYPTION_KEY` を使用する必要があります。** 異なる `ENCRYPTION_KEY` を持つ worker は credential を復号できず、credential を使用するすべての実行が、原因を特定できないエラーで失敗します。Heym は各ハートビートで両方のキーのダイジェストを、アプリのバージョンおよびデータベースのリビジョンとともに比較し、不一致のインスタンスを **Mismatch** としてマークし、一切の作業を割り当てません。修正するまで、負荷は main にフォールバックします。

これはアップグレードの順序も規定します。main を先にアップグレードすると、すべての worker が互換性なしとマークされます。作業は main に戻り、各 worker はアップグレードされ次第、順次復帰します。より低速ですが可視的で、かつロールバック可能です。

**ingress は main インスタンスのみを指すようにしてください。** ユーザートラフィックをインスタンス間でラウンドロビンすると、ファイルアップロードが一方のマシンに送られ、そのダウンロードが別のマシンに送られることになります。コード上でこれを防ぐ仕組みはありません。worker は同じイメージを実行しており、受け取ったリクエストにはすべて応答するためです。

**すべてのインスタンスに `FRONTEND_URL` が必要で、同じ公開アドレスを設定してください。** 人手によるレビューのために一時停止する実行は、main 上ではなくそれを実行したインスタンス上でレビューリンクを生成します。Codex のフォローアップリンクや生成ファイルのダウンロード URL についても同様です。これが設定されていない worker は、自身のローカルアドレスに対してこれらのリンクを生成し、受け取った誰もそれを開けなくなります。

**worker インスタンスは送信元 IP が異なります。** 送信元アドレスを allowlist する API は、新しい IP を認識します。Send Email が main 上で実行されるのはまさにこの理由によります。HTTP ノードについては、クラスタに単一の NAT 送信アドレスを付与するか、すべてのインスタンスを allowlist に追加してください。

## 別マシンへの worker の追加

リポジトリルートの `docker-compose.worker.yml` は、独自のホスト上で worker を実行します。データベースも UI も持ちません。main インスタンスの PostgreSQL に接続し、バックグラウンド実行の分担分を処理します。

その隣に `.env` を用意し — イメージタグ、データベースのホストと認証情報、両方のキー、インスタンス id を記入して — 起動してください。Compose はすべての必須値が設定されるまで起動を拒否します。後から判読しにくい形で失敗するプレースホルダで起動することはありません。

イメージタグは main が実行しているバージョンでなければならず、両方のキーは正確にコピーする必要があります。いずれかが異なると、worker は Mismatch として表示され、一切の作業を受け取りません。

## Instances テーブルの読み方

| 列 | 意味 |
|---|---|
| Name | 編集可能なラベル。このインスタンスが実行するすべての実行に付与されます |
| Role | 環境変数による `main` または `worker` |
| Status | ハートビートが新しければ **Live**、30秒間の沈黙で **Offline**、バージョン、データベースのリビジョン、またはキーが main と異なる場合は **Mismatch** |
| ms | そのインスタンスからデータベースへのラウンドトリップ。インスタンス自身が計測します |
| On | worker を停止せずにローテーションから外します — 実行中の実行は完了し、新しい実行は割り当てられません。main インスタンスではロックオンされます。トグルの状態にかかわらず、ファイル、プラグイン、コーディングエージェントの作業はそこで実行されます |
| Weight | 分散可能な実行の分担分 |

## クラスタ内の同時実行制限

ワークフローの[同時実行制限](./webhooks.md#concurrency-limit-and-queued-runs)は PostgreSQL でカウントされるため、すべてのインスタンスおよびプロセス全体で適用されます。2つのインスタンスが制限を超えて1つのワークフローを実行することはありません。スロットを待機していた実行は開始時に他の実行と同じルールに従って配置されるため、main にとどまる必要がある実行は main で実行されます。これらの実行を処理するキューワーカーは、単一インスタンスを含むすべてのインストールで起動するようになり、自身のインスタンスがキューに入れた実行のみを取得します。これは、単一インスタンスであっても各プロセスでキュー起床用の `LISTEN` 接続を保持することを意味するため、クラスタインスタンスと同様に接続数を考慮してください。

## 実行履歴

実行履歴のすべての実行は、それを実行したインスタンスを記録しており、両方の履歴ダイアログで1つのインスタンスに絞り込めます。フィルタはインスタンスの id で照合しつつ名前を表示するため、インスタンスの名前を変更しても、過去の実行の表示内容は書き換わりません。

単一インスタンスのインストールではこれらは一切表示されません。フィールドは空で、ラベルも表示されず、フィルタも提供されません。
## 障害時の動作

**Worker が実行中に停止した場合**、そのハートビートは stale となり、leader の既存のリカバリースイープが稼働中のインスタンス上で実行を再実行します。Worker がクレームしていた queue の行は別途退役処理されます。すなわち、その行に対するアクティブな実行が存在しなくなり、2分間の猶予が経過すると、leader がその行を失敗とし、結果を待っていた相手を起こします。経過時間だけがトリガーになることは決してないため、正当に長時間実行されているものはそのまま放置されます。また、その行は再キューイングではなく失敗とされます。これは、リカバリーがすでに再実行を担っており、再キューイングすると同じ Workflow が二重に実行されてしまうためです。

**main がダウンした場合**、cron は Worker から発火し続け、分散可能な実行はそのまま実行され続けます。main を必要とする実行はキューに入って待機し、main が復帰すると処理されますが、それは misfire 猶予ウィンドウ（`HEYM_CRON_MISFIRE_GRACE_SECONDS`、デフォルトで600秒）内に限られます。それより古いものは、何時間分ものバックログを一度にリプレイするのではなく、理由を記録したうえでスキップとしてクローズされます。

main がダウンしている間は、ingress がそこを経由するため、UI、API、MCP、およびエディターは利用できません。
