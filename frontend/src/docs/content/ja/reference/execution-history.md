# 実行履歴

実行履歴はWorkflowの実行を記録します。入力、出力、ノードの結果、ステータス、Triggerのソースなどが含まれます。これを使用して、稼働中の本番実行の監視、過去の実行の確認、失敗のデバッグ、または**Bring to Canvas**による同じ入力での再実行を行うことができます。

## 概要

各実行では以下が保存されます：

| フィールド | 説明 |
|-------|-------------|
| **Inputs** | リクエストボディまたは実行入力（例：Inputノードの`text`） |
| **Outputs** | Workflowレベルの出力 |
| **Node results** | ノードごとの出力、ステータス、実行時間 |
| **Status** | `success`、`error`、`pending`、`skipped`、または`failed`（[Crash Recovery](#crash-recovery)を参照） |
| **trigger_source** | 実行がどのようにTriggerされたか（[Triggers](./triggers.md)を参照） |

## 履歴へのアクセス

| 場所 | スコープ |
|----------|-------|
| **Editor**ツールバー | 現在のWorkflowのみ |
| **Docs**ビューヘッダー | 現在のWorkflowのみ |
| **Dashboard**ヘッダー（Chatタブ） | すべてのWorkflow + チャット/アシスタント実行 |
| **Evals**ビューヘッダー | すべてのWorkflow + チャット/アシスタント実行 |

**History**ボタン（時計アイコン）をクリックしてダイアログを開きます。

## Workflow単位 vs すべての履歴

- **Workflow単位**（Editor、Docs）：開いているWorkflowの実行を表示します。**Clear history**を使用すると、そのWorkflowの実行のみが削除されます。
- **すべての履歴**（Dashboard、Evals）：すべてのWorkflowおよびチャット/アシスタントセッションにわたる実行を表示します。対象範囲はWorkflowへのアクセス権と一致します：自分が所有するWorkflow、自分に直接共有されたWorkflow、自分が所属するチームに共有されたWorkflowです。**Clear all history**を使用すると、自分が所有するすべてのレコードが削除されます。共有Workflowの履歴は保持されます。

## Bring to Canvas

**Bring to Canvas**は、選択した実行の入力とノード出力を現在のWorkflowに読み込みます。

### 読み込まれる内容

- **Inputs** → 実行入力パネル（例：Inputノードの`text`、またはカスタムフィールド）
- **Node results** → 実行結果パネルにノードごとの過去の出力が表示されます
- **Execution result** → その実行のステータス、出力、タイミング

### コンテキストごとの動作

- **Editor内**（Workflow単位の履歴）：開いているWorkflowに即座に適用され、ダイアログが閉じます。
- **すべての履歴から**（Dashboard/Evals）：Workflowエディタに移動し、エディタの読み込み時にデータを適用します。Workflowの実行にのみ使用可能で、チャット/アシスタントの実行には使用できません。

### 実行ディープリンク

`/workflows/{workflowId}/{executionId}`でWorkflowを開くと、その実行が自動的にキャンバスに読み込まれます — 実行を選択して**Bring to Canvas**を選ぶのと同じです。これにより、特定の過去の実行をURLとして共有できます。実行が見つからない場合（IDが誤っているか削除されている場合）、エディタは通常のWorkflowの読み込みにフォールバックします。

### ユースケース

- 同じ入力でWorkflowを再実行する
- 入力とノード出力を検査して失敗した実行をデバッグする
- 実行間で出力を比較する

## AIに質問

両方の履歴ダイアログのタイトルの横に **AIに質問** ボタン（輝きアイコン）があります。ワークフローと選択した実行が削除可能なチップとして添付された状態で、新しい会話で [Chat タブ](../tabs/chat-tab.md#asking-about-a-run) を開きます。実行が遅かった理由や失敗した原因を尋ねたり、Chat にワークフローを修正させたりできます。Chat はノードごとのトレースやエラーを含め、その正確な実行を読み取ります。

All History ダイアログでは、ワークフローの実行が選択されている場合にのみ **AIに質問** が表示されます。チャットやアシスタントの実行では表示されません。

## 実行タイムライン

実行の詳細で、**すべて展開** の横にある **タイムライン** ボタン（ストップウォッチアイコン）をクリックすると、**ステップ** リストがスパンタイムラインに切り替わります。タイムラインが表示されている間、同じボタンには **ログ** と表示されます。クリックするとリストに戻ります。All History では、このボタンはワークフローの実行にのみ表示されます。タイムラインは各ノードが開始された時刻にバーを描画するため、どのノードにどのくらいの時間がかかり、どのノードが並行して実行されたかを確認できます。バーにカーソルを合わせると所要時間が表示され、クリックするとエディターの [実行タイムライン](#execution-timeline-details) と同じ詳細インスペクターが開きます。選択したビューはダイアログが開いている間維持されます。

ノードの開始時刻が保存される前に記録された実行は、所要時間順に順次配置されます。

## Execution Highlights

ライブ実行後、または**Bring to Canvas**の後に、**キャンバスの右上**に閉じることができる**Execution Highlights**ポップアップが表示されます。これは*各ノードが何を生成したか*を実行順に上から下へ素早く確認する方法です。**✕**で閉じることができ、次回の実行時に再度開きます。

### 表示される内容

| レコード | ソース | 自動？ |
|--------|--------|-------|
| **Input** | その実行の入力パラメータ（input/triggerノード） | はい |
| **Output** | 出力ノードの結果 — 存在しない場合は最後のノードのメッセージ | はい |
| **Agent / LLM** | 各AgentまたはLLMノードの出力 | はい |
| **Output** | **Highlight Node Output**が有効なその他のノード | オプトイン |

すでに自動ハイライトされているノード（input / output / last / agent / llm）は、トグルを有効にしても二重に表示されることはありません。

### 各レコード

- `Node — message…`を最初の**250文字**まで表示します。行をクリックすると展開され、**完全なメッセージがMarkdownとしてレンダリング**され、**Copy**ボタンが表示されます。
- 複数回実行されたノード（例：ループ内）は`Node (N)`と`‹ i / N ›`セレクターを表示します — 表示する実行を選択できます。各ノードのセレクターは独立しています。

### Highlight Node Output

**AgentとLLMを除く**すべてのノードには、プロパティパネルに**Highlight Node Output**チェックボックスがあります（デフォルトはオフ）。これを有効にすると、そのノードの出力がポップアップに追加されます。ハイライトされたノードにはキャンバス上で小さな✦バッジが表示されます。[workflow DSL](./expression-dsl.md)では、これはノードデータフィールド`"highlight": true`です（デフォルトは`false`）。

### ダッシュボード上

Workflowを実行したDashboardウィジェットカードは、カードヘッダーに✦**Execution highlights**ボタンを表示します。クリックするとそのウィジェットの実行に対して同じポップアップが開き、ウィジェットが描画した出力が主要なレコードとして表示されます。

## 実行の実行中

両方の履歴ダイアログでは、過去の実行の前に、**現在実行中の実行**がリストの先頭に表示されます。

- 開始時刻とともに、回転するインジケーターと **Running** ラベルが表示されます
- **Open live** をクリックすると、実行を再起動せずに、その正確な実行にエディターを接続できます
- キャンバスはまずすでに完了したノードを復元し、その後 SSE 経由で
  `node_start`、`node_complete`、および最終的な実行イベントを受信します
- 現在のノードはキャンバス上でパルス表示され、下流のノードは保留中のアニメーションを維持し、
  Debug パネルは結果が到着するたびに追加します—エディターから開始した実行とまったく同じです
- **Cancel** をクリックすると、実行を即座に停止します
- 任意のダイアログ（Editor または Dashboard）からキャンセルすると、その Workflow に対して開いているすべてのキャンバスタブのアクティブな SSE ストリームも閉じられるため、エディターの状態がクリーンにリセットされます
- キャンセル後、実行中のエントリは次回の更新で消えます。手動でリストを更新するには **Refresh** を押してください
- すでに終了した実行をキャンセルした場合、リクエストは no-op になります

[同時実行スロット](./webhooks.md#concurrency-limit-and-queued-runs)を待機している実行は、同じセクションに **Queued 2/5** ラベル、順番、およびキューのサイズとともに一覧表示されます。まだ何も実行されていないため **Open live** ボタンはありません。**Cancel** をクリックすると、待機中の実行がキューから削除され、`cancelled` として記録されます。Workflow の最大待機時間よりも長く待機した実行は `expired` として記録され、キューが満杯のために拒否された実行は `queue_full` として記録されます。どちらも実行リストに専用のバッジが表示されます。

ライブ URL は `/workflows/{workflowId}/{executionId}` です。オブザーバーは読み取り専用です。エディターを離れるとそのブラウザタブが切断されるだけで、Workflow が停止することはありません。アクティブなスナップショットは PostgreSQL を通じて共有されるため、Trigger とエディターのリクエストが異なるバックエンドワーカーに到達した場合でも、実行を開くことができます。

## クラッシュリカバリ

Workflow の実行中にサーバーが再起動した場合（デプロイ、コンテナの再起動、またはクラッシュ）、その実行のワーカーは実行の途中で停止します。Heym はこれらの中断された実行を **Running** のまま放置せず、自動的にリカバリします。

- 次回の起動時に、選出されたリーダープロセスが孤立した実行を検出します — グレースフルな再起動の場合は即座に、ハードクラッシュの場合は約60秒以内に（ハートビートが明確に停止した時点で）。
- リカバリされた実行は、**同じ入力で最初から再実行**されます（停止した場所から再開するのではなく）、現在の Workflow 定義を使用します。完了時には通常の終端エントリ（例: `success`）が記録されるため、履歴にはその実行が完了したものとして表示されます。
- 実行は **1回** 再試行されます。リカバリの試行も中断された場合 — またはその間に Workflow が削除された場合 — エントリは `failed` として記録されます。
- これは単一コンテナでもマルチワーカーのデプロイでも同様に機能します。リカバリを実行するのはリーダーのみであるため、実行が異なるワーカーによって二重にリカバリされることはありません。

### Auto-recover トグル

エディターの **Execution Log**（実行）パネルには **Auto-recover** チェックボックスがあり、Workflow ごとに **デフォルトでオン** になっています。

- **オン**: この Workflow の中断された実行は、上記のように再実行されます。
- **オフ**: 中断された実行は再実行されず、ステータス `skipped` で記録されます。

> サブ Workflow の実行は独立してリカバリされません — リカバリされた親実行によって再駆動されます。独自の再配信を持つ Trigger（RabbitMQ、scheduled/cron、IMAP）も再起動時に再配信する場合があるため、リカバリされた実行がまれに二重に実行されることがあります。

## 保留中のヒューマンレビュー

[Human-in-the-Loop](./human-in-the-loop.md) の承認のために一時停止した実行は、ステータス `pending` で即座に履歴に書き込まれます。

- 保留中の Agent ノードは、`reviewUrl`、`draftText`、`expiresAt` を含むレビュー Payload を保存します
- Agent の `review` ハンドルに接続された任意のノードも、人間が応答する前に実行でき、それらのノード結果は同じ保留中の履歴エントリに保存されます
- 履歴ダイアログにはレビューリンクが表示されるため、オーナーはコピーまたは開くことができます
- 履歴ダイアログとエディターの Debug パネルは、実行が再開された後に最終的な人間の決定を表示します
- レビュアーがドラフトを承認、編集、または拒否すると、同じ履歴エントリが最終的な実行結果で更新されます
- 同じ実行が HITL のために複数回一時停止した場合、履歴エントリは同じままですが、各チェックポイントには独自のワンタイムレビューリンクが付与されます

これは、ポータル実行や、続行するまでに数時間または数日待機する可能性のある長時間実行の Workflow に特に役立ちます。

## コピー

Inputs または Outputs の隣にある **Copy** を使用して、JSON をクリップボードにコピーします。

## 履歴のクリア

- **Workflow ごと**: エディターの履歴ダイアログで **Clear history** をクリックすると、現在の Workflow の実行が削除されます。
- **すべての履歴**: Dashboard/Evals の履歴ダイアログで **Clear all history** をクリックすると、所有するすべての実行レコードが削除されます。共有 Workflow からの実行は保持されます。この操作は元に戻せません。

## 実行タイムラインの詳細

エディターの **Execution Log** が開いているとき、タイマーボタンをクリックすると実行タイムラインが表示されます。スパンを選択すると、行領域を占有するインライン詳細インスペクターが開きます。選択したステップのステータス、所要時間、試行回数、リトライ情報、エラー、トレース ID、およびコンパクトな出力プレビューが表示されます。オブジェクトと配列の出力は、Debug パネルの他の部分と同じ `JsonTree` ビューアーを使用します。スカラー値はテキストプレビューを使用します。ステップが画像（Playwright のスクリーンショット、生成された画像、画像ファイル、またはリクエスト本文内の base64 画像で、出力内の任意の場所に見つかったもの）を出力する場合、それらは出力の上にサムネイルとして表示され、JSON には生の base64 の代わりに短いプレースホルダーが表示されます。サムネイルをクリックするとライトボックスで開きます。矢印ボタンまたは ←/→ キーで実行内のすべての画像を順に移動でき、`2 / 5` のようなカウンターが表示されます。トレース ID が利用可能な場合、LLM および Agent スパンには **Open trace** を使用します。

## モバイルでのノード詳細

スマートフォンでは、エディターは自由形式のキャンバスの代わりに全画面のWorkflowツリーを表示します。記録された結果を持つツリーノードをタップすると、その実行内容が全画面の詳細として開きます。このビューには、**Input Data**、**Output Data**、**Errors** の個別タブが用意されています。Outputタブには記録された結果が表示され、**Copy Output** を利用できます。Inputタブには選択したノードの設定が表示され、Errorsタブにはノードが失敗した際に記録されたエラーが表示されます。ツリーに戻るには、**Back to workflow** または閉じるボタンを使用します。

キャンバスとダッシュボードの履歴ダイアログでは、実行コントロールが1行にまとめられ、利用可能なタグおよびインスタンスのフィルターがレスポンシブグリッドに配置されます。これらのフィルターメニューは同じアプリ内セレクターを使用するため、選択時のチェックマークはすべてのオプションラベルと一貫した余白とベースラインで表示されます。
