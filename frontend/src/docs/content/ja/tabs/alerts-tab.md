# Alertsタブ

**Alerts**タブでは、時間枠に対するしきい値条件を定義し、それを超えたときに通知を受け取ることができます。Heymはすでに実行結果、実行時間、LLMの消費額を記録していますが、それらを自発的に知らせることはありません。Alertは、それを知らせるようにHeymに依頼するための仕組みです。

すべてのAlertは、単一のイベントではなく、選択した**時間枠**に対して評価されます。1回の失敗はノイズにすぎません。10分間に12回の失敗があれば、それはインシデントです。

## Alertの種類

| 種類 | 答える問い | 数値の出所 |
|---|---|---|
| **Error threshold** | この時間枠でN回を超えて失敗したか？ | エラーステータスを持つ[実行履歴](../reference/execution-history.md)の行 |
| **Workflow duration** | この時間枠で実行が想定より遅くなったか？ | 実行時間をmax、average、または95パーセンタイルで集計 |
| **Token / USD cost** | この時間枠で消費額が予算を超えたか？ | [LLM traces](./traces-tab.md)とLLMコストテーブル |
| **Execution count** | 想定よりはるかに頻繁に実行されたか？ | 実行履歴の行数 |

### Error threshold

時間枠内の失敗した実行をカウントし、その数がしきい値に達したときに発火します。個々の失敗をフックするのではなく時間枠でカウントするため、単発の一時的なエラーでページ通知が飛ぶことはありません。

### Workflow duration

時間枠内の実行時間を測定します。**max**（最も遅い実行）、**average**、または**p95**を選択できます。p95の値は[Analyticsタブ](./analytics-tab.md)と同じパーセンタイル計算を使用するため、同じ時間枠に対してAlertとレイテンシチャートが食い違うことはありません。

**Minimum runs in the window**は、この指標を誠実に保ちます。ほぼ空の時間枠における最も遅い実行は、その1回の実行にすぎません。たとえば最小値を3に設定すれば、ノイズでAlertが発火するのを防げます。

### Token / USD cost

時間枠内のLLM消費額を、合計トークン数または米ドルで合計します。ドル金額は[Tracesタブ](./traces-tab.md)と[LLM Cost Table](./datatable-tab.md#llm-cost-table-system-table)が使用するのと同じ価格テーブルで解決されるため、コストAlertとコストページは常に一致します。

スコープがすべてのWorkflowの場合、これには[Chatタブ](./chat-tab.md)や[AI Assistant](../reference/ai-assistant.md)など、Workflow外で行われたLLM呼び出しも含まれます。コーディングエージェントの使用（Codex、OpenCode）は含まれません。

価格行がないモデルは、暗黙的にゼロとしてカウントされるのではなく、Alertのコンテキストでunpricedとして報告されます。

### Execution count

時間枠内のあらゆるステータスの実行をカウントします。これはTriggerの異常を捉えるものです。通常は1時間に20回実行されるWorkflowが、突然2,000回実行されるといったケースです。発火レコードにはTriggerソースごとの内訳が含まれます。これは通常、「なぜこれが起きたのか」への答えになるからです。

## スコープ

Alertは、**1つのWorkflow**または**すべてのWorkflow**のいずれかを監視します。

「すべてのWorkflow」とは、Alertの所有者がアクセスできるすべてのWorkflowを意味します。Heymインスタンス上のすべてのWorkflowを意図的に意味するものではありません。Alertは共有できるため、Alertを共有することが、開くことのできないWorkflowの集計数値を誰かに渡すことになってはならないからです。

## ウィザード

Alertの作成は5つのステップを順に進みます。

1. **Type** — 上記4種類から1つを選択します。
2. **Scope** — 1つのWorkflow、またはすべて。
3. **Condition** — 時間枠と、その種類に応じたしきい値フィールド。
4. **Response** — 発火時に実行される内容と、通知を繰り返す頻度。
5. **Review** — 名前を付け、バックテストを確認します。

### バックテスト

Reviewステップは、保存する前に本当に重要な問いに答えます。*過去24時間で、これは何回発火しただろうか？*

発火回数と、しきい値に対して観測された最高値を報告します。もし条件が400回発火したと表示されたなら、ページ通知を受けた後ではなく、保存する前にしきい値を修正できます。ルックバック期間は3日または7日に広げることができます。

## AIドラフト

最初のステップの上部には、希望する内容を平易な言葉で記述するボックスがあります。

> Warn me if the invoice sync fails more than 5 times in 10 minutes

HeymはこれをAlert定義に変換し、埋められるすべてのステップを埋め、AIが埋めたフィールドをマークした状態で先へ進みます。そのため、入力し直すのではなく確認するだけで済みます。完全なリクエストであれば、Reviewまで到達します。

**部分的なリクエストでも先へ進めます。** たとえば「warn me if it fails 5 times」とだけ指定した場合、カウントが埋められたError threshold Alert、その他はデフォルト値、そしてウィザードはまだあなたの判断が必要な最初のステップで開きます。この場合はWorkflowが指定されていないためScopeです。上部の注記に、何を決める必要が残っているかが表示されます。NextやCreateがブロックされることは決してありません。

同じことは、モデルがアクセスできないWorkflowを指定した場合や、フィールドが欠けた条件を返した場合にも当てはまります。意味の通る部分は保持され、残りはそのAlert種類のデフォルトにフォールバックし、そこから調整します。ここで検証が回避されることはありません。ウィザード自身のルールとAPIの両方が、保存時にAlertを再チェックします。

## 繰り返し動作

アラートが一度発火すると、Trigger状態に入ります。その後に何が起こるかは、ステップ4で選択できます。

- **復旧するまで1回だけ通知する**（デフォルト） — 一度発火した後、条件が成立し続けている間は通知を停止します。メトリクスがしきい値を下回ると、アラートはOKに戻り、再び発火できる状態になります。復旧は状態変化であり、イベントではありません。発火レコードは作成されず、通知Workflowも実行されません。
- **一定間隔で通知を続ける** — 条件が成立し続けている限り、N分ごとに再発火します。

デフォルトがこの動作になっている理由は、壊れたWorkflowを60秒ごとにチェックすると1時間に60回の発火が発生し、それによってアラートがミュートされてしまうためです。

## 発火時にWorkflowを実行する

ステップ4では、「発火したときに何をすべきか」に対して3つの選択肢があります。

- **新しいWorkflowを作成して割り当てる**（デフォルト） — アラートを保存すると、*「&lt;アラート名&gt; notification」*という名前のWorkflowが作成され、リンクされます。このWorkflowには、以下に示すPayloadとまったく同じフィールドを持つ入力ノードが付属しているため、`$alert.body.observed_value`などをすぐに解決でき、メッセージを配信するノードを接続するだけで済みます。アラートカードの**Go to workflow**から開けます。これがデフォルトである理由は、何も起こらないまま発火するアラートは見逃されやすいためです。
- **既存のWorkflowを選択する** — すでに構築済みのWorkflowを実行します。
- **何もしない** — 発火はタブに記録されますが、何も実行されません。

アラートのPayloadは、そのWorkflowの入力bodyとして渡されます。

```json
{
  "alert_id": "...",
  "alert_name": "Invoice sync failures",
  "alert_type": "error_threshold",
  "condition": "5+ errors in 10m",
  "scope": "workflow",
  "workflows": [{ "id": "...", "name": "Invoice Sync", "value": 12 }],
  "observed_value": 12,
  "threshold_value": 5,
  "window_start": "2026-08-09T11:50:00+00:00",
  "window_end": "2026-08-09T12:00:00+00:00",
  "window_minutes": 10,
  "context": { "error_count": 12 }
}
```

### どのWorkflowがその数値を生み出したか

Workflowが登場するのは`workflows`だけです。この配列には、その計測値に寄与したすべてのWorkflowが、それぞれの`value`とともにリストされます。`value`はアラートタイプに応じて、そのWorkflowのエラー数、実行回数、最も遅い実行時間（ミリ秒）、または支出額を表します。リストは`value`の降順でソートされるため、`workflows[0]`が最も問題の大きいWorkflowです。

これは**常に配列**です。単一Workflowスコープでは要素が1つ、 「すべてのWorkflow」では複数、何も帰属できない場合はnullではなく空になります。通知Workflowは形状チェックなしでこれを反復処理できます。

単数形の`workflow_id`は意図的に存在しません。これはメトリクスではなくアラートのスコープを表していたため、システムスコープでは`null`になっていました。しかし、まさにそのケースこそ「どのWorkflowか？」が最も重要になります。`observed_value`はしきい値と比較された集計値のままであり、Workflowごとの`value`フィールドがその由来を説明します。

これが、アラートをSlack、メール、Telegram、その他の場所に届ける仕組みです。専用の通知システムではなく、すでにお持ちの[ノード](../reference/node-types.md)を使用します。

アラートは、監視対象のWorkflowに通知することはできません。それはループになるためです。最も明白なのは実行回数アラートで、通知するたびに計測対象のカウントが増加してしまいます。

通知の実行は通常の実行であるため、他の実行と同様に[実行履歴](../reference/execution-history.md)に表示されます。通知Workflowが失敗した場合、その失敗は発火に記録されますが、発火自体の記録が妨げられることはありません。

通知Workflowはアラートのオーナーとして、そのオーナーの認証情報とグローバル変数を使用して実行されます。まるでオーナー自身が実行したかのようです。誰かが共有してくれたWorkflowを選択しても、その人の認証情報を借用することはありません。オーナーが通知Workflowへのアクセス権を失った場合、発火は記録されますが、通知の実行はスキップされます。

## 発火履歴

アラートリストの下には発火履歴があります。何が発火したか、いつ発火したか、しきい値に対する観測値、評価された正確なウィンドウ、そして通知の結果が表示されます。

発火を確認済みにすると、その行がマークされ、アラートのバッジが**Firing**から**Acknowledged**に変わります。これはアラートについてではなく、あなたについての表明です。条件は依然として成立しており、メトリクスがしきい値を下回ればアラートは自動的に**OK**に戻ります。

各レコードには、発火した瞬間の寄与の詳細が保存されます。失敗した実行のIDとエラーメッセージ、モデルごとの支出、またはTrigger元の内訳などです。これは意図的な設計です。ウィンドウはすでに過ぎており、後から再計算すると異なる結果になる可能性があるためです。

発火レコードは90日間保持されます。

## アラートについてChatに質問する

[Chatタブ](./chat-tab.md)では、アラートに関する質問に回答できます。

- 「自分のアラートには何がありますか？」
- 「invoice workflowにアラートはありますか？」
- 「なぜコストアラートが発火したのですか？」
- 「これは最後にいつTriggerされましたか？」

「なぜ発火したのか」という質問に対して、Chatは発火レコードから実際の観測値、しきい値、時間ウィンドウを、寄与の詳細とともに引用します。

## 共有

アラートは個々のユーザーまたは[チーム](./teams-tab.md)と共有できます。共有された人はアラートとその発火履歴を閲覧できます。編集、一時停止、削除、再共有ができるのはオーナーだけです。

### Workflowへのアクセスが削除された場合

単一のWorkflowに対するアラートは、そのWorkflowの実行メトリクスを継続的に読み取ります。そのため、誰かのWorkflowへのアクセスを削除することは、そのユーザーのアラートをどう扱うかも決定づけます：

- **ユーザーまたはチームの共有を削除する**と、Workflowの所有者に対して、そのユーザーまたはチームのWorkflow上のアラートも停止するかどうかが確認されます。デフォルトでは停止されます。停止されたアラートは削除ではなく一時停止となり、それぞれが[audit log](../reference/audit.md)に`alert.disable_on_access_revoke`として記録されます。
- **チームメンバーを削除する、またはチームを削除する**場合は、影響を受けるアラートが常に停止されます。これは、その変更を行った人物が必ずしもWorkflowの所有者であるとは限らないためです。
- アラートが停止されるのは、その所有者が直接共有や別のチームなど、Workflowへの他のアクセス経路を持たない場合のみです。
- 一時停止されたアラートを再開またはテストすると、所有者のアクセスが再度確認されます。そのため、停止されたアラートは、アクセスなしで再有効化したり、Workflowのメトリクスを読み取るために使用したりすることはできません。アクセス権がない状態で**Resume**を押すと、Workflowの所有者がまず再度共有する必要がある旨の通知が表示されます。

## アラートの管理

- **Pause / Resume** — 一時停止されたアラートは評価されません。Resumeすると、次のインターバルを待たずに即座にチェックされます。
- **Edit** — 変更は全体として検証されるため、部分的な編集によってアラートが無効な状態になることはありません。
- **Delete** — アラートとその発火履歴を削除します。
