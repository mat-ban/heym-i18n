# 부하 분산

두 번째 Heym 인스턴스를 동일한 PostgreSQL 데이터베이스를 바라보도록 지정하면 워커로 참여합니다. 이후 백그라운드 Workflow 실행은 설정한 비율에 따라 인스턴스 간에 분배되므로, UI와 API를 제공하는 머신이 모든 Workflow를 실행하는 유일한 머신이 되는 일이 없습니다.

인스턴스들은 서로 통신하지 않습니다. Postgres가 작업을 전달하므로 워커는 열린 포트도, 인증서도, 메인 인스턴스로 돌아가는 경로도 필요하지 않습니다 — 오직 데이터베이스 접근만 필요합니다.

## 역할

하나의 인스턴스는 환경 변수로 고정된 **main**입니다. 이 인스턴스는 UI, API, MCP 및 채팅 포털을 제공하며 파일 저장소와 설치된 플러그인을 소유합니다. 그 외의 모든 인스턴스는 **worker**입니다: 데이터베이스에만 접근하고 백그라운드 실행을 수행합니다.

```
HEYM_CLUSTER_ENABLED=true
HEYM_INSTANCE_ROLE=main       # 또는: worker
HEYM_INSTANCE_NAME=EU Main    # 표시 레이블, 나중에 Settings에서 편집 가능
HEYM_INSTANCE_ID=eu-main      # 선택 사항; 비어 있으면 이름에서 파생됨
```

main 역할은 리더 선출과는 별개입니다. Heym은 이미 클러스터 전체에서 하나의 리더를 선출하여 cron, 알림 평가 및 충돌 복구를 담당합니다. main이 다운되면 리더십은 몇 초 내에 워커로 이동하며 예약된 실행은 계속 발동됩니다. main 역할은 이동하지 않습니다. 파일 저장소가 함께 이동할 수 없기 때문입니다.

## main 인스턴스를 떠날 수 있는 것

배치는 실행이 시작되기 전에 Workflow의 노드를 기준으로 결정됩니다. 실행 내의 어떤 노드 — 호출하는 하위 Workflow 내부의 노드를 포함 — 가 한 머신에만 존재하는 무언가를 건드리면 해당 실행은 main에 남습니다:

| 노드 | main에 남는 이유 |
|---|---|
| Codex, OpenCode Go | 코딩 에이전트 워크스페이스가 로컬 디스크에 남아 있어 후속 작업이 그 안에서 재개될 수 있음 |
| 스킬이 연결된 Agent | 스킬 코드가 Heym Drive를 읽고 씀 |
| Drive, Converter, Google Drive | 생성된 파일을 읽고 씀 |
| File Upload Trigger | 업로드가 main의 디스크에 저장됨 |
| Send Email | 기업 SMTP 릴레이가 일반적으로 하나의 소스 주소만 허용 목록에 등록함 |
| 플러그인 노드 | 플러그인은 한 인스턴스의 디스크에 설치됨 |

**그 외의 모든 것은 분배됩니다** — Code 노드, Playwright 및 Agent Python 도구를 포함합니다. 모든 인스턴스는 자체 Docker 소켓을 가진 동일한 이미지를 실행하므로 샌드박스는 실행을 main에 유지할 이유가 되지 않으며, 이들은 제품에서 CPU를 가장 많이 소모하는 노드들입니다.

하위 Workflow가 표현식으로 선택되는 Workflow는 사전에 검사할 수 없으므로 main에 남습니다.

## 비율 선택

가중치는 **Settings → Instances**에서 설정하는 정수입니다. 이는 100에 대한 백분율이 아니라 **현재 작업을 받을 수 있는 인스턴스들의 몫**입니다: 스케줄러는 해당 풀 자체의 합계로 나눕니다.

이 구분은 인스턴스 하나가 빠지는 즉시 드러납니다. `Main 41, Worker A 26, Worker B 33`에서 Worker B를 끄면 풀은 67이 되므로 Main은 실제로 41/67 = **61%**를, Worker A는 26/67 = **39%**를 받습니다. 패널이 표 아래에 실효 분배를 출력하는 이유가 바로 이것이며, 숫자가 100이 되지 않는다고 해서 저장이 차단되는 일은 결코 없습니다 — 활성화된 인스턴스 중 가중치를 가진 인스턴스가 하나도 없는 분배만 거부됩니다.

두 가지를 더 쉽게 잘못 이해할 수 있습니다.

**백분율은 머신 성능의 몫이 아닙니다.** 이는 큐를 통과하는 실행만을 대상으로 합니다. UI와 API 제공, 에디터 및 포털 실행 스트리밍, 파일 업로드 처리는 모두 main의 작업이며 어느 것도 계산에 포함되지 않습니다. Main은 자신의 숫자가 말하는 것보다 더 많은 일을 하고 있습니다.

**Main의 백분율은 상한이지 하한이 아닙니다.** main에서만 실행될 수 있는 실행은 main의 할당량에 부과되므로, 그 할당량이 소진되면 남은 분배 가능한 실행은 워커로 넘어갑니다. main의 숫자를 낮게 설정하는 것은 안전합니다 — 반드시 그곳에서 실행되어야 하는 작업은 여전히 실행됩니다. 높게 설정하면 워커가 굶주리게 됩니다.

따라서 강력한 main과 더 작은 워커가 있다면 머신의 원시 비율보다 60/40에 가깝게 시작한 다음, Traces 탭에서 실제 실행 시간을 비교하며 조정하십시오.

가중치는 현재 라이브 상태이고 활성화된 인스턴스들 사이에서 재정규화됩니다. `main=70, A=15, B=15`에서 A가 오프라인이 되면 분배는 main과 B 사이에서 70/85와 15/85가 되고, A가 돌아오면 70/15/15로 복귀합니다.

**되돌아온 인스턴스가 놓친 실행을 받을 권리는 없습니다.** Offline, Disabled 또는 버전 불일치 상태로 보낸 시간은 해당 인스턴스에 계산되지 않으므로, 밤새 사용할 수 없었던 워커는 풀의 현재 위치로 재합류하여 첫 실행부터 분배가 다시 70/30으로 표시됩니다 — 따라잡을 때까지 모든 실행을 흡수하지는 않습니다. 내내 사용 가능했던 워커는 여전히 따라잡으며, 이것이 main의 백분율을 상한으로 만드는 이유입니다.

### 새 인스턴스는 0으로 합류합니다

한 번도 가중치를 부여받지 않은 인스턴스는 0에서 시작하므로, Live, Enabled 상태이면서도 아무것도 받지 못하게 됩니다. **새 인스턴스에 자동으로 몫 부여** — 인스턴스 표 아래에서 기본적으로 켜져 있음 — 가 이 문제를 해결합니다: 리더의 다음 순회에서 새로 온 인스턴스에 풀의 동등한 몫이 부여되고, 기존 가중치는 서로 간의 비율을 유지한 채 축소되므로 의도적인 70/30은 이후에도 대략 70/30으로 표시됩니다. 합계는 정확히 100으로 유지됩니다.

이는 **인스턴스당 한 번** 실행됩니다. 자동 순회와 직접 편집 모두 해당 인스턴스를 구성됨으로 표시하므로, 직접 설정한 인스턴스는 뒤에서 변경되지 않습니다 — 의도적으로 0으로 설정한 인스턴스를 포함해서요. 모든 새 머신이 직접 설정할 때까지 기다리게 하려면 이 설정을 끄십시오.

활성화되고 라이브이며 호환되는 인스턴스만 참여합니다. 아무것도 실행할 수 없는 머신에 몫을 넘기면 그 몫이 묶이게 됩니다.
### 백분율이 도움이 되지 않는 경우

설정 패널은 지난 24시간 동안의 실행 중 몇 건이 main에서만 실행될 수 있었는지 보고합니다. 이 수치가 높다면 — Codex 비중이 크거나 Drive 비중이 큰 워크로드라면 — 가중치가 무엇을 말하든 워커는 유휴 상태로 남게 되며, 해답은 워커를 늘리는 것이 아니라 더 큰 main 인스턴스입니다.

## 클러스터를 위한 PostgreSQL 사이징

연결 수는 사용자 수뿐 아니라 인스턴스 수에 따라 확장됩니다. 각 인스턴스는 여러 uvicorn 프로세스를 실행하며, 각 프로세스는 연결 풀 하나와 네 개의 `LISTEN` 연결(취소, 큐 깨우기, 실행 결과, 채팅 스트림)을 보유합니다. 열린 채팅 스트림은 하나의 채팅 연결을 공유하므로 데이터베이스 연결을 추가하지 않습니다. 기본 `max_connections = 100`에서 3개 인스턴스 클러스터는 연결이 고갈되며, 그러면 Heym이 자체 데이터베이스에 도달하지 못합니다.

대략 `instances x processes x (async pool + sync pool + 4)`로 예산을 산정하고 `max_connections`를 그보다 높게 설정하십시오.

상한만 올리지 말고 풀을 줄이십시오. 단일 배포는 기본적으로 프로세스당 async 10+20 및 sync 5+10 연결을 사용하는데, 이는 한 대의 머신에는 넉넉하지만 클러스터에는 너무 많습니다:

| 변수 | 단일 인스턴스 | 클러스터 |
|---|---|---|
| `HEYM_DB_POOL_SIZE` | 10 | 3 |
| `HEYM_DB_MAX_OVERFLOW` | 20 | 5 |
| `HEYM_DB_SYNC_POOL_SIZE` | 5 | 2 |
| `HEYM_DB_SYNC_MAX_OVERFLOW` | 10 | 3 |

예제 compose 파일은 이 값들과 `max_connections = 300`을 설정합니다. 이는 2개 인스턴스 클러스터의 연결 상한을 768에서 192로 낮추며, 3개 인스턴스도 여전히 300 미만입니다.

## 클러스터가 대신 강제할 수 없는 요구 사항

**모든 인스턴스는 동일한 `SECRET_KEY`와 `ENCRYPTION_KEY`를 사용해야 합니다.** 다른 `ENCRYPTION_KEY`를 가진 워커는 자격 증명을 복호화할 수 없으며, 자격 증명을 사용하는 모든 실행이 아무 쓸모 없는 오류를 내며 실패합니다. Heym은 각 하트비트에서 두 키의 다이제스트를 앱 버전 및 데이터베이스 리비전과 함께 비교하고, 불일치하는 인스턴스를 **Mismatch**로 표시하여 아무 작업도 받지 않도록 합니다. 문제를 해결할 때까지 부하는 main으로 폴백됩니다.

이는 업그레이드 순서도 정의합니다. main을 먼저 업그레이드하면 모든 워커가 호환되지 않는 것으로 표시되고, 작업은 main으로 돌아가며, 각 워커는 업그레이드되는 대로 다시 합류합니다. 더 느리지만 가시적이고 되돌릴 수 있습니다.

**인그레스는 main 인스턴스만을 향하게 하십시오.** 인스턴스 간에 사용자 트래픽을 라운드 로빈하면 파일 업로드는 한 머신으로, 그 다운로드는 다른 머신으로 전달됩니다. 워커가 동일한 이미지를 실행하며 수신하는 모든 요청에 응답하므로, 코드상으로 이를 막는 것은 없습니다.

**모든 인스턴스에는 동일한 공개 주소로 설정된 `FRONTEND_URL`이 필요합니다.** 사람의 검토를 위해 일시 중지된 실행은 main이 아니라 이를 실행한 인스턴스에서 검토 링크를 생성하며, Codex 후속 링크와 생성된 파일의 다운로드 URL도 마찬가지입니다. 이 설정 없이 남겨진 워커는 자체 로컬 주소를 기준으로 해당 링크를 생성하며, 링크를 받은 사람은 이를 열 수 없습니다.

**워커 인스턴스는 다른 아웃바운드 IP를 가집니다.** 소스 주소를 허용 목록에 등록하는 모든 API가 새 IP를 보게 됩니다. Send Email이 바로 이 이유로 main에서 실행됩니다. HTTP 노드의 경우, 클러스터에 단일 NAT 이그레스 주소를 부여하거나 모든 인스턴스를 허용 목록에 등록하십시오.

## 다른 머신에 워커 추가하기

저장소 루트의 `docker-compose.worker.yml`은 자체 호스트에서 워커를 실행합니다. 데이터베이스도 UI도 없습니다. main 인스턴스의 PostgreSQL에 연결하여 백그라운드 실행의 자기 몫을 가져갑니다.

그 옆에 `.env`를 작성하고 — 이미지 태그, 데이터베이스 호스트와 자격 증명, 두 키, 인스턴스 id — 시작하십시오. Compose는 모든 필수 값이 설정될 때까지 시작을 거부하며, 나중에 읽기 어려운 방식으로 실패하는 플레이스홀더로 기동하지 않습니다.

이미지 태그는 main이 실행하는 버전이어야 하며, 두 키는 정확히 복사해야 합니다. 둘 중 하나라도 다르면 워커가 Mismatch로 표시되고 아무 작업도 받지 않습니다.

## Instances 테이블 읽기

| 열 | 의미 |
|---|---|
| Name | 편집 가능한 레이블이며, 이 인스턴스가 실행하는 모든 실행에 각인됩니다 |
| Role | 환경에서 결정되는 `main` 또는 `worker` |
| Status | 하트비트가 최신이면 **Live**, 30초간 침묵하면 **Offline**, 버전·데이터베이스 리비전·키가 main과 다르면 **Mismatch** |
| ms | 해당 인스턴스에서 데이터베이스까지의 왕복 시간으로, 인스턴스 자체에서 측정합니다 |
| On | 워커를 중지하지 않고 로테이션에서 제외합니다 — 실행 중인 실행은 완료되고, 새 실행은 할당되지 않습니다. main 인스턴스는 잠금 상태입니다: 파일, 플러그인, 코딩 에이전트 작업은 토글과 무관하게 여기서 실행됩니다 |
| Weight | 분배 가능한 실행에서의 몫 |

## 실행 기록

실행 기록의 모든 실행은 이를 실행한 인스턴스의 이름을 표시하며, 두 기록 대화상자 모두 하나의 인스턴스로 필터링할 수 있습니다. 필터는 인스턴스의 이름을 표시하면서 id로 일치시키므로, 인스턴스 이름을 바꿔도 과거 실행이 표시하는 내용은 다시 쓰이지 않습니다.

단일 인스턴스 설치에서는 이와 관련된 어떤 것도 나타나지 않습니다: 필드는 비어 있고, 레이블이 표시되지 않으며, 필터도 제공되지 않습니다.
## 장애 동작

**worker가 실행 중에 종료되면**, 해당 worker의 heartbeat가 오래된 상태가 되고, leader의 기존 복구 sweep이 살아 있는 인스턴스에서 실행을 다시 수행합니다. worker가 점유했던 queue row는 별도로 정리됩니다. 해당 row에 대한 활성 실행이 더 이상 존재하지 않고 2분의 유예 시간이 지나면, leader가 해당 row를 실패 처리하고 결과를 기다리던 주체를 깨웁니다. 경과 시간만으로는 절대 trigger가 되지 않으므로, 정당하게 오래 실행되는 작업은 그대로 유지됩니다. 또한 row는 requeue가 아니라 실패 처리되는데, 복구가 이미 재실행을 담당하고 있어 requeue하면 동일한 Workflow가 두 번 실행되기 때문입니다.

**main이 다운되면**, cron은 worker에서 계속 발화하고 distributable 실행은 계속 수행됩니다. main이 필요한 실행은 queue에 쌓여 대기하다가 main이 복귀하면 처리됩니다. 다만 misfire 유예 window(`HEYM_CRON_MISFIRE_GRACE_SECONDS`, 기본 600초) 내에서만 그렇습니다. 그보다 오래된 것은 몇 시간 분량의 backlog를 한꺼번에 재생하는 대신, 사유를 기록한 채 skipped로 종료됩니다.

main이 다운된 동안에는 UI, API, MCP, editor를 사용할 수 없습니다. ingress가 main을 가리키기 때문입니다.
