# Evals 탭

**Evals** 탭은 `/evals`에 위치한 별도의 페이지입니다. 이를 통해 평가 스위트를 생성하고, 테스트 케이스를 정의하며, [Agent](../nodes/agent-node.md) Workflow에 대한 평가를 실행할 수 있습니다. [에이전트 스위트](#agent-suites)는 에이전트를 실행하거나 실제 실행 기록을 읽어와 호출된 도구, 지연 시간, USD 비용, 토큰 및 도구 호출 횟수를 검증합니다.

## 접근

- 대시보드 탭 바에서 **Evals**를 클릭합니다
- 또는 `/evals`로 이동합니다
- 또는 **Ctrl+K** (Cmd+K)를 사용하여 명령 팔레트에서 "Evals"를 선택합니다

## Eval 스위트

- **새 스위트** – 모델 간 시스템 프롬프트를 테스트하려면 **프롬프트 스위트**를, 에이전트의 실제 실행을 검증하려면 **에이전트 스위트**를 선택하십시오 ([에이전트 스위트](#agent-suites) 참조)
- **스위트 선택기** – 각 이름 옆에 유형과 함께 프롬프트 및 에이전트 스위트를 목록으로 표시합니다. 입력하여 검색할 수 있습니다
- **스위트 생성** – 이름과 설명이 포함된 스위트를 정의합니다
- **Workflow 선택** – 평가할 Workflow를 선택합니다
- **Credential 선택** – Workflow 실행을 위한 API key입니다
- **System Prompt** – 왼쪽 패널에서 스위트 수준의 system prompt를 직접 편집합니다
- **Prompt 최적화** – LLM에게 현재 system prompt 개선을 요청합니다

## 테스트 케이스

- 입력 prompt와 예상 출력이 포함된 테스트 케이스를 추가합니다
- 각 케이스는 비교를 위한 사용자 정의 예상 값을 가질 수 있습니다
- 스위트에서 케이스를 편집하거나 삭제합니다
- **테스트 데이터 생성** – 선택한 credential/model을 사용하여 스위트 prompt로부터 테스트 케이스를 자동 생성합니다

## 평가 실행

- **하나 이상의 모델 선택** – 하나의 평가에서 여러 모델에 대해 동일한 스위트를 실행합니다
- **채점 방식** – `Exact Match`, `Contains`, 또는 `LLM-as-Judge`를 선택합니다
- **Judge** – `LLM-as-Judge`의 경우, 선택적으로 OpenAI, OpenAI 호환 (Custom), Gemini (Google) 또는 [Decision Model](../nodes/decision-node.md) credential을 선택하고 judge의 모델(예: `gpt-4o-mini` 또는 `jev-latest`)을 입력하여 독립적인 judge로 채점합니다
- **테스트당 실행 횟수** – 하나의 실행에서 각 테스트 케이스를 여러 번 반복합니다
- **기억된 설정** – 스위트는 가장 최근 실행의 설정으로 열립니다: 자격 증명, 모델, 채점 방식 및 심사위원, 온도, 추론 노력, 테스트당 실행 횟수. 이전 실행을 열면 해당 설정이 로드되므로 **평가 재실행**으로 동일한 테스트를 반복할 수 있습니다
- **Temperature** – 모델 temperature를 설정합니다 (`Exact Match` 및 `Contains`)
- **추론 노력** – LLM 및 Agent 노드와 마찬가지로 추론 모델에 대해 낮음부터 매우 높음 및 최대로 추론 노력을 설정합니다 (`Exact Match` 및 `Contains`)

### LLM-as-Judge

Judge를 사용하면, 각 모델은 스위트 prompt만으로 테스트 입력에 답변하고, judge는 답변이 예상 출력과 얼마나 일치하는지를 0에서 100까지 평가합니다:

- **모델 judge** (OpenAI, OpenAI 호환 또는 Gemini)는 질문, 예상 출력, 답변을 읽고 한 줄의 이유와 함께 점수를 반환합니다. Temperature `0`으로 실행되며, reasoning 모델의 경우 `low` reasoning effort로 실행되므로 동일한 답변은 동일한 판정을 받습니다.
- **Decision model judge**는 *Completely off*부터 *Fully matches*까지 5단계 루브릭으로 답변을 평가합니다. 점수는 해당 루브릭에서 확률 가중치가 적용된 위치이므로, 모델이 작성한 숫자가 아니라 모델이 계산한 분포에서 나옵니다.

셀 호버 카드는 심사위원의 이유 또는 결정 모델의 경우 레벨, 점수 및 신뢰도를 보여줍니다. 지연 시간과 토큰은 테스트 중인 모델을 설명합니다. 심사위원 자체의 호출은 [추적](./traces-tab.md)의 **평가** 소스 아래에 나타납니다. 심사위원 선택기는 Model Router 자격 증명을 제외합니다. 심사위원은 하나의 고정된 모델이어야 하기 때문입니다. 테스트 대상 모델의 자격 증명은 [Model Router](../reference/credentials.md#model-router-auto-model)일 수 있습니다: **Auto** 모델은 워크플로에서와 마찬가지로 요청당 모델을 동적으로 선택합니다.

Judge가 없으면 각 모델은 단일 요청에서 자체 답변을 생성하고 채점합니다.

이 모드에서는 Temperature와 reasoning effort가 숨겨지며, 실행은 고정 설정을 사용합니다: 표준 모델의 경우 temperature `0.7`, reasoning 모델의 경우 `medium` reasoning effort (자체 답변을 채점할 때는 `low`)입니다.

## 결과

- 테스트 케이스별 통과/실패를 확인합니다
- 실제 출력과 예상 출력을 검사합니다
- 실행에 여러 모델이 포함된 경우 모델별 출력을 나란히 비교합니다
- 과거 평가의 실행 기록을 검토합니다. `LLM-as-Judge` 실행은 기록 목록에 judge 모델을 표시합니다
- 결과 패널에서 과거 실행을 열고 저장된 prompt/입력/출력 스냅샷을 검사합니다
- 과거 실행을 열면 해당 채점 방식과 judge가 왼쪽 패널에 로드되므로, **Re-Run Evals**는 동일한 평가를 반복합니다
- **Export**는 `judge_credential_id`와 `judge_model`을 포함하여 실행을 JSON으로 다운로드합니다

## Agent Suites

에이전트 스위트는 [Agent](../nodes/agent-node.md) 노드를 실행 기록에 대조하여 검증합니다. 모든 실행에서 시간, 토큰, 비용, 도구 호출을 이미 기록하고 있는 [추적](./traces-tab.md)에서 이를 읽어오며, 워크플로를 대신 실행할 수도 있습니다.

**새 스위트** → **에이전트 스위트**로 생성하고 다음 3단계를 진행하십시오:

1. **Agent** – 워크플로를 선택한 다음 에이전트 노드를 선택합니다. 에이전트 노드가 있는 워크플로만 나열됩니다. 아직 실행되지 않은 워크플로나 에이전트는 표시되지만 선택할 수는 없습니다. 선택한 에이전트의 설정(모델, 지침, 도구 및 제한)이 오른쪽에 표시되며, 에이전트가 강조 표시된 워크플로의 읽기 전용 캔버스가 아래에 나타납니다.
2. **Baseline** – 에이전트의 최근 10회 실행 기록: 지연 시간 p50 및 p95, 실행당 비용, 실행당 토큰, 실행당 도구 호출 횟수, 호출한 도구와 빈도, 각 실행의 개별 수치. 오류로 종료된 실행은 나열되지만 baseline에서는 제외됩니다.
3. **검증 항목** – 각 도구를 **Must call**, **Must not call** 또는 **Either**로 표시합니다. 모든 호출 유형이 종류와 함께 나열됩니다: Python 및 노드 도구, 서버 정보가 포함된 **MCP** 도구, 라벨별 **하위 에이전트**, 이름별 **하위 워크플로** 및 **skills**. 아직 실행되지 않은 도구는 종류와 이름을 입력하여 추가할 수 있으며, **X** 버튼으로 제거할 수 있습니다. 지연 시간, 비용, 총 토큰, 도구 호출에 대한 상한을 설정하십시오. 각각은 baseline p95보다 20% 높은 값에서 시작하며 끌 수 있습니다.

저장된 스위트는 **결과** 탭에서 열리며, 옆에 **Baseline** 및 **검증 항목 편집**이 표시됩니다:

- **워크플로 실행** – 실행 횟수를 선택합니다(최대 20회). 한 번에 4회씩 동시에 실행됩니다. 입력값은 워크플로의 가장 최근 실행에서 채워지며 편집할 수 있고 모든 실행에서 이를 사용합니다. **입력 생성**(스파클 아이콘)을 켠 다음 자격 증명과 모델을 선택하면 모델이 각 실행마다 서로 다른 입력을 작성합니다. 에이전트의 시스템 지침을 읽고 입력한 값과 유사한 변형을 유지합니다. 도시 이름을 입력하면 다른 도시 이름을 생성합니다. 각 실행은 일반 실행과 마찬가지로 전체 워크플로를 온전히 실행하며 실행 기록에 `agent_suite` 트리거로 기록됩니다. 이메일 전송과 같은 후속 단계를 건너뛰려면 패널의 **워크플로로 이동**을 통해 워크플로를 열고 해당 노드를 먼저 비활성화하십시오. **중지**는 스위트 실행을 종료합니다. 새 실행은 시작되지 않으며 진행 중인 실행은 취소됩니다. 재시작 등으로 인해 서버가 중지된 스위트 실행은 멈춰 있는 대신 1분 후에 중단됨으로 표시됩니다.
- **결과** – 기본적으로 최신 스위트 실행이 평가됩니다. 각 스위트 실행은 실행 선택기에 날짜와 함께 보관되어 열거나 삭제할 수 있습니다. 또는 에이전트의 최근 10회, 20회, 50회 실행으로 전환하여 다른 일반 실행도 포함할 수 있습니다. 저장된 baseline 옆에 합격률, 각 검증 통과 빈도, 지연 시간, 비용, 토큰, 도구 호출이 표시되며, 실패 이유와 추적 링크가 포함된 각 실행을 확인할 수 있습니다.
- **워크플로로 이동**은 새 탭에서 에이전트의 워크플로를 엽니다. 이름 필드에서 **Esc** 또는 **X**를 누르면 텍스트가 지워집니다.

수치 해석 방법:

- **지연 시간**은 모델의 응답 시간에 실행 중 발생한 도구 호출 시간을 더한 값입니다.
- **비용**은 Traces와 동일한 단가를 적용합니다. 가격이 설정되지 않은 모델의 실행은 실패하는 대신 비용 검사를 건너뜁니다.
- 실행이 오류 없이 완료되고 모든 검증을 통과하면 **합격**으로 판정됩니다.
- 스위트는 추적 탭과 동일한 규칙에 따라 본인에게 권한이 있는 추적만 읽습니다.
- **검증 항목 편집**에서 **최신 실행을 기준선으로 사용**을 클릭하면 저장된 baseline이 에이전트의 최신 실행 기록으로 대체됩니다.

스위트의 baseline은 세 가지 출처 중 하나에서 가져옵니다. **검증 항목 편집**에서는 **저장된 기준선** 옆에 현재 활성화된 출처를 표시합니다:

- 에이전트의 최신 실행 (기본값이며 **최신 실행을 기준선으로 사용**이 가져오는 값),
- 완료된 1회의 스위트 실행,
- 수동으로 입력한 수치.

후자의 두 가지는 [Chat](./chat-tab.md#working-with-evals) 또는 API를 통해 설정합니다:

- `PATCH /api/evals/agent-suites/{id}`는 `baseline: {"source": "suite_run", "run_id": "…"}` 또는 `{"source": "manual", "values": {"latency_p95_ms": 3000, "cost_avg_usd": 0.01}}`을 수신합니다.
- `POST /api/evals/agent-suites/{id}/runs`는 `inputs_list`를 수신합니다: 실행당 1개의 입력 객체, 최대 20개.

### Chat 및 MCP에서 사용

[Chat](./chat-tab.md#working-with-evals) 및 MCP `heym_chat` 도구는 프롬프트 및 에이전트 스위트를 생성, 수정, 실행할 수 있습니다:

- 테스트 케이스와 실행 입력을 자체적으로 작성합니다.
- 프롬프트 스위트를 생성하기 전에 적합한 자격 증명이 하나뿐이지 않은 한 사용할 자격 증명을 묻습니다.
- 이 페이지에서 언급하는 모든 스위트로의 링크를 제공합니다.

## 벤치마크 매트릭스 아이디어

Agent Workflow를 위한 벤치마크 매트릭스를 구축할 때는, HITL 시나리오를 엣지 케이스로 취급하는 대신 일급 케이스로 포함하십시오.

- 세 가지 리뷰 결정을 모두 포함합니다: `accepted`, `edited`, `refused`
- editor 실행, portal, curl/webhook, cron-triggered 실행 등 여러 Trigger 소스를 포함합니다
- 하나의 agent 실행이 두 번 이상 일시 중지되는 반복 리뷰 시나리오를 추가합니다
- agent의 `review` 출력에 연결된 알림 분기를 검증합니다
- 거부 이후의 다운스트림 동작을 검증합니다. 특히 이후 노드가 `$agent.decision`을 기준으로 분기하는 경우 중요합니다
