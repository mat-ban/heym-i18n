# Запуск і розгортання

Heym надає два скрипти для різних середовищ: `run.sh` для локальної розробки та `deploy.sh` для продакшн-розгортань за допомогою Docker Compose.

> **Відеоогляд:** [Налаштуйте Heym локально менш ніж за 2 хвилини](https://www.youtube.com/watch?v=P6YvlupUboU) — клонуйте репозиторій, запустіть PostgreSQL, заповніть необхідні змінні середовища та створіть свій перший акаунт на локальному екземплярі.

## Передумови

Обидва скрипти вимагають встановлення таких інструментів:

| Інструмент | Призначення |
|------|---------|
| [Docker](https://docs.docker.com/get-docker/) | Контейнер бази даних (dev) і повний стек (prod) |
| [uv](https://github.com/astral-sh/uv) | Менеджер пакетів Python для бекенду |
| [bun](https://bun.sh) | Середовище виконання JavaScript для фронтенду |

## Налаштування середовища

Обидва скрипти `run.sh` і `deploy.sh` читають дані з файлу `.env` у корені проєкту. Якщо він не існує, скрипт автоматично створює його з `.env.example` — як для локальної розробки, так і для продакшену.

`SECRET_KEY` і `ENCRYPTION_KEY` постачаються порожніми в `.env.example`. Коли будь-який із них порожній, `run.sh` і `deploy.sh` автоматично генерують криптографічно стійке значення та записують його назад у `.env`, тож для свіжого налаштування не потрібне ручне керування ключами. Якщо наявний `.env` усе ще містить застарілий заповнювач `ENCRYPTION_KEY` (`change_this_to_a_random_32_byte_hex_value`), скрипти зупиняються з явною помилкою замість його перезапису — ротація цього ключа зробила б раніше зашифровані облікові дані нечитабельними. Сам бекенд також відмовляється запускатися, якщо будь-який із ключів порожній або залишений на відомому заповнювачі.

Щоб створити файл вручну (необов'язково — скрипти роблять це за Вас):

```bash
cp .env.example .env
```

Ключові змінні середовища:

Щодо кожної підтримуваної змінної, значення за замовчуванням і примітки для продакшену дивіться [Environment Variables](https://github.com/heymrun/heym/blob/main/ENVIRONMENT-VARIABLES.md).

| Змінна | Опис |
|----------|-------------|
| `SECRET_KEY` | **Обов'язково.** Секрет для підпису JWT. Автоматично генерується `run.sh`/`deploy.sh`, коли порожній. |
| `ENCRYPTION_KEY` | **Обов'язково.** Ключ шифрування облікових даних. Автоматично генерується `run.sh`/`deploy.sh`, коли порожній. |
| `DATABASE_URL` | Необов'язкове перевизначення рядка підключення до бази даних. Якщо порожній, Heym будує його з налаштувань `POSTGRES_*`. |
| `BACKEND_PORT` | Порт API бекенду — за замовчуванням `10105` |
| `FRONTEND_PORT` | Порт фронтенду — за замовчуванням `4017` |
| `FRONTEND_URL` | **Обов'язково в продакшені.** Публічна URL-адреса застосунку (схема + хост, наприклад `https://heym.example.com`). Використовується для URI перенаправлення OAuth (Google Sheets, BigQuery, Notion тощо), а також для посилань на рев'ю, продовження Codex і файли, які створюють фонові запуски; має збігатися з URL-адресою, яку користувачі використовують у браузері. У кластері встановіть однакове значення на кожному екземплярі. |
| `ALLOW_REGISTER` | Відкрита реєстрація користувачів (`false` у prod, `true` у dev). Перемкніть на `false` лише після створення Вашого адміністративного акаунта — початкового завантаження першого користувача немає, тож порожня база даних разом із вимкненою реєстрацією не залишає способу його створити. |
| `DOCKER_LOGS_ENABLED` | Увімкнює доступ до вкладки Logs на основі Docker, коли встановлено `true`; також вимагає доступу до сокета Docker |
| `DOCKER_LOGS_ALLOWED_EMAILS` | Список довірених електронних адрес користувачів, розділених комами, яким дозволено доступ до логів Docker, коли `DOCKER_LOGS_ENABLED=true` |
| `REQUEST_BODY_MAX_SIZE_MB` | Максимальний розмір тіла HTTP-запиту, що приймається до запуску обробників endpoint; за замовчуванням `100`, на один МБ більше за `FILE_MAX_SIZE_MB`, щоб залишити місце для накладних витрат multipart |
| `HEYM_PYTHON_TOOL_SANDBOX` | Як виконуються визначені користувачем інструменти Python: `auto` (за замовчуванням — посилений, ізольований контейнер Docker; безпечна відмова, якщо Docker недоступний), `docker` (те саме, ніколи не перемикається на резервний варіант) або `subprocess` (локальний резервний варіант у процесі; не є межею безпеки, лише для довіреного/dev-середовища). `run.sh` встановлює `subprocess` для нативної розробки. Дивіться [Security](../reference/security.md#python-tool-sandbox). |
| `HEYM_PYTHON_TOOL_IMAGE` | Образ, який використовується для пісочниці Docker інструментів Python. Порожній = автоматично визначити запущений образ бекенду. |

Значення за замовчуванням для підключення до бази даних (`POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`) задокументовано в [Environment Variables](https://github.com/heymrun/heym/blob/main/ENVIRONMENT-VARIABLES.md) і `.env.example`.

## Розробка: `run.sh`

`run.sh` запускає всі три сервіси локально — базу даних (як Docker-контейнер), бекенд FastAPI та сервер розробки Vite — однією командою.

```bash
./run.sh
```

**Що він робить, крок за кроком:**

1. Перевіряє, що `docker`, `bun` та `uv` доступні
2. Створює `.env` з `.env.example`, якщо він відсутній, і генерує випадкові `SECRET_KEY` та `ENCRYPTION_KEY`, коли будь-який із них порожній
3. Запускає (або створює) Docker-контейнер бази даних на порту `6543`, зберігаючи його дані в Docker-томі `heym-postgres-data`, а не в каталозі хоста
4. Встановлює залежності Python за допомогою `uv sync`
5. Запускає міграції бази даних Alembic (`alembic upgrade head`)
6. Звільняє порти бекенду та фронтенду, якщо вони зайняті
7. Запускає бекенд FastAPI з `--reload` (гаряче перезавантаження при змінах коду)
8. Встановлює залежності фронтенду за допомогою `bun install`
9. Запускає сервер розробки Vite

**Опції:**

| Прапорець | Опис |
|------|-------------|
| *(немає)* | Запуск із увімкненим журналюванням налагодження (`LOG_LEVEL=DEBUG`) |
| `--no-debug` | Запуск із типовим рівнем журналювання (без виводу налагодження) |
| `--help` | Показати інформацію про використання |

**Адреси сервісів (розробка):**

| Сервіс | Адреса |
|---------|---------|
| Фронтенд | `localhost` на `FRONTEND_PORT` (типово: 4017) |
| Бекенд API | `localhost` на `BACKEND_PORT` (типово: 10105) |
| Інтерактивна документація API | `localhost:10105/docs` |
| База даних | `localhost:6543` |

Натисніть `Ctrl+C`, щоб коректно зупинити всі сервіси.

## Наскрізні тести: `run_e2e.sh`

Набір тестів Playwright для фронтенду запускається проти справжнього застосунку Vue, бекенду FastAPI та
ізольованої бази даних PostgreSQL:

```bash
./run_e2e.sh
```

Цей набір є димовим і регресійним набором для ключових шляхів, а не вичерпним покриттям продукту. Він охоплює
автентифікацію, життєвий цикл і виконання основних workflow, вибрані ресурси панелі керування, публічні
маршрути та змодельований інтерфейс перевірки HITL. Інтеграції з провайдерами, кожен тип вузла, матриці
спільного доступу/дозволів та повне виконання відновлення HITL залишаються переважно покритими бекенд-тестами
або потребують спеціальних інтеграційних середовищ.

Кожен запуск отримує власний тимчасовий контейнер PostgreSQL 16, випадкові доступні порти бази даних, бекенду
та фронтенду, стан автентифікації, результати тестів і HTML-звіт. Це дозволяє кільком процесам `run_e2e.sh`
працювати одночасно без спільного стану чи перезапису артефактів. Скрипт видаляє свій контейнер бази даних
після завершення запуску та виводить каталог артефактів і шлях до звіту.

Корисні команди:

```bash
./run_e2e.sh --ui         # Інтерактивний запуск Playwright з ізольованою базою даних
cd frontend
bun run test:e2e:report   # Відкрити останній завершений локальний запуск
```

Прямі запуски `bun run test:e2e` та `bun run test:e2e:ui` вимагають явного `DATABASE_URL`, щоб вони
не могли непомітно запуститися проти локальної бази даних розробки. Використовуйте `./run_e2e.sh` для звичайних
локальних запусків.

`./check.sh` запускає лінтер, перевірку типів, форматування та бекенд-тести без набору E2E, зберігаючи
типовий шлях локальної перевірки швидким. Запускайте E2E-тести Playwright окремо за допомогою `./run_e2e.sh`. Pull
requests завжди запускають набір E2E для Chromium у GitHub Actions і зберігають трасування, знімки екрана,
відео та HTML-звіт у разі збоїв.

## Production: `deploy.sh`

`deploy.sh` збирає та запускає повний стек за допомогою Docker Compose. Усі три сервіси — база даних, backend і frontend — працюють як контейнери. Entrypoint backend автоматично запускає міграції перед стартом сервера з 8 workers.

**Початковий деплой (збірка + запуск):**

```bash
./deploy.sh
```

Це виконує деплой без простою: образи спочатку збираються, поки наявні контейнери продовжують працювати, потім нова версія підміняється.

**Доступні команди:**

| Команда | Опис |
|---------|-------------|
| `./deploy.sh` | Зібрати образи та запустити/оновити всі сервіси |
| `./deploy.sh --status` | Показати статус контейнерів |
| `./deploy.sh --logs` | Потоково виводити логи з усіх контейнерів |
| `./deploy.sh --restart` | Перезапустити всі контейнери |
| `./deploy.sh --down` | Зупинити та видалити всі контейнери |
| `./deploy.sh --migrate-pgdata` | Одноразова міграція: скопіювати наявний каталог `data/postgres` у Docker volume `heym-postgres-data` та перебудувати його індекси |
| `./deploy.sh --help` | Показати довідку щодо використання |

**Зберігання бази даних: іменований Docker volume, а не каталог на хості.**

Compose зберігає PostgreSQL у Docker volume `heym-postgres-data`. Ранніші версії натомість монтували каталог хоста `./data/postgres` через bind mount. Bind mounts хоста на macOS (virtiofs) та Windows/WSL2 не дають PostgreSQL гарантій `fsync` і закриття файлів, яких він потребує: кластери там натрапляють на `PANIC: could not close file … Input/output error` на WAL-сегментах і з часом пошкоджуються. Bind mounts на Linux ніколи не були уражені, але тепер усі платформи використовують однакову схему.

Оновлення деплою, який досі має дані в `./data/postgres`, є одноразовим кроком. `./deploy.sh` виявляє це, зупиняється перед збіркою та просить Вас спершу виконати міграцію:

```bash
./deploy.sh --migrate-pgdata   # stop services, copy into the volume, rebuild indexes
./deploy.sh                    # deploy as usual
```

**Міграція також перебудовує індекси.** Копіювання є побайтовим, тож пошкодження індексів, спричинені старим bind mount, переносяться разом із даними. Тому `--migrate-pgdata` запускає сервіс `postgres` окремо на новому volume, виконує `reindexdb` щодо нього та знову зупиняє його, перш ніж піднімається решта стеку. Це важливо, оскільки цей клас пошкоджень залишає записи індексів, що вказують за межі heap — стан, який `pg_amcheck` звітує як чистий, тож успішна перевірка не є доказом здорової таблиці. REINDEX виправляє ці записи; він не може відновити сторінки heap, які старий файловий простір уже втратив. На великій базі даних, що відомо є здоровою, Ви можете обійти перебудову за допомогою `./deploy.sh --migrate-pgdata --skip-reindex`.

Копіювання є неdestructive. `./data/postgres` залишається на місці як резервна копія, і міграція відмовляється перезаписувати volume, який уже містить базу даних. Якщо якийсь крок зазнає невдачі, новий volume видаляється, тож наполовину мігрований кластер ніколи не буде розгорнуто помилково. Видаліть старий каталог, щойно Ви підтвердите, що Ваші workflows неушкоджені. Контейнер `postgres` має такий самий захист, тож ручний `docker compose up` також не може непомітно ініціалізувати порожню базу даних поверх Ваших даних. Свіжі інсталяції не потребують жодних дій.

**Адреси сервісів (production):**

Контейнер frontend відкрито на `FRONTEND_PORT` (типово: 4017). Backend API обслуговується за шляхом `/api`, проксіюється через контейнер frontend — тож у production є лише один публічний порт.

**Огляд контейнерів:**

| Контейнер | Опис |
|-----------|-------------|
| `heym-db` | Реляційна база даних |
| `heym-backend` | Сервер FastAPI API (8 workers, зібраний з `backend/Dockerfile`) |
| `heym-frontend` | Контейнер попереднього перегляду frontend, що обслуговує зібраний застосунок Vue (зібраний з `frontend/Dockerfile`) |

**Бейдж оновлення версії:**

У заголовку застосунку показано версію запущеного Docker build. Коли ця версія відстає від останнього релізу Heym на GitHub, поруч із версією з'являється фіолетовий бейдж **Update**. Натисніть на версію або бейдж, щоб відкрити сторінку релізів Heym на GitHub.

## Готовий образ: `docker run`

Якщо Ви не бажаєте збирати застосунок локально, можете завантажити опублікований образ контейнера та запустити його безпосередньо.

Образ запускає frontend і backend разом в одному контейнері. PostgreSQL усе ще зовнішній, але Ви можете надати або `DATABASE_URL`, або змінні `POSTGRES_*` з `.env.example`.

> **Зберігайте базу даних у Docker named volume.** Образ релізу не містить бази даних, тож PostgreSQL за `DATABASE_URL` — це Ваша відповідальність. Монтуйте його як `-v heym-postgres-data:/var/lib/postgresql/data`, а не як шлях на хості: на macOS (virtiofs) та Windows/WSL2 bind-mounted каталог даних PostgreSQL не дотримується гарантій `fsync`, яких потребує база даних, і з часом пошкоджує cluster.

> **Бекенд vector store.** `run.sh` і `deploy.sh` запускають офіційний образ `postgres:16` та автоматично встановлюють пакет `postgresql-16-pgvector` під час запуску, тож **бекенд RAG Postgres (pgvector)** працює там одразу без змін у Ваших даних. Однак готовий single-container образ підключається до PostgreSQL, який надаєте **Ви** — ця база даних повинна підтримувати розширення `vector`, щоб використовувати бекенд Postgres. Heym не може встановити pgvector у базу даних, якою він не керує. Без нього міграція під час запуску коректно пропускає таблицю pgvector — розгортання все одно завершується успішно, Qdrant RAG продовжує працювати, а створення чи завантаження до Postgres vector store повертає чітке повідомлення "backend unavailable", доки pgvector не буде увімкнено.

**Встановіть ключі самостійно для прямих запусків образу.** На відміну від `run.sh`/`deploy.sh`, готовий образ не генерує ключі автоматично. Після `cp .env.example .env` заповніть два порожні ключі (заміна на місці дозволяє уникнути дубльованих записів):

```bash
SECRET_KEY=$(python3 -c "import secrets; print(secrets.token_urlsafe(32))")
ENCRYPTION_KEY=$(python3 -c "import secrets; print(secrets.token_hex(32))")
sed -i.bak "s|^SECRET_KEY=.*|SECRET_KEY=${SECRET_KEY}|; s|^ENCRYPTION_KEY=.*|ENCRYPTION_KEY=${ENCRYPTION_KEY}|" .env && rm -f .env.bak
```

```bash
docker pull ghcr.io/heymrun/heym:latest

docker run --rm \
  --env-file .env \
  -p 4017:4017 \
  --shm-size 2g \
  -e FILE_STORAGE_DIR=/app/data/files \
  -e HEYM_PLUGINS_DIR=/app/data/plugins \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v "$(pwd)/data/files:/app/data/files" \
  -v "$(pwd)/data/plugins:/app/data/plugins" \
  -v heym-codex-workspaces:/app/data/codex-workspaces \
  -v heym-opencode-workspaces:/app/data/opencode-workspaces \
  ghcr.io/heymrun/heym:latest
```

> **Зробіть монтування файлів і плагінів абсолютними.** `FILE_STORAGE_DIR` і `HEYM_PLUGINS_DIR` за замовчуванням мають відносні шляхи `./data/files` і `data/plugins`, а образ релізу запускає backend з `/app/backend`. Якщо залишити їх відносними, вони розв'яжуться в `/app/backend/data/files` і `/app/backend/data/plugins`, тож два bind mounts вище не отримають нічого, і завантаження буде втрачено, коли контейнер буде замінено. Прапорці `-e` перекривають відносні значення, які надає `.env.example` через `--env-file`, оскільки командний рядок `-e` має пріоритет над `--env-file`. Compose (`./deploy.sh`) цього не потребує: той образ запускає backend з `/app`, де відносні значення за замовчуванням уже вказують на монтування.

> **Доступ до Docker socket.** Монтування `/var/run/docker.sock` надає backend широкий контроль над Docker daemon хоста. Служба Docker Compose за замовчуванням і приклад прямого `docker run` включають його для Docker-based MCP stdio tools, які виконують команди `docker`. Вкладка Logs усе ще потребує `DOCKER_LOGS_ENABLED=true` і `DOCKER_LOGS_ALLOWED_EMAILS` зі списком довірених email користувачів, розділених комами. Створіть довірений admin-акаунт перед увімкненням Docker logs або залиште `ALLOW_REGISTER=false`, щоб непідтверджена самореєстрація не могла заявити email зі списку дозволених. Користувацькі Python tools **не** отримують цей socket: вони виконуються в окремому посиленому контейнері без Docker socket. Дивіться [Security](../reference/security.md#python-tool-sandbox).

> **Codex runner.** Вузол Codex використовує той самий образ `ghcr.io/heymrun/heym` як sibling runner container (`--entrypoint codex`), щоб Linux sandbox Codex міг створювати namespaces. Залиште монтування тому `heym-codex-workspaces`, якщо Ви хочете використовувати Codex workflows у налаштуванні прямого образу; runner не отримує Docker socket або секрети backend.

> **OpenCode Go runner.** Вузол OpenCode Go використовує той самий образ як посилений sibling runner (`--entrypoint opencode`), спільно використовуючи `heym-opencode-workspaces`. Залиште це монтування тому, якщо Ви хочете використовувати OpenCode workflows у налаштуванні прямого образу; runner не отримує Docker socket або GitHub token.

> **Skill sandbox.** Python skills на вузлі Agent виконуються в посиленому sibling container, який спільно використовує том `heym-codex-workspaces`, тож залиште це монтування тому також для skills — не лише для Codex. Кожен запуск отримує ізольований subpath для кожного запуску, а sibling не отримує ні Docker socket, ні секрети backend. Це потребує **Docker Engine 25.0+**; на старіших engine або без тому `HEYM_PYTHON_TOOL_SANDBOX=auto` завершується відмовою — встановіть `HEYM_PYTHON_TOOL_SANDBOX=subprocess` лише для довірених single-user налаштувань. Дивіться [Security](../reference/security.md#skill-sandbox).

> **`--shm-size 2g` є обов'язковим для Playwright.** Docker надає контейнеру 64 МБ `/dev/shm`, і Chromium зазнає збою рендерера за такого обмеження. Вузли Playwright на основі кроків запускають Chromium як підпроцес усередині цього контейнера, тому обмеження належить цьому контейнеру; користувацький `playwrightCode` виконується в сусідньому контейнері, який встановлює власне обмеження. `docker-compose.yml` уже оголошує `shm_size: "2gb"`, тому `run.sh` і `deploy.sh` не зазнають впливу — лише звичайний `docker run` потребує цього прапорця.

> **Playwright Run Code.** Користувацькому Playwright Python потрібні `HEYM_PLAYWRIGHT_CUSTOM_CODE_ENABLED=true` і монтування Docker socket, зазначене вище. Релізний образ встановлює `HEYM_PLAYWRIGHT_SANDBOX_IMAGE` / `HEYM_PLAYWRIGHT_SANDBOX_PYTHON` для схеми GHCR (`/app/backend/.venv`). Compose `./deploy.sh` за замовчуванням використовує sandbox-образ `heym-backend:local`. Залишайте `--no-sandbox` у аргументах запуску Chromium усередині sandbox-контейнерів.

**Примітки:**

- Образ відкриває порт `4017`
- Backend залишається внутрішнім і проксіюється за шляхом `/api`
- Коли `POSTGRES_HOST=localhost`, релізний образ автоматично переписує його на `host.docker.internal`, коли потрібно, щоб той самий `.env` працював із контейнером PostgreSQL на рівні хоста в інструментах macOS Docker/Desktop
- Зберігайте монтування `data/files`, якщо хочете, щоб завантаження в Drive і файли, згенеровані навичками, переживали перезапуски контейнера
- **Плагіни:** щоб увімкнути їх, встановіть `HEYM_PLUGINS_ENABLED=true` і `HEYM_PLUGIN_ADMIN_EMAILS`, а також змонтуйте `data/plugins`, щоб встановлені файли плагінів зберігалися між перествореннями контейнера. Метадані плагінів зберігаються у Вашому PostgreSQL, тому вони також зберігаються. Оголошені плагіном pip `dependencies` встановлюються в контейнер під час встановлення; оскільки файлова система образу є ефемерною, вони **повторно встановлюються автоматично під час запуску** для кожного встановленого плагіна (venv `uv` релізного образу доступний для запису, тому це працює і в одноконтейнерному образі)

### Перенесення наявної бази даних до іменованого тому

`./deploy.sh --migrate-pgdata` знає лише про стек Compose. Якщо Ви запускаєте релізний образ із власним контейнером PostgreSQL, і цей контейнер монтує каталог хоста через bind-mount, перенесіть його самостійно.

Спочатку перевірте, що використовує Ваш контейнер бази даних:

```bash
docker inspect <your-postgres-container> | grep -A8 Mounts
```

Якщо `"Type"` має значення `bind`, перемістіть його до іменованого тому:

```bash
# 1. Зупиніть базу даних. Heym може бути вимкнений для цього.
docker stop <your-postgres-container>
docker rm <your-postgres-container>

# 2. Скопіюйте каталог даних до іменованого тому. Надайте кожному екземпляру власний

#    назва тому, якщо цей Docker host запускає більше одного розгортання Heym.
docker volume create heym-postgres-data
docker run --rm \
  -v "/path/to/your/data/postgres:/legacy:ro" \
  -v heym-postgres-data:/pgdata \
  --entrypoint sh <your-postgres-image> -c 'cp -a /legacy/. /pgdata/'

# 3. Знову запустіть PostgreSQL на томі, повторно використовуючи прапорці, які Ви мали раніше,
#    але замінивши bind mount.
docker run -d --name <your-postgres-container> --restart always \
  ... your original -e / -p / --network flags ... \
  -v heym-postgres-data:/var/lib/postgresql/data \
  <your-postgres-image>

# 4. Щойно він почне приймати з'єднання, перебудуйте індекси.
docker exec <your-postgres-container> reindexdb -U <user> -d <database>
```

**Використовуйте власний образ на кроках 2 і 3, а не `postgres:16`.** Якщо Ваша база даних працює на `pgvector/pgvector:pg16` або іншому варіанті, запуск скопійованого cluster зі стандартним образом може завершитися невдачею, оскільки бібліотеки розширень, яких він очікує, відсутні.

Ваш оригінальний каталог даних цією процедурою не змінюється, тож він залишається Вашим шляхом відкату. Видаліть його лише після підтвердження, що мігрована база даних обслуговує Ваші workflow. Крок 4 важливий з тієї ж причини, що й у міграції Compose: копія переносить із собою будь-яке наявне пошкодження індексів.

## Запуск більше ніж одного екземпляра

Усе описане вище розгортає один екземпляр Heym. Коли однієї машини вже
недостатньо, спрямуйте другий екземпляр на ту саму базу даних PostgreSQL, і він
приєднається як worker: фонові запуски — cron, webhooks, виклики інструментів MCP,
chat triggers — далі розподіляються між екземплярами за відсотком, який Ви
задаєте в розділі **Settings → Instances**.

Екземпляри ніколи не спілкуються один з одним. Postgres несе роботу, тож worker
не потребує відкритого порту чи маршруту назад до головного екземпляра, і жоден
брокер повідомлень не задіяний. Робота, що торкається локального диска — файли
Drive, робочі простори coding-agent, встановлені плагіни — завжди виконується на
головному екземплярі, тож нічого не потрібно спільно використовувати через
файлову систему.

Два правила, які cluster не може забезпечити за Вас: кожен екземпляр має
використовувати однакові `SECRET_KEY` та `ENCRYPTION_KEY`, і ingress має
вказувати лише на головний екземпляр. Обидва пояснено разом із правилами
розміщення та тим, як вибирати відсотки, у [Load Distribution](../reference/cluster.md).

> Це розподіл навантаження, а не висока доступність. Головний екземпляр
> залишається єдиною точкою відмови для ingress, файлового сховища та редактора.

## Поширені workflow

**Перше налаштування:**

```bash
./run.sh          # development — creates .env from .env.example and generates SECRET_KEY/ENCRYPTION_KEY automatically
# or
./deploy.sh       # production — same automatic .env and key generation
```

Для попередньо зібраного образу `docker run` спершу згенеруйте ключі вручну (див. розділ **Prebuilt Image** вище).

**Оновлення production після зміни коду:**

```bash
git pull
./deploy.sh       # rebuilds images, zero-downtime swap
```

**Перегляд логів production:**

```bash
./deploy.sh --logs
```

**Зупинка сервісів production:**

```bash
./deploy.sh --down
```
