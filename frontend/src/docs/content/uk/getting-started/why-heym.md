# Чому Heym

Heym — це інфраструктура для запуску та керування AI-агентами у production. Один self-hosted runtime покриває кожен етап життєвого циклу агента.

Прототипу агента потрібні модель, prompt і кілька інструментів. Production-агенту також потрібні triggers і повторні спроби, збережений стан, коли він зупиняється для людини, запис кожного виклику моделі та інструменту, вартість кожного запуску, тести перед випуском змін і чіткі обмеження на те, що він може робити самостійно. Heym зберігає все це в одному місці, тож система, яку Ви проєктуєте на canvas, — це та сама система, яка виконується. Створюйте агентні системи, а потім запускайте їх упевнено.

## Один Runtime для життєвого циклу агента

| Етап | Що дає Вам Heym |
|---|---|
| **Build** | Компонуйте агентів і детерміновані кроки на canvas, генеруйте їх за допомогою [AI Assistant](../reference/ai-assistant.md) або починайте з [Templates](../tabs/templates-tab.md) і портативних skills. |
| **Orchestrate** | Координуйте агентів, [sub-agents](../reference/agent-architecture.md), coding agents, RAG, автоматизацію браузера та інструменти з явним потоком даних і [паралельним виконанням](../reference/parallel-execution.md). |
| **Run** | Запускайте runs із [webhooks](../reference/webhooks.md), розкладів і подієвих [triggers](../reference/triggers.md), з повторними спробами для кожного вузла, [обробкою помилок](../nodes/error-handler-node.md) і [розподілом навантаження](../reference/cluster.md) між інстансами. |
| **Observe** | Досліджуйте кожне виконання через [history](../reference/execution-history.md), [LLM traces](../tabs/traces-tab.md), вартість кожного запуску в USD, live runs на canvas, [analytics](../tabs/analytics-tab.md), [alerts](../tabs/alerts-tab.md) і експорт [OpenTelemetry](../reference/opentelemetry.md). |
| **Evaluate** | Тестуйте prompts і моделі щодо очікуваних результатів у [Evals](../tabs/evals-tab.md) з оцінюванням LLM-as-Judge і порівнянням моделей пліч-о-пліч. |
| **Control** | Тримайте людей під контролем за допомогою [review checkpoints](../reference/human-in-the-loop.md) і [guardrails](../reference/guardrails.md), а також керуйте доступом із зашифрованими [credentials](../reference/credentials.md), [teams](../reference/teams.md), [single sign-on](../reference/sso.md) і [audit trail](../reference/audit.md). |
| **Expose** | Надавайте workflows через REST і [SSE](../reference/sse-streaming.md), як інструменти [MCP](../tabs/mcp-tab.md), як чат-інтерфейси [Portal](../reference/portal.md) і як віджети [dashboard](../tabs/dashboard-tab.md). |

## Build

### AI Assistant: створюйте Workflows природною мовою

[AI Assistant](../reference/ai-assistant.md) — це чат-панель усередині редактора workflow. Опишіть, що Ви хочете, наприклад "create a workflow that takes user input, searches my knowledge base, and replies using GPT-4o", і асистент генерує вузли та зв'язки, які одразу застосовуються до canvas.

- Використовує Ваш власний LLM credential (будь-яка підтримувана модель)
- Підтримує **голосове введення** для проєктування workflow без рук
- Автоматично застосовує валідний workflow JSON з відповіді AI до canvas
- Стрімить відповіді в реальному часі

Асистент працює безпосередньо в редакторі та стрімить вузли на canvas у реальному часі, а все, що він генерує, залишається редагованим, як вузли, які Ви розмістили вручну.

### Skills System

Skills — це портативні набори можливостей, файл інструкцій `SKILL.md` плюс опціональні Python-скрипти, які можна додати до будь-якого Agent node.

- Інструкції skill додаються на початок system prompt агента
- Python-файли в skill стають викликаними інструментами
- Skills можна повторно використовувати між workflows і ділитися ними як `.zip`-архівами

Це аналогічно до того, як дати Вашому агенту посадову інструкцію та набір інструментів одним додаванням.

### Workflow Analyzer: зворотний зв'язок з урахуванням запусків

Панель [Workflow Analysis](../reference/workflow-analysis.md) — це вбудований у редактор інструмент документації та зворотного зв'язку, що враховує запуски. Натисніть **Analyze**, виберіть LLM credential і модель, і Heym згенерує редагований Markdown-звіт для поточного workflow.

На відміну від статичної нотатки, аналізатор спершу запускає workflow, коли це можливо, і включає результат виконання в prompt. Звіт охоплює сфери покращення, призначення workflow та покрокове пояснення того, що роблять вузли. Коли звіт уже існує, **Reanalyze** стрімить окремий попередній перегляд, щоб Ви могли прийняти нову версію або зберегти поточний спільний документ.

## Orchestrate

### Вбудовані вузли LLM та Agent

[Agent Node](../nodes/agent-node.md) від Heym запускає тісно інтегрований цикл виклику інструментів із вбудованими інструментами Python, з'єднаннями MCP та портативною системою skills, усе розроблено для production-агентів.

Звичайний [LLM node](../nodes/llm-node.md) від Heym також виходить за межі одного кроку prompt-response. Для підтримуваних OpenAI та OpenAI-сумісних endpoints він може перемикатися в **режим Batch API**, тож один вузол надсилає масив prompts у дешевшому провайдер-нативному batch-запиті. Після цього canvas відкриває окрему гілку `batchStatus`, яка спрацьовує, коли batch проходить через такі стани, як `pending`, `processing` та `completed`.

Це означає, що LLM node може робити дві речі одночасно:

- Виконувати основний batch-запит і повертати фінальні результати для кожного елемента на звичайній гілці
- Запускати логіку сповіщень або логування на кожному значущому оновленні статусу batch, не перетворюючи flow на власний цикл опитування

Batch-виконання є першокласним примітивом LLM workflow, з перевірками можливостей провайдера та моделі в UI вузла.

**Agent Node** є ядром оркестрації агентів у Heym:

- **Tool calling** – Агент ітерує виклики інструментів у циклі, доки не видасть фінальну відповідь
- **Python tools** – Визначайте власні інструменти inline повноцінним Python; агент викликає їх під час виконання
- **MCP connections** – Підключайтеся до будь-якого сервера [Model Context Protocol](https://modelcontextprotocol.io/) (stdio або SSE), і агент автоматично отримує всі його інструменти
- **Skills** – Перетягніть файл `.zip` або `.md` на агента, щоб розширити його системний контекст і додати Python-інструменти
- **Sub-workflow calls** – Агент може викликати інші workflows Heym як інструменти, компонуючи складну поведінку без кастомного коду

Дивіться [Agent Node](../nodes/agent-node.md) та [Agent Architecture](../reference/agent-architecture.md) для повного довідника.

### Мультиагентна оркестрація

Heym підтримує **патерн orchestrator** із першокласними візуальними примітивами:

- Один агент виступає як **orchestrator** (`isOrchestrator: true`) і отримує інструмент `call_sub_agent`
- Він делегує завдання іменованим **sub-agents** на тому самому canvas
- Sub-agents можуть самі викликати інших агентів або sub-workflows (максимальна глибина: 5)
- **Паралельне виконання**: Коли orchestrator викликає кілька sub-agents за один хід, вони виконуються паралельно для швидших результатів

Це уможливлює такі архітектури, як агент планування, що маршрутизує роботу до дослідника, програміста та узагальнювача, усе зібрано візуально без кастомного коду оркестрації.

Дивіться [Agent Architecture](../reference/agent-architecture.md) для деталей виконання.

### Coding Agents як вузли Workflow

Heym постачає два вузли, які запускають справжнього coding agent як крок workflow, а не chat completion:

- **[Codex Node](../nodes/codex-node.md)** – Запускає OpenAI Codex CLI в ізольованому workspace Heym проти репозиторію GitHub. Підтримує **Sign in with ChatGPT** (PKCE OAuth на вашій підписці Plus/Pro, без витрат API за кожен token) або access token, клонує репозиторій, дозволяє Codex редагувати код і повертає `summary`, `diff`, `changedFiles` та чернетку `pullRequestUrl`.
- **[OpenCode Go Node](../nodes/opencode-go-node.md)** – Той самий workflow з репозиторієм через провайдер-агностичний шлюз OpenCode (Kimi, DeepSeek, Qwen та інші), що виконується в **посиленому одноразовому контейнері**: усі capabilities відкинуто, read-only root, обмеження pid/memory/CPU. GitHub token залишається поза sandbox: Heym виконує кожну операцію git і GitHub на стороні хоста, тож згенерований код не може викрасти push-credentials.

Це означає, що workflow може тріажити баг із webhook, передати репозиторій coding agent, дочекатися чернетки PR і опублікувати посилання в Slack, повністю автоматизовано, з обмеженнями ресурсів, що налаштовуються для кожного розгортання.

### Вбудований RAG Pipeline

Heym включає [RAG / Vector Store Node](../nodes/rag-node.md) та керовану вкладку [Vectorstores](../tabs/vectorstores-tab.md). Ви можете:

- Вибрати свій vector backend: **Qdrant** (зовнішній сервер) або **Postgres (pgvector)**, який зберігає vectors у власній базі даних Heym без потреби запускати додатковий сервіс
- Вставляти документи у vector store безпосередньо з вузла workflow
- Виконувати семантичний пошук і передавати результати в LLM або Agent node
- Посилатися на результати виразами на кшталт `$ragNode.results.map("item.payload.content").join("\n\n")`

У Heym RAG — це два вузли з повним контролем над embeddings і retrieval.

### Автоматизація браузера з Playwright

[Playwright node](../nodes/playwright-node.md) — це first-party автоматизація браузера на canvas.

- **Режим Steps** – Візуально компонуйте дії navigate, click, type, fill, screenshot, extract та scroll
- **AI steps з auto-heal** – Опишіть дію природною мовою, і LLM згенерує дії Playwright; невдалі селектори можуть виправлятися автоматично, а згенеровані кроки можна кешувати, щоб пропускати майбутні виклики LLM
- **Режим Run Code** – Перемкніть вузол на повний Playwright Python для складних flow (вимкнено за замовчуванням; виконується в посиленому sandbox Heym, коли увімкнено)
- **Автентифіковані сесії** – Відновлюйте cookies/`storageState` перед запуском, перевіряйте вхід через перевірку селектора та переходьте до скриптових кроків входу як запасного варіанта
- **Network capture** – За бажанням збирайте JSON-відповіді, headers, cookies та сховище браузера разом із результатами

Heym ставиться до браузера як до звичайного вузла з тими самими виразами, credentials та обробкою помилок, як і до всього іншого.

### Expression DSL

[Expression DSL](../reference/expression-dsl.md) від Heym надає чистий і потужний синтаксис для посилання на дані вузлів вище за потоком:

- `$input.text` – дані вузла Input
- `$nodeName.field` – поле виводу будь-якого вузла вище за потоком
- `$global.variableName` – постійні глобальні змінні
- Помічники для масивів: `.first()`, `.map("field")`, `.join("\n")`

Expression працюють у кожному рядковому полі, зокрема в prompt, HTTP-заголовках, умовах і значеннях set, тож дані переходять між кроками явно. DSL балансує між потужністю та читабельністю, не вимагаючи повного знання JavaScript.

## Run

### Triggers, Retries та Error Paths

Workflow може запускатися з багатьох місць. Вузли [Input](../nodes/input-node.md) отримують HTTP [webhooks](../reference/webhooks.md), [Cron](../nodes/cron-node.md) запускається за розкладом, а event [triggers](../reference/triggers.md) запускають виконання з Telegram, Discord, Slack, поштових скриньок IMAP, потоків WebSocket, черг RabbitMQ, завантажень файлів і подій платформи Heym.

Збої обробляються всередині графа. Будь-який вузол може повторити спробу в разі збою із заданою кількістю спроб і очікуванням між ними, кожна спроба записується в [execution history](../reference/execution-history.md), а вузол [Error Handler](../nodes/error-handler-node.md) запускається автоматично, коли вузол зазнає збою, тож відновлення є частиною самого workflow.

### Паралельне виконання DAG

Виконавець workflow у Heym використовує планувальник на основі спрямованого ациклічного графа (DAG). Незалежні вузли запускаються паралельно автоматично, без потреби в налаштуванні.

- Вузли на одному рівні залежностей надсилаються одночасно до пулу потоків (`max_workers=8`)
- Щойно будь-який вузол завершується, його нижчі вузли ставляться в чергу
- [Merge Node](../nodes/merge-node.md) об'єднує результати паралельних гілок
- Кілька виконань workflow виконуються одночасно; кожне виконання повністю ізольоване

Паралелізм є типовою поведінкою, визначеною структурою графа.

Див. [Parallel Execution](../reference/parallel-execution.md).

### Масштабування між інстансами

Спрямуйте другий інстанс Heym на ту саму базу даних PostgreSQL, і він приєднається як worker. Фонові виконання розподіляються між інстансами за вагами, які Ви задаєте, один обраний лідер підтримує розклади, оцінювання алертів і відновлення після збоїв через failover, а кожне виконання фіксує інстанс, який його виконав. Див. [Load Distribution](../reference/cluster.md).

### Agentic Kanban Board

Вкладка [Board](../tabs/board-tab.md) — це вбудована Kanban-дошка, де самі колонки виконують workflow. Картка — це постійне agentic-завдання, яке несе контекст, історію розмови, стан виконання, виводи та виконання workflow.

- **Ланцюжки workflow колонок** – Переміщення картки в колонку запускає ланцюжок workflow цієї колонки; **Agentic Kanban Model** (Ваш credential + модель) зіставляє вміст картки з входами workflow і перетворює виводи назад у читабельний текст
- **Вкладення карток** – Перетягніть файли на картку; документи витягуються в текст, а зображення передаються моделям із підтримкою vision перед кожним виконанням
- **Живе полотно виконання** – Відкрийте активне виконання всередині картки та спостерігайте, як воно виконується на справжньому полотні workflow, вузол за вузлом
- **Спільний доступ для команди** – Діліться дошками з користувачами або командами з правами читання/запису; ланцюжки на спільних дошках виконуються з credential власника, тож співробітникам ніколи не потрібні власні
- **Видимість збоїв** – Невдалі картки показують індикатор історії помилок, а подальші виконання можуть зупинятися в очікуванні коментарів

Дошка є нативною поверхнею платформи: картки, workflow, credential і живі виконання — усе в одному місці.

### Heym Drive: вбудоване сховище файлів

Вкладка [Drive](../tabs/drive-tab.md) — це файлове сховище, вбудоване в платформу. Файли, створені skills і workflow (PDF, DOCX, CSV, зображення), потрапляють туди автоматично, а вкладення карток дошки також зберігаються там.

- **Посилання для спільного доступу** – Публічні або захищені паролем (Basic Auth) посилання для завантаження з опційним терміном дії та обмеженнями на максимальну кількість завантажень
- **Спільний доступ для команди** – Діліться файлами лише для читання зі своїми командами та видаляйте всі спільні доступи команди однією дією
- **Масові дії** – Множинний вибір із діапазонами через shift-click, пакування вибраного в одне ZIP-завантаження або застосування одного налаштування спільного доступу/пароля/видалення до багатьох файлів одразу
- **Доступ агента** – Skills можуть увімкнути читання файлів Drive, тож агент може працювати з документами, які створили Ви або інші workflow

Згенеровані артефакти отримують постійне місце для спільного доступу всередині платформи.

## Observe

### LLM Traces

Вкладка [Traces](../tabs/traces-tab.md) забезпечує повну спостережуваність кожного виклику LLM:

- Payload запитів і відповідей
- Час на виклик: `llm_ms`, `tools_ms`, `mcp_list_ms`
- Назви викликів інструментів, аргументи та результати
- Skills, передані моделі

Система traces створена спеціально для налагодження agentic-поведінки, з повними payload запитів і відповідей та часом на виклик.

### Відстеження витрат на LLM Token

Кожен виклик LLM у Heym автоматично оцінюється за вартістю. [Вкладка Traces](../tabs/traces-tab.md) показує кількість вхідних і вихідних token для кожного trace разом із вартістю в USD у реальному часі, розрахованою на основі синхронізованої таблиці цін.

- **Вартість на trace** – Вхідні token, вихідні token і загальна сума в USD, що відображається в кожному рядку trace
- **Аналітика витрат** – KPI-картки та графік витрат за моделями оновлюються відповідно до вибраного діапазону часу (1h / 24h / 7d / 30d / All)
- **Таблиця витрат на LLM** – Системна таблиця у [вкладці DataTable](../tabs/datatable-tab.md) наповнюється з Helicone кожні 24 години; Ви можете перевизначити ціни або додати власні рядки для моделей, яких ще немає в списку
- **Попередження про відсутню ціну** – Для trace моделей без запису про ціну відображається вбудоване попередження з прямим посиланням на таблицю витрат

Кожне виконання має власну вартість у USD, розподілену за моделями.

### Відкриття production-запусків на живому Canvas

Production workflow залишається доступним для перегляду після запуску поза редактором. Відкрийте будь-який запис зі статусом **Running** у будь-якому з діалогів History або відкрийте активний запуск у картці Agentic Kanban, і Heym приєднає звичайний редактор workflow до саме цього виконання.

- Вузли, які вже завершилися, одразу відображаються зі своїми результатами
- Поточний вузол і наступні вузли в очікуванні продовжують пульсувати в міру просування виконання
- Панель Debug отримує ті самі інкрементальні результати вузлів, що й запуск, розпочатий з canvas
- Фінальний вивід і підсвічування виконання з'являються без polling і без запуску дубльованого виконання
- Закриття редактора лише від'єднує спостерігача; воно ніколи не скасовує production workflow

Спостерігач використовує SSE на основі знімка виконання між воркерами, тому він працює для webhook, schedule, chat, MCP, integration і Board trigger, навіть коли запуском володіє інший backend-воркер.

### OpenTelemetry, аналітика та сповіщення

Heym створює [OpenTelemetry](../reference/opentelemetry.md) span для кожного запуску workflow, виконання вузла та виклику інструмента Agent, експортуючи їх через OTLP/HTTP до Jaeger, Grafana Tempo, Honeycomb, Datadog або будь-якого іншого сумісного backend.

[Вкладка Analytics](../tabs/analytics-tab.md) відстежує кількість запусків, відсоток успішних виконань, тривалість і тенденції для кожного workflow. [Alerts](../tabs/alerts-tab.md) стежать за кількістю помилок, тривалістю запуску, витратами token або USD та обсягом виконань за часовий проміжок, а потім запускають обраний Вами notify workflow, тож сповіщення надходить у Slack, email, Telegram або будь-куди, де це може зробити вузол.

## Evaluate

### Вбудовані Evals

[Вкладка Evals](../tabs/evals-tab.md) дозволяє Вам визначати набори тестів і запускати їх проти Ваших agent workflow:

- Створюйте тестові випадки з вхідними даними та очікуваними вихідними даними або генеруйте їх із prompt набору
- Запускайте один набір проти кількох моделей і порівнюйте їхні вихідні дані пліч-о-пліч
- Оцінюйте за допомогою Exact Match, Contains або LLM-as-Judge з незалежною моделлю-суддею
- Переглядайте pass/fail, фактичне проти очікуваного та історію запусків

Змініть prompt або модель, повторно запустіть набір і порівняйте результати, перш ніж зміна потрапить у production.

## Control

### Human-in-the-Loop (HITL)

Heym має вбудовану систему [Human-in-the-Loop](../reference/human-in-the-loop.md), яка дозволяє agent призупиняти виконання, запитувати перевірку людиною та відновлювати роботу з того самого місця, де він зупинився.

- **Контрольні точки Agent** – Увімкніть `hitlEnabled` на будь-якому вузлі Agent, щоб надати йому інструмент `request_human_review`. Agent вирішує, коли рішення потребує нагляду людини, і викликає інструмент із резюме та чернеткою.
- **Публічні URL для перевірки** – Кожен запит на перевірку генерує захищене одноразове посилання за адресою `/review/{token}` (TTL 168 годин). Рецензенти можуть **прийняти**, **відредагувати й продовжити** або **відхилити** без входу в систему.
- **Знімки виконання** – Workflow заморожує свій повний стан (історію розмови, змінні, результати інструментів), тож він відновлюється точно з того місця, де зупинився, після відповіді рецензента.
- **Гілка сповіщень** – Необов'язковий вихідний порт `review` дозволяє Вам під'єднати потік сповіщень (Slack, email, webhook), який спрацьовує, коли запитується перевірка.
- **Політики схвалення інструментів MCP** – Письмові настанови HITL інтерпретуються в області схвалення (`always` / `once` / `never`), тож agent може автоматично схвалювати низькоризикові інструменти та ескалувати високоризикові.
- **Кілька контрольних точок** – Один запуск agent може зупинятися для перевірки кілька разів; кожна контрольна точка є незалежною.

Публічні URL для перевірки, редагування й продовження, розгалуження сповіщень і відновлення на основі знімків – усе це працює з однієї контрольної точки agent.

Повний довідник дивіться в розділі [Human-in-the-Loop](../reference/human-in-the-loop.md).

### LLM Guardrails

Heym має вбудовані [Guardrails](../reference/guardrails.md) як на вузлах [LLM](../nodes/llm-node.md), так і на вузлах [Agent](../nodes/agent-node.md), тож Ви можете блокувати небезпечний вміст, перш ніж відповідь моделі досягне наступних кроків.

- **Перемикач безпеки на рівні вузла** – Увімкніть guardrails безпосередньо на вузлі, який генерує або обробляє контент, орієнтований на користувача
- **Широке покриття політик** – Блокування насильства, мови ворожнечі, сексуального контенту, NSFW/нецензурної лексики, домагань, незаконної діяльності, запитів персональних даних і спроб prompt injection
- **Багатомовне виявлення** – Застосовуйте ті самі правила безпеки для турецької, англійської, арабської, іспанської та інших мов
- **Рідний для workflow fallback** – Коли повідомлення заблоковано, вузол викидає типізовану помилку workflow, яку Ви можете спрямувати через [Error Handler](../nodes/error-handler-node.md)

Політика безпеки міститься безпосередньо в конфігурації LLM і Agent та безпосередньо підключається до розгалуження workflow і обробки помилок.

### Доступ, облікові дані та аудит

Агенти діють із реальними обліковими даними, тому доступ є частиною governance. [Облікові дані](../reference/credentials.md) шифруються під час зберігання, маскуються після створення та можуть надаватися користувачам або [командам](../reference/teams.md), а команди також спільно використовують workflows, змінні, vector stores і файли Drive. [Single sign-on](../reference/sso.md) підключає будь-якого постачальника OpenID Connect, зокрема Okta, Entra ID, Keycloak, Auth0 і Google. [Журнал аудиту](../reference/audit.md) фіксує кожну дію, що стосується безпеки, разом з її виконавцем, ціллю та результатом, і транслюється разом із логами Вашого контейнера до log collector або SIEM, який Ви вже використовуєте.

### Self-Hosted, Ви володієте своїми даними

Heym працює на Вашій інфраструктурі. Workflows, облікові дані, історія виконань і трейси зберігаються у Вашій власній базі даних, а виклики моделей ідуть із Ваших серверів до обраного Вами постачальника або до моделі, яку Ви розміщуєте самостійно через Ollama чи vLLM. Для агентів, які обробляють конфіденційні документи, дані клієнтів або пропрієтарні бази знань, це часто є жорсткою вимогою.

Heym ліцензовано за **MIT License з умовою Commons Clause**. Вихідний код є source-available: Ви можете вільно використовувати, змінювати та розміщувати його самостійно. Commons Clause обмежує продаж програмного забезпечення, зокрема надання платного хостингу або консалтингових/підтримувальних послуг, цінність яких суттєво походить від Heym. Для комерційного ліцензування, enterprise-розгортань або професійної підтримки звертайтеся на [enterprise@heym.run](mailto:enterprise@heym.run).

## Expose

### APIs та Streaming

Workflows можна викликати через HTTP за адресою `/api/workflows/{workflow_id}/execute`, яка повертає JSON, та за адресою `/api/workflows/{workflow_id}/execute/stream`, яка транслює події вузлів як Server-Sent Events під час виконання. Обидві використовують автентифікацію на рівні workflow, обмеження швидкості та кешування відповідей. Дивіться [Webhooks](../reference/webhooks.md) і [SSE Streaming](../reference/sse-streaming.md).

### Інтеграція з MCP (Model Context Protocol)

Heym має нативну підтримку [MCP](../tabs/mcp-tab.md) з обох сторін:

- **Як клієнт**: вузли Agent підключаються до зовнішніх MCP-серверів (Filesystem, Browserbase, власні інструменти) через stdio або SSE та автоматично використовують їхні інструменти
- **Як сервер**: workflows з увімкненим MCP стають інструментами на сервері за замовчуванням за адресою `/api/mcp/sse` або на іменованих серверах із власним URL та API key, тож Claude Desktop, Cursor та інші MCP-клієнти можуть викликати Ваші workflows Heym напряму

Агенти можуть використовувати кілька MCP-серверів одночасно, і будь-який workflow може стати інструментом для зовнішнього MCP-клієнта.

### Portal: публікуйте workflows як чат-інтерфейси

Функція [Portal](../reference/portal.md) перетворює будь-який workflow на публічний чат-інтерфейс за адресою `/chat/{slug}`:

- Необов'язкова автентифікація з обліковими даними для кожного користувача
- Потокове виконання (прогрес вузлів у реальному часі)
- Підтримка завантаження файлів
- Історія багатоходових розмов

Команди випускають внутрішні інструменти, чат-боти для клієнтів і AI-форми з одного workflow та URL, без написання frontend-коду.

### Дашборди на основі workflows

Вкладка [Dashboard](../tabs/dashboard-tab.md) — це створена користувачем поверхня звітності, де кожен віджет діаграми працює на власному прихованому workflow Heym. Віджет може викликати APIs, робити запити до BigQuery, шукати в RAG/vector stores, виконувати кроки LLM, трансформувати рядки та завершуватися [вузлом Chart Output](../nodes/chart-output-node.md). Ви можете створювати віджети вручну, генерувати їх за допомогою AI, доопрацьовувати пізніше, кешувати результати та візуально переставляти сітку.

Zapier і Make.com не документують експорт OpenTelemetry своїх виконань Workflow/сценаріїв станом на червень 2026 року. ¹⁷ n8n документує панель Insights для метрик виконання в продакшені, Zapier документує Zap History плюс Task Usage, а Make.com документує Scenario History; це поверхні моніторингу/історії, а не кастомні віджети панелі, підкріплені довільною логікою Workflow, як вкладка Dashboard у Heym. ¹⁸ Heym Workflow Analyzer запускає Workflow, коли це можливо, читає результат виконання та генерує спільний редагований Markdown-звіт, що охоплює сфери покращення, призначення та покрокову поведінку. n8n документує AI Workflow Builder для створення/вдосконалення/налагодження Workflow, Zapier документує AI troubleshooting для запусків Zap із помилками, а Make.com документує історію сценаріїв плюс кроки міркування AI-агента, але їхня публічна документація не описує той самий спільний документ аналізу Workflow з урахуванням запуску. ¹⁹ [n8n All executions](https://docs.n8n.io/workflows/executions/all-executions/) перелічує запущені виконання і може завантажувати дані з попереднього виконання в редактор, тоді як [Zapier run statuses](https://help.zapier.com/hc/en-us/articles/20505304170637-Review-run-statuses-in-Zap-workflows) показує стан running у своєму редакторі. [Make Scenario History](https://help.make.com/scenario-history) документує деталі запуску та логи. Їхня публічна документація, перевірена 18 липня 2026 року, не описує точний потік Heym: відкрити довільний запуск у продакшені, що виконується, з History або Kanban-картки, відновити його поточний знімок вузла та продовжити отримувати анімацію вузлів і Debug-логи на тому самому полотні. ²⁰ Вузли Heym [Codex](../nodes/codex-node.md) і [OpenCode Go](../nodes/opencode-go-node.md) запускають справжній CLI coding-агента в ізольованому робочому просторі Heym проти репозиторію GitHub — clone, edit, produce a diff, push a branch, open a pull request — як першокласний крок Workflow. Станом на 20 липня 2026 року жоден конкурент не документує еквівалент: [OpenAI node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-langchain.openai) від n8n охоплює виклики chat/assistant API, а не coding-агента рівня репозиторію, і нативна підтримка Codex залишається запитом спільноти; власний блог Zapier документує зворотний напрямок — [Codex driving Zapier tools through Zapier MCP](https://zapier.com/blog/automate-codex-zapier-mcp/) — а не Codex як крок Zap; модулі OpenAI від Make.com надають completions/assistants/batch-дії, а не coding-агента, який клонує репозиторії та відкриває PR. ²¹ [Board tab](../tabs/board-tab.md) у Heym — це вбудована agentic Kanban-дошка, стовпці якої виконують Workflow, а картки несуть контекст, історію розмови, стан виконання та запуски. n8n ([Kanban Tool integration](https://n8n.io/integrations/kanban-tool/)), Zapier ([Kanban Tool integrations](https://zapier.com/apps/kanbantool/integrations)) і Make.com ([Kanban Tool integration](https://www.make.com/en/integrations/kanban-tool)) лише підключаються до сторонніх kanban-застосунків, як-от Kanban Tool, Wekan або NocoDB; жоден не документує вбудовану дошку, яка запускає власні Workflow, станом на 20 липня 2026 року. ²² n8n зберігає бінарні дані виконання внутрішньо (за потреби на [S3-compatible external storage](https://docs.n8n.io/hosting/scaling/external-storage/)), але не документує жодного користувацького файлового сховища з посиланнями для поширення або командним доступом, тому його позначено як limited. [Files by Zapier](https://zapier.com/apps/files-by-zapier/integrations) обробляє файли лише протягом запуску Zap, а [Storage by Zapier](https://help.zapier.com/hc/en-us/articles/8496293271053-Save-and-retrieve-data-from-Zaps) зберігає невеликі текстові значення, тому Zapier позначено як limited. [data stores](https://help.make.com/l6du-data-stores) від Make.com зберігають структуровані записи, а його [file handling](https://help.make.com/working-with-files) передає файли між застосунками без постійного вбудованого сховища, тому Make позначено як unavailable. ²³ [Playwright node](../nodes/playwright-node.md) у Heym — це першопартійна автоматизація браузера з візуальним режимом кроків, кроками, згенерованими AI, і повним режимом коду. n8n пропонує лише пакети спільноти, як-от [n8n-playwright](https://github.com/toema/n8n-playwright), із досі відкритим [запитом на функцію нативних вузлів автоматизації браузера](https://community.n8n.io/t/front-end-web-mobile-app-test-automation-nodes/129796), тому його позначено як limited. Zapier Agents можуть [переглядати та читати сторінки через веб-перегляд і розширення Chrome](https://help.zapier.com/hc/en-us/articles/29025734470925-Use-Zapier-Agents-Chrome-extension), але Zapier не документує жодного кроку скриптової автоматизації браузера, тому його позначено як limited. Make.com документує HTTP-модулі та сторонні застосунки для scraping, а не будь-який нативний модуль автоматизації браузера, станом на 20 липня 2026 року.
