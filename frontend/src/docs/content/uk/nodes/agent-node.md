# Вузол Agent

Вузол **AI Agent** — це вузол LLM із викликом інструментів. Він може запускати інструменти Python, викликати підключені вузли Canvas як інструменти, підключатися до серверів MCP, використовувати навички, за потреби діяти як оркестратор, що делегує завдання іншим вузлам Agent, викликати інші Workflow як інструменти та призупинятися для [перевірки людиною](../reference/human-in-the-loop.md).

## Огляд

| Властивість | Значення |
|----------|-------|
| Входи | 1 |
| Виходи | 1, а також додатковий `review`, коли ввімкнено HITL |
| Вихід | `$nodeLabel.text`, `$nodeLabel.fieldName` (коли ввімкнено вихід JSON) або відкладений payload HITL під час очікування перевірки |

## Основні параметри

### Облікові дані та модель

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `credentialId` | UUID | Облікові дані LLM (API key) з розділу Settings |
| `model` | string | Назва моделі (наприклад, `gpt-4o`, `gemini-2.5-flash-lite`) |
| `fallbackCredentialId` | UUID (необов'язково) | Резервні облікові дані на випадок збою основних |
| `fallbackModel` | string (необов'язково) | Резервна модель на випадок збою основної |

Додайте облікові дані на вкладці [Облікові дані](../tabs/credentials-tab.md). Список моделей завантажується з вибраних облікових даних. Якщо основні облікові дані або модель повертають помилку, вузол автоматично повторює спробу з резервними обліковими даними та моделлю, перш ніж завершитися з помилкою.

### Prompt

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `systemInstruction` | string | Системний prompt для AI. Підтримує [вирази](../reference/expression-dsl.md). |
| `userMessage` | string | Повідомлення/prompt користувача. За замовчуванням: `$input.text` |
| `jsonOutputEnabled` | boolean | Структурований вихід JSON |
| `jsonOutputSchema` | string | JSON Schema для структурованого виходу |
| `extraBodyEnabled` | boolean | Надсилати специфічні для провайдера параметри запиту (за замовчуванням: `false`) |
| `extraBody` | string | Об'єкт JSON, що додається до кожного API-запиту, який виконує агент |

Використовуйте `$input.text`, `$nodeName.field` та інший синтаксис [Expression DSL](../reference/expression-dsl.md).

### Моделі міркування (o1, o3)

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `temperature` | number | 0.0–2.0 (за замовчуванням: 0.7), для стандартних моделей |
| `reasoningEffort` | `"low"` \| `"medium"` \| `"high"` | Глибина міркування для моделей міркування |

Під час використання моделі міркування (наприклад, o1, o3) в інтерфейсі відображається **Reasoning Effort** замість Temperature. Для стандартних моделей **Temperature** керує креативністю.

**Приклад виходу JSON:** Коли потрібні структуровані дані від агента (наприклад, класифікація, вилучення), увімкніть вихід JSON і надайте схему. Агент повертає JSON, що відповідає схемі; доступ до полів здійснюється за назвою на виході вузла:

```json
{
  "jsonOutputEnabled": true,
  "jsonOutputSchema": "{ \"type\": \"object\", \"properties\": { \"status\": { \"type\": \"string\", \"enum\": [\"APPROPRIATE\", \"INAPPROPRIATE\"] }, \"reason\": { \"type\": \"string\" } }, \"required\": [\"status\", \"reason\"] }"
}
```

Нижчі вузли можуть використовувати `$agentLabel.status`, `$agentLabel.reason` тощо. Поведінка така сама, як у виході JSON [вузла LLM](../nodes/llm-node.md).

## Перевірка людиною (HITL)

Використовуйте HITL, коли агенту може знадобитися схвалення в певні моменти перед важливими діями.

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `hitlEnabled` | boolean | Додає контрольні точки перевірки людиною до агента |
| `hitlSummary` | string | Настанови щодо схвалення, які вказують агенту, коли потрібна перевірка людиною |

Коли ввімкнено HITL, агент отримує інструмент `request_human_review`. Використовуйте системний prompt і
це поле настанов, щоб пояснити, які виклики інструментів, субагенти, суб-Workflow, дії MCP, навички
або побічні ефекти потребують схвалення. Агент може викликати цей інструмент лише за потреби, зокрема кілька
разів за один запуск.

Підсумок для рецензента на публічній сторінці генерується з запиту на перевірку агента під
час виконання. Якщо агент не надає підсумок явно, Heym виводить його з Markdown-тексту
перевірки.

Для інструментів MCP Heym просить модель інтерпретувати ваші письмові інструкції HITL як одну з трьох
областей застосування: `always`, `once` або `never`. Це означає, що вільне формулювання, як-от «для кожного виклику», «лише
один раз» або «ніколи не запитувати», нормалізується перед застосуванням обмежень під час виконання.

Кожна контрольна точка HITL створює одноразове посилання для публічної перевірки за адресою `/review/{token}`. Рецензент може:

- **Accept** — прийняти оригінальний Markdown-текст перевірки
- **Edit & Continue** — продовжити зі зміненим Markdown
- **Refuse** — відхилити та продовжити з `text: ""`

Коли ввімкнено HITL, вузол також надає вихідний порт `review` на Canvas. Підключіть цю гілку до Slack, електронної пошти або інших вузлів сповіщень, якщо потрібно транслювати URL перевірки та підсумок щойно виконання призупиниться.

Виконання переходить у стан `pending`, доки рецензент не відповість. Текст перевірки — це єдиний Markdown-текст, а відкладений payload також містить текст посилання для поширення для зовнішньої передачі. Вузли на гілці `review` запускаються негайно після створення паузи; звичайний шлях виходу продовжується лише після схвалення. Після схвалення Heym відновлює роботу зі збереженого знімка виконання, і агент продовжує зі схваленим контекстом. Якщо наступний крок також потребує схвалення, агент може створити ще одну контрольну точку HITL. Див. [Human-in-the-Loop](../reference/human-in-the-loop.md) щодо форми payload, поведінки URL перевірки та семантики відновлення.

HITL доступний лише для виходу агента в текстовому режимі. У v1 його не можна поєднувати з `jsonOutputEnabled`.
## Режим оркестратора

Коли його ввімкнено, агент може делегувати завдання іншим вузлам-агентам у workflow. Якщо **режим оркестратора вимкнено**, агент **не може створювати зв'язки агент→агент** на canvas.

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `isOrchestrator` | boolean | Коли `true`, агент отримує інструмент `call_sub_agent` |
| `subAgentLabels` | string[] | Мітки вузлів-агентів, які цей оркестратор може викликати |

**Субагенти** мають використовувати `$input.text` у своєму User Message, щоб отримувати prompt від оркестратора.

Коли оркестратор викликає кілька субагентів за один хід, вони виконуються паралельно. Докладніше див. [Agent Architecture](../reference/agent-architecture.md).

## Під-workflow

Коли налаштовано, агент отримує інструмент `call_sub_workflow` для виконання інших workflow.

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `subWorkflowIds` | string[] | Ідентифікатори workflow, які цей агент може викликати як інструменти |

Виберіть workflow у розділі Sub-Workflows конфігурації агента. Агент викликатиме їх із `workflow_id` та `inputs` (об'єкт, що відповідає вхідним полям цільового workflow). Максимальна глибина: 5 вкладених викликів під-workflow.

## Інструменти вузлів Canvas

Ви можете під'єднати підтримуваний вузол workflow до ручки **tools** агента, щоб агент міг викликати цей вузол під час виконання. Це перетворює наявні дії та перетворення на canvas на інструменти, які можна викликати, без написання Python.

Використовуйте інструменти вузлів canvas, коли потрібно, щоб агент вирішував, коли запускати налаштований вузол, зберігаючи при цьому облікові дані, статичні поля та специфічні для workflow налаштування в інтерфейсі вузла.

### Поля, які надає агент

Поля на під'єднаному вузлі-інструменті можна позначити значком бота. Позначені поля стають обов'язковими параметрами інструмента, які агент має надати під час виклику вузла. Непозначені поля залишаються фіксованими та зчитуються з конфігурації вузла.

Наприклад:

- Під'єднайте вузол Slack до агента як інструмент
- Залиште облікові дані фіксованими у вузлі Slack
- Позначте `message` як поле, яке надає агент
- Агент отримує інструмент Slack, у якому він надає лише повідомлення під час виконання

Якщо вузол не під'єднано до агента як інструмент, значок бота приховано, і вузол поводиться як звичайний крок workflow.

### Поведінка під час виконання

Коли агент викликає інструмент вузла canvas, Heym тимчасово об'єднує надані агентом аргументи з даними цього вузла, виконує вузол, повертає вихідні дані вузла агенту, а потім відновлює початкову конфігурацію вузла. Вузли-інструменти не запускаються як звичайні кроки workflow через стандартне планування; вони виконуються лише тоді, коли їх викликає агент.

Інструменти вузлів canvas корисні з інтеграційними вузлами, такими як Slack, Telegram, HTTP, Send Email, та вузлами перетворення даних, такими як [Set](./set-node.md). Вузли Trigger, вузли керування потоком та термінальні мапери вихідних даних ([JSON output mapper](./json-output-mapper-node.md), [HTML output mapper](./html-output-mapper-node.md)) не можна використовувати як інструменти агента.

## Інструменти Python

Визначте власні інструменти, які агент може викликати. Кожен інструмент має:

| Поле | Тип | Опис |
|-------|------|-------------|
| `name` | string | Назва інструмента (наприклад, `count_characters`) |
| `description` | string | Опис для LLM |
| `parameters` | JSON Schema | Схема function-calling OpenAI (формат об'єкта) |
| `code` | string | Код функції Python |

**Parameters** має бути JSON-об'єктом, а не рядком:

```json
{
  "type": "object",
  "properties": {
    "text": { "type": "string", "description": "Text to count" }
  },
  "required": ["text"]
}
```

**Приклад інструмента:**

```python
def count_characters(text: str) -> int:
    return len(text)
```

> **Пісочниця.** Інструменти Python за замовчуванням виконуються як недовірений код у посиленому ізольованому контейнері Docker (без мережі, без Docker-сокета, файлова система лише для читання, без прав root). Імпорт обмежено списком дозволених безпечних модулів стандартної бібліотеки. Див. [Security → Python Tool Sandbox](../reference/security.md#python-tool-sandbox) щодо налаштування (`HEYM_PYTHON_TOOL_SANDBOX`).

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `toolTimeoutSeconds` | number | Максимальна кількість секунд на одне виконання інструмента (за замовчуванням: 30) |
| `requestTimeoutSeconds` | number | Максимальна кількість секунд очікування кожної відповіді моделі до тайм-ауту (за замовчуванням: 60). Збільште це значення для повільних або self-hosted провайдерів (LiteLLM, vLLM, локальні моделі) та тривалих багатокрокових запусків. |
## Підключення MCP

Підключайтеся до серверів [Model Context Protocol](https://modelcontextprotocol.io/), щоб надати агенту доступ до їхніх інструментів.

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `transport` | `"stdio"` \| `"sse"` \| `"streamable_http"` | Тип підключення |
| `timeoutSeconds` | number | Час очікування для цього підключення (за замовчуванням: 30) |
| `label` | string | Необов'язкова відображувана назва |

**stdio** (локальний процес):

| Поле | Опис |
|-------|-------------|
| `command` | Команда для виконання (наприклад, `npx`) |
| `args` | Масив JSON (наприклад, `["-y", "@modelcontextprotocol/server-filesystem", "--path", "/tmp"]`) |
| `env` | Об'єкт JSON зі змінними середовища, що впроваджуються в процес (наприклад, `{"GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_..."}`) |

Більшість stdio-серверів, що використовують API-ключі, автентифікуються через змінні середовища, а не через аргументи команди. Встановлюйте `env` для кожного підключення окремо, щоб кожен вузол агента міг використовувати інші облікові дані, не змінюючи середовище хоста.

Значення `env` підтримують [Expression DSL](../reference/expression-dsl.md), тож ви можете передавати вхідні дані workflow як облікові дані замість того, щоб жорстко кодувати секрети:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "$userInput.pat" }
}
```

Вираз `$userInput.pat` обчислюється під час виконання на основі вхідних даних workflow до запуску процесу MCP. Це дозволяє приймати token з trigger або вхідного вузла, а не вбудовувати його у визначення workflow.

Приклад — GitHub MCP із жорстко закодованим token:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxxxxxxxxx" }
}
```

Приклад — GitHub MCP із динамічним token із вхідних даних workflow:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "$userInput.pat" }
}
```

Приклад — GitHub MCP з обліковими даними GitHub у Heym:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "$credentials.MyGitHubToken" }
}
```

Вбудовані облікові дані GitHub наразі орієнтовані на автентифікацію на основі PAT. Якщо вам потрібен доступ на рівні організації, використовуйте PAT із необхідними дозволами для організації/репозиторію.

Приклад — Slack MCP:

```json
{
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-slack"],
  "env": { "SLACK_BOT_TOKEN": "xoxb-...", "SLACK_TEAM_ID": "T0123456" }
}
```

**SSE** (віддалений сервер):

| Поле | Опис |
|-------|-------------|
| `url` | URL SSE endpoint. Підтримує вирази (наприклад, `$userInput.serverUrl`). |
| `headers` | Об'єкт JSON для автентифікації/власних заголовків. Значення підтримують вирази. |

**Streamable HTTP** (віддалений сервер):

| Поле | Опис |
|-------|-------------|
| `url` | URL MCP endpoint (наприклад, `https://example.com/mcp`). Підтримує вирази. |
| `headers` | Об'єкт JSON для автентифікації/власних заголовків. Значення підтримують вирази. |

## Skills

Skills — це інструкції SKILL.md разом з необов'язковими файлами Python і вбудованими ресурсами. Вони розширюють системний контекст агента та можуть додавати інструменти Python.

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `name` | string | Назва skill |
| `content` | string | Вміст SKILL.md (інструкції) |
| `timeoutSeconds` | number | Час очікування для виконання Python у skill (за замовчуванням: 30) |
| `driveFilesEnabled` | boolean | Вмикає помічник `heym_drive` під час виконання для цього skill (за замовчуванням: false) |
| `files` | array | Необов'язкові записи `{ path, content, encoding, mimeType }` (наприклад, скрипти `.py` або бінарні ресурси, збережені як base64) |

Skills можна додавати, перетягнувши файл `.zip` або `.md` у область Skills.
Після розгортання картки skill перетягніть будь-який файл на цей skill, щоб прикріпити або замінити вбудований файл, зокрема бінарні ресурси, як-от PDF-файли та зображення.
Скористайтеся кнопкою завантаження на картці skill, щоб експортувати цей skill як архів `.zip` для резервного копіювання або повторного використання в іншому workflow.

Увімкніть **Drive files** для skill лише тоді, коли його код Python потребує читання файлів із Heym Drive. Увімкнені skills отримують згенерований помічник `heym_drive.py` під час виконання та можуть викликати `list_drive_files`, `get_drive_file`, `get_drive_file_path`, `read_drive_file`, `read_drive_text` або `read_drive_base64` з ідентифікатором файлу Drive або точною назвою файлу. Пошук за назвою файлу використовує найновіший доступний збіг. Вимкнені skills не отримують цього помічника.

Кожна картка skill має чотири дії в рядку під заголовком:

| Кнопка | Опис |
|--------|-------------|
| **Edit with AI** | Відкрити Skill Builder, щоб доопрацювати skill за допомогою prompt у чаті |
| **Download** | Експортувати skill як архів `.zip` |
| **Remove** | Видалити skill із цього вузла агента |
| **History** | Відкрити історію skill, отриману з [Історії редагування](../reference/edit-history.md) |
### Історія навичок

Історія навичок **не** зберігається окремо. Вона формується зі знімків Історії редагування workflow: кожна збережена версія workflow містить повний масив `skills` вузла агента.

У діалозі Історії доступні такі дії:

- **Перегляд** попереднього знімка (SKILL.md і список файлів)
- **Редагувати** — завантажити знімок у редактор навичок без відкату всього workflow
- **AI Fine-tune** — відкрити Skill Builder із цим знімком як початковою точкою
- **Відкотити** — відновити лише цю навичку з попередньої версії (інші вузли залишаються без змін)

Історія підпорядковується тому самому 7-денному терміну зберігання, що й Історія редагування workflow. Збереження workflow після редагування навичок створює нові записи в історії.

Розділ Навички також містить **AI Build**:

- Натисніть **AI Build**, щоб створити нову навичку з prompt у чаті
- Натисніть кнопку із зірочкою на наявній навичці, щоб переглянути її за допомогою AI
- Перетягніть файли до поля введення prompt, щоб прикріпити їх до коментаря fine-tune; ці файли також зберігаються як вбудовані ресурси навички
- Модальне вікно транслює текст асистента, показуючи наживо попередній перегляд файлів `SKILL.md` і `.py`
- **Download ZIP** експортує поточний попередній перегляд без додавання його до вузла
- **Save & Add** зберігає згенеровані файли через той самий процес розбору ZIP, що використовується для ручного завантаження

Під час редагування за допомогою AI Heym надсилає до builder лише текстові файли навичок `.md` і `.py`. Бінарні та інші нередаговані вкладення зберігаються й передаються до builder як метадані шляхів, щоб згенерований код Python міг зберігати коректні відносні посилання на файли.
Виберіть прикріплений файл на правій панелі та увімкніть **Include this file in AI context**, коли AI потрібно переглянути вбудований шаблон. Текстові файли, PDF і DOCX за можливості витягуються в контекст prompt; Heym не застосовує окремого обмеження розміру вкладень Skill Builder, крім ліміту тіла запиту платформи.

## Extra Body

Деякі провайдери приймають параметри запиту, які не охоплюються стандартними полями, сумісними з OpenAI, наприклад вимкнення режиму мислення моделі. Позначте **Send extra request body** у властивостях вузла та введіть об'єкт JSON.

```json
{
  "extraBodyEnabled": true,
  "extraBody": "{ \"thinking\": { \"type\": \"disabled\" } }"
}
```

- **Вимкнено за замовчуванням.** Якщо прапорець знято, нічого додаткового не надсилається.
- Застосовується до **кожного** запиту в циклі виклику інструментів, а не лише до першого кроку, а також до спроби резервної моделі. Не застосовується до перевірок guardrail, які використовують окрему модель.
- Має бути **об'єктом** JSON. Масив, скалярне значення або некоректний текст призводять до помилки вузла `Invalid extra body JSON`, а не до його тихого відкидання.
- Вирази `$` обчислюються перед розбором. Оскільки це текстова підстановка, обчислене значення, що містить подвійну лапку або символ нового рядка, створює некоректний JSON і призводить до помилки вузла.

Ті самі поле та поведінка, що й у extra body [вузла LLM](./llm-node.md).

## Guardrails

Увімкніть **Guardrails** у властивостях вузла, щоб блокувати небезпечні повідомлення користувача до запуску агента. Повний довідник дивіться в розділі [Guardrails](../reference/guardrails.md).

## Постійна пам'ять (граф)

Необов'язковий граф знань **для кожного вузла агента**, що зберігається в базі даних. Коли його увімкнено, Heym додає Markdown-підсумок запам'ятованих сутностей і зв'язків до **системної інструкції** перед кожним запуском (лише якщо граф не порожній). Після **успішного** завершення агента фонова задача витягує нові довготривалі факти з розмови та об'єднує їх із графом.

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `persistentMemoryEnabled` | boolean | Увімкнути завантаження + фонове витягування для цього вузла canvas |

**Субагенти** зберігають **власний** граф (з ключем за ідентифікатором їхнього вузла), окремий від оркестратора.

Використовуйте рожевий елемент керування **brain** на вузлі (коли пам'ять увімкнено або показано рядок моделі), щоб відкрити редактор графа та необов'язкове **спільне використання пам'яті** (інші workflow/агенти). Повна поведінка, шляхи REST і подробиці експорту JSON: [Постійна пам'ять агента](../reference/agent-persistent-memory.md).

## Responses API і безперервність міркувань

Прапорець **Use Responses API** спрямовує виклики моделі агента через
[Responses API](https://platform.openai.com/docs/api-reference/responses) замість Chat
Completions. За замовчуванням його вимкнено.

Це найважливіше для моделі міркування, як-от `gpt-5` або серії `o`. Responses API повертає
міркування моделі разом із кожним викликом інструменту, і агент передає ці елементи міркувань
назад на наступному кроці, тож модель зберігає свій ланцюг думок упродовж багатокрокового циклу
інструментів, а не виводить його заново після кожного результату інструменту. Увесь цикл виконується
тим самим шляхом, включно з паузою та відновленням [перевірки людиною](#human-review-hitl),
[стисненням контексту](#context-compression) і фінальною відповіддю.

Сама розмова залишається в Heym. Heym надсилає повні вхідні дані на кожному кроці та передає
міркування як зашифрований блок, тож на боці провайдера між викликами нічого не зберігається.
Елементи міркувань усередині проміжку, який підсумовує стиснення контексту, відкидаються разом із
ним, оскільки зашифрований блок неможливо підсумувати.

Це працює з обліковими даними OpenAI, а також із користувацькими обліковими даними, чий шлюз
підтримує цей endpoint. З обліковими даними Google це залишається вимкненим.
## Стиснення контексту

Коли агент виконує багато ітерацій інструментів із великими результатами (вебскрейпінг, читання документів, виводи під-workflow), накопичена історія повідомлень може наблизитися до ліміту контекстного вікна моделі. Heym автоматично стискає історію розмови під час виконання, щоб запобігти переповненню контексту.

**Як це працює:**

1. Перед кожною ітерацією інструмента Heym оцінює поточну кількість токенів (~4 символи на токен).
2. Якщо оцінка перевищує **80%** контекстного вікна моделі, запускається стиснення.
3. Історія повідомлень розділяється на збережену та стиснену частини:
   - **Збережено**: системний prompt, перше повідомлення користувача, найновіше повідомлення користувача
   - **Стиснено**: усе між ними (кроки міркувань асистента, виклики інструментів, результати інструментів)
4. Середня частина підсумовується з використанням **тієї самої моделі та облікових даних** — додаткове налаштування не потрібне.
5. Стиснений підсумок замінює середню частину як єдине повідомлення асистента.

**Спостережуваність:**

Події стиснення відображаються як записи `Context compressed (N messages → summary)` у:
- Списку викликів інструментів на **панелі Debug** під час живого виконання
- Поданні деталей запуску в **Історії виконань**
- Вкладці **Трасування** як запис трасування `context.compression`

Стиснення виконується автоматично й завжди активне для вузлів Agent. Воно **не** застосовується до вузлів LLM, вкладки Chat або сесій AI Assistant.
