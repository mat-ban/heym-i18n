# Heym

Вузол **Heym** зчитує власні дані Heym: workflow, до яких Ви маєте доступ, структуру одного workflow та історію його виконань. Саме так будуються мета-workflow — інвентаризація інстансів, дайджести виконань та звіти про стан самого Heym.

## Огляд

| Властивість | Значення |
|----------|-------|
| Входи | 1 |
| Виходи | 1 |
| Операції | `listWorkflows`, `getWorkflow`, `getExecutionHistory` |
| Облікові дані | Не потрібні |

## Параметри

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `heymOperation` | Select | Яке читання виконати |
| `heymWorkflowId` | UUID | Цільовий workflow. Обов'язковий для `getWorkflow` та `getExecutionHistory`. Підтримує вирази. |
| `heymLimit` | String | Максимальна кількість рядків для повернення. **Залиште порожнім або введіть `0`, щоб повернути все** — це значення за замовчуванням. Підтримує вирази. |
| `heymStatus` | String | Необов'язковий фільтр статусу для `getExecutionHistory`. Підтримує вирази. |
| `heymSinceDays` | String | Необов'язковий період ретроспективи в днях для `getExecutionHistory`. Підтримує вирази. |

Селектор workflow — це розкривний список із пошуком, що містить усі workflow, до яких Ви маєте доступ.

## Область доступу

Результати обмежуються **власником workflow, у якому розташовано вузол**, — а не тим, хто запустив виконання. Видимий набір становить:

- workflow, якими володіє власник,
- workflow, надані власнику напряму,
- workflow, надані команді, до якої належить власник.

Обмеження за власником — саме те, що змушує вузол поводитися однаково незалежно від того, чи виконання було запущено вручну, через cron, із порталу чи подією платформи. Обмеження за суб'єктом повертало б нічого під час кожного автоматичного запуску. Це те саме правило, яке Heym уже застосовує до облікових даних і глобальних змінних.

Workflow, до якого Ви не маєте доступу, і workflow, якого не існує, видають однакове повідомлення про помилку, тож вузол не можна використовувати для зондування ідентифікаторів workflow.

## Операції

### List Workflows

Повертає кожен workflow, доступний власнику, спочатку — нещодавно оновлені.

| Вираз | Опис |
|------------|-------------|
| `$nodeLabel.workflows` | Масив підсумків workflow |
| `$nodeLabel.workflows[0].id` | UUID workflow |
| `$nodeLabel.workflows[0].name` | Назва workflow |
| `$nodeLabel.workflows[0].description` | Опис або `null` |
| `$nodeLabel.workflows[0].active` | Чи активний workflow |
| `$nodeLabel.workflows[0].folder_id` | UUID теки або `null` |
| `$nodeLabel.workflows[0].updated_at` | Мітка часу ISO останнього збереження |
| `$nodeLabel.workflows[0].node_count` | Скільки вузлів містить workflow |
| `$nodeLabel.total` | Повна кількість доступних **до** застосування обмеження |

`total` навмисно є необмеженою кількістю, тож `$inventory.total` усе одно повідомляє реальний розмір, навіть коли Ви обмежуєте кількість повернутих рядків. Очищення поля **Limit** або встановлення його в `0` повертає кожен workflow — це значення за замовчуванням.

### Get Workflow

Повертає ідентичність і структуру одного workflow.

| Вираз | Опис |
|------------|-------------|
| `$nodeLabel.id`, `$nodeLabel.name`, `$nodeLabel.description` | Ідентичність workflow |
| `$nodeLabel.active`, `$nodeLabel.folder_id`, `$nodeLabel.updated_at` | Метадані workflow |
| `$nodeLabel.node_count` | Кількість вузлів |
| `$nodeLabel.nodes` | Масив `{ id, type, label, position, data }` |
| `$nodeLabel.edges` | Масив `{ id, source, target, sourceHandle, targetHandle }` |

`data` — це **повна конфігурація вузла**, кожне поле в тому вигляді, у якому його було збережено. Саме це уможливлює аудит: Ви не можете просканувати workflow на наявність API-ключа, який хтось вставив у поле, якщо вузол відмовляється показувати це поле.

Це не надає жодного доступу, якого в того, хто викликає, не було раніше. Вузол обмежено workflow, які власник і так може відкрити в редакторі, а збережених секретів облікових даних тут усе одно немає: дані вузла містять лише **ідентифікатори** облікових даних, тоді як самі секрети зберігаються зашифрованими в таблиці облікових даних.

### Сканування на наявність жорстко закодованих секретів

```
cron → heym (listWorkflows) → loop → heym (getWorkflow) → agent → slack
```

Надайте агенту `$detail.nodes` і попросіть його позначити будь-яке значення `data`, що виглядає як дійсний ключ або token. Варто звертати увагу на поля вільного тексту — `curl` на вузлах HTTP, `userMessage` та `systemInstruction` на вузлах LLM і Agent, а також тіла Python-інструментів — адже ідентифікатор облікових даних є нешкідливим UUID, а вставлений `sk-…` — ні.
### Отримання історії виконань

Повертає записи історії виконань для одного workflow, найновіші — першими.

| Вираз | Опис |
|------------|-------------|
| `$nodeLabel.executions` | Масив записів історії |
| `$nodeLabel.executions[0].id` | UUID виконання |
| `$nodeLabel.executions[0].status` | `success`, `error` тощо |
| `$nodeLabel.executions[0].started_at` | Мітка часу у форматі ISO |
| `$nodeLabel.executions[0].execution_time_ms` | Тривалість за реальним часом |
| `$nodeLabel.executions[0].trigger_source` | Що запустило виконання, наприклад `cron` або `heym_event` |
| `$nodeLabel.executions[0].recovered` | Чи було виконання відновлено після збою |
| `$nodeLabel.executions[0].inputs` | Що отримало виконання — payload trigger або вхідні дані виклику |
| `$nodeLabel.executions[0].outputs` | Вихідні дані workflow для цього виконання |
| `$nodeLabel.workflow_id`, `$nodeLabel.workflow_name` | Workflow, якому належить історія |
| `$nodeLabel.total` | Загальна кількість відповідних виконань **до** застосування обмеження |
| `$nodeLabel.by_status` | Кількість за статусами, наприклад `{ "success": 41, "error": 3 }` |
| `$nodeLabel.since` | Початок вікна або `null` для всієї історії |

Записи містять як `inputs`, так і `outputs` — те, що отримало виконання, і те, що воно повернуло, — але ніколи не `node_results`: трасування за окремими вузлами є найбільшим стовпцем у таблиці та затьмарило б усе подальше. Отримуйте окреме виконання через API, коли потрібне повне трасування.

`total` і `by_status` завжди описують **усю** відповідну історію, навіть коли **Limit** обмежує повернені записи — тож можна взяти п'ять найновіших виконань і все одно отримати точну кількість збоїв.

Залиште **Since (days)** порожнім, щоб охопити все, **Status filter** порожнім, щоб включити всі статуси, а **Limit** порожнім або `0`, щоб повернути кожен запис.

## Приклад workflow

**Щоденний дайджест інстансу**

```
cron → heym (listWorkflows) → loop → heym (getExecutionHistory) → llm → sendEmail
```

- **Heym** `listWorkflows` з міткою `inventory`
- **Loop** за `$inventory.workflows`
- **Heym** `getExecutionHistory` з `heymWorkflowId`, встановленим у `id` елемента циклу, `heymSinceDays` зі значенням `1` та `heymLimit` зі значенням `5`
- **LLM** перетворює зібрані виконання та кількість за статусами на читабельне зведення

## Примітки

- Облікові дані не потрібні; вузол читає ту саму базу даних, на якій працює Heym.
- **Limit** — це те саме поле для обох операцій списку, і воно означає те саме в обох: порожнє або `0` повертає все.
- Вузол приймає звичайні вхідні дані та може бути приєднаний до вузла Agent як інструмент, тож агент може відповідати на запитання про ваш інстанс Heym — або перевіряти його.
- Payload `getWorkflow` зростає разом із workflow: довгі prompt та тіла Python-інструментів передаються всередині `data`.
- Поєднуйте його з [Heym Trigger](./heym-trigger-node.md), щоб реагувати на зміни workflow у міру їх виникнення, а не опитувати за розкладом.
