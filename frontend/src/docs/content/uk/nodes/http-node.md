# HTTP

Вузол **HTTP** виконує HTTP-запити, використовуючи синтаксис cURL. Він може бути початковою точкою workflow (без вхідного ребра) або отримувати вхідні дані від вищестоящих вузлів.

## Огляд

| Властивість | Значення |
|----------|-------|
| Входи | 0 або 1 |
| Виходи | 1 |
| Вихід | `$nodeLabel.status`, `$nodeLabel.body`, `$nodeLabel.headers` |

## Параметри

| Параметр | Тип | Опис |
|-----------|------|-------------|
| `label` | string | Ідентифікатор вузла (camelCase) |
| `curl` | string | Команда cURL (наприклад, `curl -X GET https://api.example.com`) |

## Формат відповіді

```json
{
  "status": 200,
  "headers": { "content-type": "application/json", ... },
  "body": "response body or parsed JSON",
  "request": { "method": "POST", "url": "...", "headers": {...} }
}
```

## Доступ до відповіді

- `$httpNode.status` – код стану HTTP
- `$httpNode.body` – Тіло відповіді (рядок або розібраний JSON)
- `$httpNode.body.fieldName` – Доступ до полів JSON
- `$httpNode.headers` – Заголовки відповіді

## Приклад

```json
{
  "type": "http",
  "data": {
    "label": "fetchApi",
    "curl": "curl -X GET https://api.example.com/data"
  }
}
```

Використовуйте синтаксис cURL з `-H` для заголовків, `-d` для тіла POST тощо. Вирази можна використовувати будь-де в рядку curl, зокрема в URL, заголовку або цілому рядку заголовка. [Облікові дані](../reference/credentials.md) типу Header розгортаються у `key: value`, тому `-H "$credentials.MyApiKey"` надсилає повний заголовок:

```
curl -X GET "https://api.example.com/search?q=$query.body.text.urlEncode()" -H "$credentials.MyApiKey"
```

Лапки та пробіли всередині виразу належать виразу, а не команді cURL, тому методи, що приймають рядкові аргументи, працюють у рядку:

```
curl "https://r.jina.ai/$url.text.replaceAll("\n", "").strip()" -H "Authorization: $credentials.Jina"
```

## Автентифікація за допомогою облікових даних

`$credentials.Name` розгортається в різне значення для кожного типу [облікових даних](../reference/credentials.md), тому рядок заголовка залежить від типу:

| Тип облікових даних | `$credentials.Name` розгортається у | Заголовок |
|-----------------|---------------------------------|--------|
| Bearer | `Bearer <token>` | `-H "Authorization: $credentials.Name"` |
| Header | `<Header-Name>: <value>` | `-H "$credentials.Name"` |
| OpenAI, Custom, Cohere | Необроблений API-ключ | `-H "Authorization: Bearer $credentials.Name"` |
| Google | Необроблений API-ключ | `-H "x-goog-api-key: $credentials.Name"` |
| ElevenLabs | Необроблений API-ключ | `-H "xi-api-key: $credentials.Name"` |
| Google Sheets, Google Drive | Свіжий токен доступу OAuth, який оновлюється після закінчення терміну дії | `-H "Authorization: Bearer $credentials.Name"` |
| GitHub, Notion, Sentry | Токен | `-H "Authorization: Bearer $credentials.Name"` |

Облікові дані типу Bearer вже містять префікс `Bearer `, тому додавання ще одного надсилає `Bearer Bearer …`. Облікові дані Google Sheets і Google Drive дають змогу викликати Google API, які не покриваються їхнім вузлом, наприклад додавати вкладку до електронної таблиці, у межах наданих обліковим даним областей доступу. Якщо ім'я не є простим ідентифікатором (містить `-`, починається з цифри або є зарезервованим словом), використовуйте форму з дужками: `-H "Authorization: $credentials["my-api-key"]"`.

Коли [AI Assistant](../reference/ai-assistant.md) або [Chat](../tabs/chat-tab.md) формує HTTP-запит, який потребує автентифікації, і жоден спеціалізований вузол не покриває цю службу, він запитує, які облікові дані використовувати. Виберіть одні, змініть попередньо заповнену назву заголовка, якщо API очікує іншу, і він напише рядок заголовка за вас. Асистент бачить назви та типи облікових даних, але ніколи їхні значення. Якщо у вас немає відповідних облікових даних, запитання пропонує створити їх. Секрети, які потрапляють у вихід вузла, як-от надіслані `request.headers`, маскуються в результатах виконання.

## Безпека вихідного трафіку

- За замовчуванням URL має використовувати `http://` або `https://` і розпізнаватися лише як публічні адреси. Адреси зворотного зв'язку, приватні, локальні для каналу, багатоадресні та хмарні метадані блокуються.
- Heym перевіряє розпізнані адреси та закріплює ціль з'єднання, щоб запобігти DNS rebinding. Проксі середовища вимикаються, поки активний захист. Перенаправлення за замовчуванням не відстежуються; додайте опцію cURL `-L`, щоб їх відстежувати. Коли її увімкнено, кожен крок перенаправлення перевіряється відповідно до тієї самої політики публічних адрес і закріплюється перед з'єднанням.
- Довірені розгортання на власних серверах, які навмисно підключаються до внутрішніх служб, можуть встановити `HEYM_HTTP_ALLOW_PRIVATE_URLS=true`. Залишайте значення за замовчуванням у розгортаннях на хостингу або з кількома орендарями.

**Примітка щодо оновлення до v0.0.105:** ця політика на рівні всього екземпляра тепер також захищає призначення, похідні від облікових даних, які використовуються Jira, Sentry, GitHub, Grist, Supabase, ClickHouse, виконанням користувацьких LLM і виявленням моделей, AI-асистентом, guardrails і RAG-вбудовуваннями. Наявні облікові дані, які вказують на адреси зворотного зв'язку, приватні або локальні для каналу, відхиляються, якщо `HEYM_HTTP_ALLOW_PRIVATE_URLS=true` не увімкнено на довіреному екземплярі з власним розгортанням. Поки захист увімкнено, захищені HTTP-клієнти ігнорують `HTTP_PROXY` і `HTTPS_PROXY`; увімкнення відмови від захисту відновлює їх. Набори сертифікатів ЦС оператора, налаштовані через `SSL_CERT_FILE` або `SSL_CERT_DIR`, залишаються підтримуваними. ClickHouse перевіряється перед відкриттям з'єднання, але не закріплюється під час з'єднання, оскільки clickhouse-connect використовує власний транспорт urllib3.
