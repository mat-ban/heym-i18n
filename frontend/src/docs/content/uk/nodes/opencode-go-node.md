# Вузол OpenCode Go

Вузол **OpenCode Go** запускає CLI [OpenCode](https://opencode.ai) (Go) в ізольованому, захищеному контейнері Heym для роботи з репозиторієм GitHub. Як і вузол Codex, він призначений для завдань програмування, таких як виправлення тестів, редагування файлів, створення патча або відкриття pull request, — але використовує незалежний від постачальника шлюз моделей **OpenCode Go** замість OpenAI Codex.

## Огляд

| Властивість | Значення |
|----------|-------|
| Входи | 1 |
| Виходи | 1 |
| Облікові дані | Ключ API OpenCode Go + GitHub |
| Вихід | `$nodeLabel.summary`, `$nodeLabel.diff`, `$nodeLabel.changedFiles`, `$nodeLabel.pullRequestUrl` |

## Автентифікація

Облікові дані **OpenCode Go** зберігають **ключ API** шлюзу OpenCode Go (з [opencode.ai/go](https://opencode.ai/go)) та необов'язковий **Gateway Base URL** (типово `https://opencode.ai/zen/go/v1`; перевизначайте лише для самостійно розміщеного або проксійованого шлюзу).

Вузол також потребує облікових даних **GitHub** для клонування приватних репозиторіїв, надсилання робочої гілки та створення pull request. Token GitHub **ніколи не розміщується всередині контейнера пісочниці** — Heym виконує всі операції git і GitHub на хості, тож згенерований код не може викрасти облікові дані для надсилання.

## Ізоляція та безпека

Ізоляція виконання обирається за допомогою `HEYM_OPENCODE_CLI_COMMAND`, точно як у вузлі Codex:

- **Локальна розробка (`run.sh`)** залишає його зі значенням за замовчуванням `opencode`, тож OpenCode виконується як підпроцес хоста щодо клонованого робочого простору — Docker не потрібен, жодних додаткових прапорців.
- **Розгортання в Docker (`deploy.sh` та єдиний образ GHCR)** встановлює його в `/usr/local/bin/heym-opencode-docker` — обгортку, яка запускає `opencode run` всередині **захищеного, тимчасового сусіднього контейнера**, що спільно використовує іменований том робочого простору OpenCode.

Захищений контейнер-виконавець позбавляється всіх можливостей Linux, встановлює `no-new-privileges`, використовує корінь лише для читання з tmpfs `/tmp` та застосовує обмеження pid/пам'яті/CPU. Мережевий вихід дозволено (OpenCode має досягати шлюзу моделей). **Token GitHub ніколи не розміщується всередині контейнера** — усі операції git і GitHub виконуються на боці хоста, тож усередині перебувають лише ключ API OpenCode та файли репозиторію.

OpenCode лише редагує файли на диску; Heym керує кожною дією git/GitHub.

## Моделі

Перелік моделей OpenCode Go часто змінюється, тож поле **Model** заповнюється наживо зі списку моделей шлюзу (`GET https://opencode.ai/zen/go/v1/models`) і відображається як розкривний список із пошуком. Якщо живий список недоступний, використовується вбудований резервний список. Ідентифікатори моделей мають форму `opencode-go/<model>` (наприклад, `opencode-go/kimi-k3`, `opencode-go/deepseek-v4-pro`, `opencode-go/qwen3.7-max`) — `opencode-go` є ідентифікатором постачальника CLI OpenCode для шлюзу Go. Залиште поле порожнім, щоб використати типове значення виконавця (`opencode-go/kimi-k3`). Ідентифікатори моделей, збережені в старішій формі `opencode/<model>`, автоматично переписуються під час виконання.

## Поля

| Поле | Опис |
|-------|-------------|
| OpenCode Go Credential | Облікові дані OpenCode Go (ключ API шлюзу) |
| GitHub Credential | Облікові дані PAT GitHub, що використовуються для доступу до репозиторію |
| Repository URL | HTTPS-URL репозиторію GitHub; підтримує вирази |
| Base Branch | Гілка для клонування перед запуском OpenCode, типово `main` |
| Model | Модель OpenCode Go (живий розкривний список із пошуком, `opencode-go/<model>`); порожнє значення використовує типове для виконавця |
| Reasoning Variant | Необов'язково; відповідає `opencode run --variant` для моделей, що підтримують рівень міркування |
| Task Prompt | Завдання програмування для OpenCode; підтримує вирази, як-от `$input.text` |
| Publish Mode | Спосіб доставки змін (див. таблицю нижче) |
| Branch Name | Робоча гілка для режимів PR/commit, типово `opencode/$executionId` |
| Timeout | Максимальний час виконання OpenCode у секундах |

## Режими публікації

| Режим | Що робить |
|------|--------------|
| `diff_only` | Редагує файли локально та повертає патч і змінені файли. Нічого не надсилається. |
| `draft_pr` | Фіксує зміни в гілці, надсилає її та відкриває чернетковий pull request. |
| `open_pr` | Фіксує зміни в гілці, надсилає її та відкриває готовий до перегляду (не чернетковий) pull request. |
| `commit_push` | Фіксує зміни в гілці та надсилає її без відкриття pull request. |
| `direct_commit` | Фіксує та надсилає зміни безпосередньо до базової гілки (без окремої гілки чи PR). |
| `open_or_update_pr` | Оновлює наявний відкритий PR агента, якщо такий існує — навіть якщо назва гілки відрізняється, виконавець знаходить його за автором + базою — інакше відкриває новий. Найкраще для повторних запусків та інструкцій «оновити відкритий PR». |
| `update_existing_pr` | Додає коміт до наявної гілки/PR; відкриває новий, якщо жодного ще немає. |
| `patch_artifact` | Зберігає diff як файл для завантаження та повертає `patchUrl`. Нічого не надсилається. |

## Виходи

| Ключ | Опис |
|-----|-------------|
| `status` | Завжди `completed` (вузол OpenCode Go не зупиняється для введення) |
| `summary` | Фінальне повідомлення OpenCode |
| `validation` | Примітки щодо валідації, коли повідомляються |
| `diff` | Патч Git, коли файли змінено |
| `changedFiles` | Шляхи змінених файлів |
| `branchName` | Назва робочої гілки |
| `pullRequestUrl` | URL PR у режимах `draft_pr`, `open_pr`, `open_or_update_pr` та `update_existing_pr` |
| `pushedBranch` | Гілка, яку було надіслано в режимах commit/PR |
| `patchUrl` | Посилання для завантаження diff у режимі `patch_artifact` |
## Скриншоти UI у pull request

Для завдань UI/фронтенду OpenCode має зберігати PNG-скриншоти за шляхом, доданим до gitignore, наприклад `frontend/.e2e-artifacts/` (не у вихідному коді). Якщо залежності фронтенду відсутні, prompt runner дозволяє цільове встановлення пакетів (наприклад, `bun install`) разом із короткочасним preview/`bun run dev` виключно для захоплення UI. Heym завантажує ці зображення до єдиного спільного GitHub **prerelease** (`opencode-pr-assets`) як assets з іменами `<branch>-…`, а потім вбудовує їх в опис PR **до відкриття pull request**, тож новий PR створюється вже зі своїми скриншотами (наявні PR оновлюються на місці).

OpenCode також отримує вказівку завершувати рядком `PR_TITLE: …`, щоб Heym міг відкрити pull request зі змістовною темою замість заповнювачів на кшталт `Done.`

Іноді OpenCode завершує хід посеред завдання («…Now let me take a screenshot»), що призвело б до фіналізації запуску до захоплення скриншота. Щоб запобігти цьому, prompt runner вимагає захоплювати скриншоти **перед** фінальним повідомленням, і якщо запуск усе ж завершується без придатного для публікації підсумку або зі зміною UI, але без скриншота, Heym виконує ще один прохід OpenCode у тому самому workspace для завершення. Якщо після цього зміна UI все ще не має скриншота, до тіла PR додається видима примітка, щоб ця прогалина ніколи не залишалася непоміченою.

## Що публікується до GitHub

Ваш **Task Prompt** є приватним вхідним даним, а не вмістом PR. Публікуються лише дві речі: розділ `## Change Summary`, що описує, що робить зміна коду, та розділ `## Screenshots`, коли скриншоти було захоплено. Тема PR виводиться виключно з підсумку змін.

Prompt runner декларує цю політику, і Heym також забезпечує її дотримання після запуску: перш ніж щось буде закомічено або відкрито як pull request, він вилучає розділи-відлуння prompt (`## Task`, `## Prompt`, `## Instructions`, `## Original Request`, …) та будь-який абзац, дослівно скопійований з task prompt, з підсумку, тіла PR і повідомлення коміту.

Heym читає розділ `## Change Summary` з повідомлень агента, а не бере те, що було сказано останнім, оскільки OpenCode видає повідомлення на кожен крок, і фінальне часто є коментарем посеред запуску. Нарація кроків (`Both pass. Let me do a final review:`) також відхиляється як тема PR або subject коміту. Якщо запуск не дає придатного підсумку змін, pull request натомість наводить перелік змінених файлів замість публікації коментарів.

## Як інструмент агента

Вузол OpenCode Go можна приєднати до ручки інструментів вузла **AI Agent**, щоб агент міг делегувати завдання з кодування. Налаштуйте облікові дані, облікові дані GitHub і репозиторій на вузлі, потім позначте **Task Prompt** (і за бажанням **Repository URL**) перемикачем, що надається агентом, щоб агент передавав їх під час виклику.

## Приклад

```json
{
  "id": "opencode-1",
  "type": "opencodeGo",
  "position": { "x": 420, "y": 120 },
  "data": {
    "label": "fix_pr",
    "credentialId": "opencode-credential-uuid",
    "githubCredentialId": "github-credential-uuid",
    "repositoryUrl": "https://github.com/acme/app",
    "baseBranch": "main",
    "taskPrompt": "$input.text",
    "publishMode": "open_pr",
    "branchName": "opencode/$executionId",
    "opencodeModel": "opencode-go/kimi-k3",
    "timeoutSeconds": 3600
  }
}
```
