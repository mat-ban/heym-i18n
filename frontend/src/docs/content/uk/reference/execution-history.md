# Історія виконань

Історія виконань фіксує запуски workflow: входи, виходи, результати вузлів, статус і джерело
trigger. Використовуйте її, щоб спостерігати за активним запуском у production, переглядати минулі
запуски, налагоджувати збої або повторно запускати з тими самими входами через **Bring to Canvas**.

## Огляд

Кожне виконання зберігає:

| Поле | Опис |
|-------|-------------|
| **Inputs** | Тіло запиту або входи запуску (наприклад, `text` для вузла Input) |
| **Outputs** | Виходи на рівні workflow |
| **Node results** | Виходи кожного вузла, статус і час виконання |
| **Status** | `success`, `error`, `pending`, `skipped` або `failed` (див. [Crash Recovery](#crash-recovery)) |
| **trigger_source** | Як було запущено виконання (див. [Triggers](./triggers.md)) |

## Доступ до історії

| Розташування | Обсяг |
|----------|-------|
| Панель інструментів **Editor** | Лише поточний workflow |
| Заголовок подання **Docs** | Лише поточний workflow |
| Заголовок **Dashboard** (вкладка Chat) | Усі workflow + запуски chat/assistant |
| Заголовок подання **Evals** | Усі workflow + запуски chat/assistant |

Натисніть кнопку **History** (іконка годинника), щоб відкрити діалогове вікно.

## Історія для окремого workflow vs уся історія

- **Для окремого workflow** (Editor, Docs): Показує запуски для відкритого workflow. Використовуйте **Clear history**, щоб видалити запуски лише для цього workflow.
- **Уся історія** (Dashboard, Evals): Показує запуски в усіх workflow і сесіях chat/assistant. Обсяг відповідає доступу до workflow: workflow, якими Ви володієте, workflow, надані Вам напряму, і workflow, надані команді, до якої Ви належите. Використовуйте **Clear all history**, щоб видалити всі записи, якими Ви володієте. Історія для наданих workflow зберігатиметься.

## Bring to Canvas

**Bring to Canvas** завантажує входи вибраного запуску та виходи вузлів у поточний workflow.

### Що завантажується

- **Inputs** → Панель входів запуску (наприклад, `text` для вузла Input або власні поля)
- **Node results** → Панель результатів виконання показує минулі виходи кожного вузла
- **Execution result** → Статус, виходи та час із запуску

### Поведінка залежно від контексту

- **В Editor** (історія для окремого workflow): Застосовується негайно до відкритого workflow і закриває діалогове вікно.
- **З усієї історії** (Dashboard/Evals): Переходить до редактора workflow, потім застосовує дані після завантаження редактора. Доступно лише для запусків workflow — не для запусків chat/assistant.

### Deep link виконання

Відкриття workflow за адресою `/workflows/{workflowId}/{executionId}` автоматично переносить це виконання на canvas — так само, як вибір запуску та команда **Bring to Canvas**. Це дає змогу поділитися конкретним минулим запуском як URL-адресою. Якщо виконання не знайдено (неправильний або видалений id), редактор повертається до завантаження звичайного workflow.

### Сценарії використання

- Повторний запуск workflow з тими самими входами
- Налагодження невдалого запуску шляхом перегляду входів і виходів вузлів
- Порівняння виходів між запусками

## Execution Highlights

Після живого запуску — або після **Bring to Canvas** — у **правому верхньому куті Canvas** з'являється закривне спливне вікно **Execution Highlights**. Це швидкий спосіб побачити, *що саме створив кожен вузол*, у порядку виконання згори донизу. Закрийте його кнопкою **✕**; воно знову відкриється під час наступного запуску.

### Що показується

| Запис | Джерело | Автоматично? |
|--------|--------|-------|
| **Input** | Вхідні параметри запуску (вузол input/trigger) | Так |
| **Output** | Результат вузла output — або, якщо його немає, повідомлення останнього вузла | Так |
| **Agent / LLM** | Вихід кожного вузла agent або LLM | Так |
| **Output** | Будь-який інший вузол із увімкненим **Highlight Node Output** | За бажанням |

Вузли, які вже підсвічуються автоматично (input / output / last / agent / llm), ніколи не з'являються двічі, навіть якщо Ви також увімкнете перемикач.

### Кожен запис

- Показує `Node — message…` з першими **250 символами**; натисніть на рядок, щоб розгорнути його та відобразити **повне повідомлення як Markdown**, із кнопкою **Copy**.
- Вузол, який виконувався кілька разів (наприклад, усередині циклу), показує `Node (N)` із селектором `‹ i / N ›` — виберіть, який запуск переглянути; селектор кожного вузла незалежний.

### Highlight Node Output

Кожен вузол **крім Agent і LLM** має прапорець **Highlight Node Output** у своїй панелі властивостей (типово вимкнено). Увімкніть його, щоб додати вихід цього вузла до спливного вікна. На підсвічених вузлах на canvas з'являється невеликий значок ✦. У [workflow DSL](./expression-dsl.md) це поле даних вузла `"highlight": true` (типово `false`).

### На dashboard

Картки віджетів Dashboard, які запускали workflow, показують кнопку ✦ **Execution highlights** у заголовку картки; натисніть її, щоб відкрити те саме спливне вікно для запуску цього віджета, з намальованим виходом віджета як основним записом.

## Запуск виконань, що виконуються

Обидва діалоги історії показують **виконання, що виконуються зараз**, угорі списку, перед минулими запусками.

- Індикатор обертання та мітка **Running** з'являються разом із часом початку
- Натисніть **Open live**, щоб приєднати редактор до саме цього запуску без його перезапуску
- Полотно спочатку відновлює вузли, які вже завершилися, а потім отримує
  події `node_start`, `node_complete` та фінальні події виконання через SSE
- Поточний вузол пульсує на полотні, нижчі вузли зберігають анімацію очікування, а
  панель Debug додає кожен результат у міру його надходження — так само, як під час запуску з редактора
- Натисніть **Cancel**, щоб негайно зупинити виконання
- Скасування з будь-якого діалогу (Editor або Dashboard) також закриває активний потік SSE у будь-якій відкритій вкладці полотна для цього workflow, тож стан редактора скидається коректно
- Після скасування запис про запуск зникає під час наступного оновлення; натисніть **Refresh**, щоб оновити список вручну
- Якщо Ви скасуєте запуск, який уже завершився, запит не матиме жодного ефекту

URL наживо — `/workflows/{workflowId}/{executionId}`. Спостерігач працює лише для читання: вихід
з редактора лише від'єднує цю вкладку браузера й ніколи не зупиняє workflow. Активні знімки
стану спільно використовуються через PostgreSQL, тож відкриття запуску все одно працює, коли trigger і
запит редактора потрапляють на різні backend-воркери.

## Відновлення після збою

Якщо сервер перезапускається (розгортання, перезапуск контейнера або збій), поки workflow виконується, воркер цього запуску зупиняється посеред виконання. Heym автоматично відновлює ці перервані запуски, замість того щоб залишати їх у стані **Running**.

- Під час наступного запуску обраний лідер-процес виявляє осиротілі запуски — миттєво у разі коректного перезапуску або протягом ~60 секунд у разі жорсткого збою (щойно heartbeats явно припиняються).
- Відновлені запуски **перезапускаються з нуля з тими самими вхідними даними** (а не продовжуються з місця зупинки), використовуючи поточне визначення workflow. Після завершення вони записують звичайний термінальний запис (наприклад, `success`), тож історія показує запуск як завершений.
- Запуск повторюється **один раз**. Якщо спроба відновлення також перервана — або workflow відтоді видалено — запис фіксується як `failed`.
- Це працює однаково як для одного контейнера, так і для розгортань із кількома воркерами; відновлення виконує лише лідер, тож запуск ніколи не відновлюється двічі різними воркерами.

### Перемикач Auto-recover

Панель **Execution Log** (запуск) у редакторі має прапорець **Auto-recover**, **увімкнений за замовчуванням** для кожного workflow.

- **Увімкнено**: перервані запуски цього workflow перезапускаються, як описано вище.
- **Вимкнено**: перервані запуски не перезапускаються й записуються зі статусом `skipped`.

> Запуски sub-workflow не відновлюються незалежно — їх повторно запускає відновлений батьківський запуск. Triggers із власною повторною доставкою (RabbitMQ, scheduled/cron, IMAP) також можуть повторно доставляти повідомлення під час перезапуску, тож відновлений запуск іноді може виконатися двічі.

## Очікування перевірки людиною

Запуски, які призупиняються для схвалення [Human-in-the-Loop](./human-in-the-loop.md), одразу записуються в історію зі статусом `pending`.

- Вузол агента в стані очікування зберігає payload перевірки, що містить `reviewUrl`, `draftText` та `expiresAt`
- Будь-які вузли, з'єднані з обробником `review` агента, також можуть виконуватися до відповіді людини, і їхні результати вузлів зберігаються в тому самому записі історії зі станом очікування
- Діалоги історії показують посилання на перевірку, щоб власники могли скопіювати або відкрити його
- Діалоги історії та панель Debug у редакторі показують фінальне рішення людини після відновлення запуску
- Коли рецензент приймає, редагує або відхиляє чернетку, той самий запис історії оновлюється фінальним результатом виконання
- Якщо той самий запуск призупиняється для HITL більше ніж один раз, запис історії залишається тим самим, тоді як кожна контрольна точка отримує власне одноразове посилання на перевірку

Це особливо корисно для запусків через портал і довготривалих workflow, які можуть очікувати годинами чи днями, перш ніж продовжити.

## Copy

Використовуйте **Copy** поруч із Inputs або Outputs, щоб скопіювати JSON до буфера обміну.

## Clear History

- **Для окремого workflow**: у діалозі історії редактора натисніть **Clear history**, щоб видалити запуски для поточного workflow.
- **Уся історія**: у діалозі історії Dashboard/Evals натисніть **Clear all history**, щоб видалити всі записи виконань, якими Ви володієте. Запуски зі спільних workflow зберігаються. Цю дію не можна скасувати.

## Деталі часової шкали виконання

Коли **Execution Log** у редакторі відкрито, натисніть кнопку таймера, щоб показати часову шкалу виконання. Виберіть проміжок, щоб відкрити вбудований інспектор деталей, який займає область рядків. Він показує статус вибраного кроку, тривалість, кількість спроб, інформацію про повторні спроби, помилки, trace ID та компактний попередній перегляд виводу. Виводи у вигляді об'єктів і масивів використовують той самий засіб перегляду `JsonTree`, що й решта панелі Debug; скалярні значення використовують текстовий попередній перегляд. Коли крок виводить зображення (знімки екрана Playwright, згенеровані зображення, файли зображень), вони з'являються як мініатюри над виводом, а JSON показує короткий заповнювач замість необробленого base64. Натисніть мініатюру, щоб відкрити її в лайтбоксі; кнопки зі стрілками або клавіші ←/→ перегортають усі зображення запуску, з лічильником, як-от `2 / 5`. Використовуйте **Open trace** для проміжків LLM і Agent, коли доступний trace ID.

## Деталі вузла на мобільному пристрої

На телефоні редактор відображає повноекранне дерево workflow замість довільного полотна. Торкніться вузла дерева із записаним результатом, щоб відкрити його виконання як повноекранну деталь. Подання надає окремі вкладки **Input Data**, **Output Data** та **Errors**. Вкладка виводу відображає записаний результат і пропонує **Copy Output**; вкладка вводу показує конфігурацію вибраного вузла, а вкладка помилок показує записану помилку, коли вузол зазнав невдачі. Використайте **Back to workflow** або кнопку закриття, щоб повернутися до дерева.

Діалоги історії полотна та панелі керування зберігають свої елементи керування запуском в одному рядку та розміщують доступні фільтри тегів і примірників у адаптивній сітці. Їхні меню фільтрів використовують той самий вбудований селектор, тож вибрана позначка має узгоджений відступ і базову лінію з кожним написом опції.
