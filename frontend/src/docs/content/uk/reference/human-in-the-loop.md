# Human-in-the-Loop

Human-in-the-loop (HITL) дозволяє [Agent Node](../nodes/agent-node.md) запитувати схвалення в певні моменти, чекати на рішення людини, а потім продовжувати workflow з того самого знімка виконання.

## Що це робить

- Додає явні контрольні точки схвалення до агента без створення окремого workflow схвалення
- Створює одноразовий публічний URL перегляду за адресою `/review/{token}`
- Дозволяє рецензенту `Accept`, `Edit & Continue` або `Refuse`
- Позначає виконання як `pending`, доки не надійде рішення
- Відновлює призупинене виконання та дозволяє агенту продовжити після схвалення
- Підтримує кілька послідовних контрольних точок HITL в одному запуску агента

## Конфігурація агента

Увімкніть HITL на панелі властивостей агента.

| Налаштування | Опис |
|---------|-------------|
| `hitlEnabled` | Вмикає перегляд людиною для цього агента |
| `hitlSummary` | Настанови щодо схвалення для визначення, коли агент має запитувати перегляд людиною |

HITL додає до агента інструмент `request_human_review`. Використовуйте system prompt і настанови `hitlSummary`,
щоб повідомити агенту, які дії потребують схвалення. Коли агент вирішує, що контрольна точка
потребує перегляду, він надсилає людині єдиний текст перегляду у форматі Markdown. Підсумок для
рецензента генерується з запиту агента під час виконання; якщо агент його не надає, Heym формує його з
тіла Markdown. У v1 HITL підтримує лише виводи агента в текстовому режимі, тому його не можна поєднувати з
`jsonOutputEnabled`.

Для інструментів MCP Heym просить модель інтерпретувати письмові інструкції HITL в одну з трьох
областей схвалення:

- `always` для фраз на кшталт "always", "on each" або "for each"
- `once` для фраз на кшталт "once" або "only one time"
- `never` для фраз на кшталт "never", "do not ask" або "already approved"

Ця інтерпретація визначає, чи повторні виклики MCP знову призупиняються, залишаються схваленими один раз або повністю пропускають
перегляд людиною.

Коли HITL увімкнено, агент також надає другий вихідний порт на полотні з позначкою `review`. Використовуйте цю гілку, щоб надсилати URL очікуваного перегляду та підсумок до Slack, електронною поштою, журналювання або будь-якого іншого потоку сповіщень, поки основне виконання чекає на людину.

## Потік перегляду

1. Агент досягає кроку, що потребує схвалення, і викликає `request_human_review`
2. Heym створює публічний запит на перегляд і повертає URL перегляду
3. Будь-які вузли, підключені до порту `review` агента, виконуються негайно з payload HITL зі станом очікування
4. Виконання workflow переходить у стан `pending`
5. Рецензент відкриває `/review/{token}` без входу в систему
6. Рецензент вибирає одну дію:
   - `Accept` продовжує з оригінальним Markdown
   - `Edit & Continue` продовжує з відредагованим Markdown
   - `Refuse` продовжує з `decision: "refused"` і пропускає подальші дії агента
7. Heym відновлює workflow зі збереженого знімка та дозволяє агенту продовжити з контекстом схваленого Markdown
8. Якщо пізніший крок також потребує схвалення, агент може знову викликати HITL і створити ще одну контрольну точку зі станом очікування

Посилання для перегляду спливають через 168 годин, якщо ніхто не відповідає.

## Публічна сторінка перегляду

Публічна сторінка перегляду показує:

- Назву workflow та мітку агента
- Автоматично згенерований підсумок для рецензента із запиту на перегляд агента
- Текст перегляду у форматі Markdown спочатку, як основний вміст
- Поле редагування, яке відкривається лише після натискання рецензентом `Edit`
- Живий попередній перегляд Markdown під час редагування
- Кнопки дій для `Accept`, `Edit & Continue` і `Refuse`

Щойно рішення надіслано, token блокується і його не можна використати повторно.

## Виводи та стан виконання

Під час очікування перегляду вивід агента містить payload зі станом очікування:

```json
{
  "decision": null,
  "summary": "Review the customer-ready reply before it is sent.",
  "draftText": "# Goal\n...\n\n# Planned Tool Calls / Actions\n- ...",
  "reviewUrl": "https://example.com/review/abc123",
  "requestId": "uuid",
  "expiresAt": "2026-03-29T10:00:00Z",
  "shareMarkdown": "Review the customer-ready reply before it is sent.\n\n[Open review page](https://example.com/review/abc123)"
}
```

Після того як рецензент відповідає і workflow відновлюється, фінальний вивід агента містить метадані рішення:

```json
{
  "text": "Final agent output after approval and execution",
  "decision": "accepted",
  "summary": "Review the customer-ready reply before it is sent.",
  "originalDraft": "# Goal\n...\n\n# Planned Tool Calls / Actions\n- ...",
  "requestId": "uuid"
}
```

Використовуйте `$agentLabel.decision` у наступних вузлах, щоб розгалужуватися за результатами accepted, edited або refused.

## Гілка перегляду на полотні

Вихідний порт `review` доступний лише тоді, коли для агента увімкнено `hitlEnabled`.

- Він виконується до надходження рішення людини
- Він отримує payload HITL зі станом очікування, включно з `summary`, `draftText`, `reviewUrl`, `shareText` і `shareMarkdown`
- Він призначений для кроків сповіщення або передачі, як-от Slack, електронна пошта або журналювання аудиту
- Він виконується один раз для кожної контрольної точки HITL
- Він не виконується знову після відповіді рецензента; після відновлення продовжується лише звичайний шлях виводу агента

## Де це відображається

- [Історія виконання](./execution-history.md) одразу показує запуски зі статусом `pending` і зберігає URL перевірки в результатах вузла
- Відповіді чату в [Portal](./portal.md) показують посилання на перевірку людиною замість порожньої відповіді
- Панель Debug і діалоги історії показують фінальне рішення HITL і перевірений текст
- Вихідний обробник перевірки може сповіщати зовнішні канали, навіть коли workflow було запущено через cron, curl або трафік portal
- Кілька контрольних точок HITL повторно використовують той самий запис історії виконання, створюючи нове одноразове посилання на перевірку для кожної паузи

## Поточні обмеження

- HITL доступний лише на вузлах Agent
- HITL використовує текстовий вивід агента і не підтримує вивід JSON у v1
- Призупинене виконання відновлюється зі збереженого знімка workflow, а не з останньої відредагованої версії workflow
- Вкладені sub-workflows не можуть перейти в стан очікування HITL у v1; запросіть перевірку від батьківського агента перед їх викликом
