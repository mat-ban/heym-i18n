# Heym Incident Playbook (L0)

Використовуйте цей playbook, щоб підтвердити інцидент у Heym, оцінити вплив на користувачів, визначити рівень критичності (severity) та отримати доступ до належної процедури відновлення і відповідального власника.

Детальні процедури: [Heym Runbook (L1)](./operations-runbook.md)

Останній перегляд: 2026-11-10. Обсяг: self-hosted Heym, окремий екземпляр або cluster, на Docker Compose чи Kubernetes.

## Передача розгортання (Deployment handover)

Заповніть цю таблицю для кожного середовища перед використанням цих документів під час чергування (on-call). Назви, URL-адреси, цілі щодо місткості та цілі відновлення є специфічними для кожного розгортання. Приклади з репозиторію не є інвентарем робочого середовища.

| Елемент | Значення розгортання |
| --- | --- |
| Середовище та публічна URL-адреса Heym | `<environment>`, `<public-url>` |
| Черговий платформи та заступник | `<rotation-or-contact>`, `<backup-contact>` |
| Канал інциденту та трекер інцидентів | `<channel>`, `<tracker-url>` |
| Черговий бази даних та ідентифікатор бази | `<contact>`, `<database-id>` |
| Власники інфраструктури, мережі та сховища | `<contacts>` |
| Власник випуску та система розгортання | `<contact>`, `<deployment-url>` |
| Панель помилок програми, затримки та доступності | `<dashboard-url>` |
| Панель процесора, пам'яті, диска та перезапусків хоста чи пода | `<dashboard-url>` |
| Панель з'єднань, блокувань, диска та реплікації PostgreSQL | `<dashboard-url>` |
| Журнали та додатковий бекенд трасування OTel | `<logs-url>`, `<trace-url-or-disabled>` |
| Проєкт/файли Compose або контекст/namespace Kubernetes | `<exact-target>` |
| Розташування екземплярів main, worker-ів, бази даних та сховища | `<services-or-deployments>`, `<storage-ids>` |
| Затверджений тестовий (smoke) workflow та очікуваний результат | `<workflow-id>`, `<safe-input>`, `<expected-result>` |
| Процедура резервного копіювання бази та файлів, останній тест відновлення | `<procedure-url>`, `<test-date>` |
| Цілі часу відновлення (RTO) та точки відновлення (RPO) | `<RTO>`, `<RPO>` |

Зберігайте контакти та посилання на панелі керування в обмеженій операційній копії розгортання. Докази мають містити ідентифікатори, позначки часу, підрахунки та очищені помилки замість облікових даних чи payload-ів workflow.

## Інвентар платформи

| Компонент | Відповідальність | Наслідки інциденту |
| --- | --- | --- |
| Frontend та головний бекенд (main) | UI, API, MCP, Portal, інтерактивне виконання | Перевіряйте публічний маршрут і головний процес окремо |
| PostgreSQL | Стан програми, реєстр виконань, черга запусків, слоти паралелізму, координація та сповіщення | Збій бази даних може зупинити як обробку запитів, так і фонове виконання |
| Екземпляри worker, коли ввімкнено режим cluster | Допустимі фонові запуски, що очікують у черзі | Справні worker-и не замінюють публічні endpoint-и екземпляра main |
| Обраний процес лідера (leader) | Cron, оцінка сповіщень, фонова координація | Сумісний worker може стати лідером; це не змінює його роль на main |
| Постійне сховище екземпляра main | Файли Drive, встановлені плагіни та робочі простори агентів кодування | Відновлюйте сховище разом із main; маршрутизація ingress на worker не відновлює його |
| Бекенд sandbox на кожному екземплярі виконання | Контейнери Docker або поди Kubernetes для ізольованого виконання | Збій бекенда sandbox може вплинути на окремі вузли, доки UI функціонує |
| Залежності workflow | Постачальники моделей, сервери MCP, зовнішні API, сховища даних та служби обміну повідомленнями | Визначте, чи виходить з ладу окрема залежність, чи вся платформа |
| Додатковий колектор OTel | Експортовані спани workflow, вузлів та інструментів Agenta | Сама відсутність експортованих трасувань не доводить збій виконання |

Вбудована черга запусків Heym використовує PostgreSQL. Redis, RabbitMQ та векторні сховища можуть бути залежностями workflow; вони не є обов'язковими службами для вбудованої черги.

`GET /api/health` повідомляє лише про стан процесу та версію. Він не перевіряє PostgreSQL, чергу, вибори лідера, місткість sandbox або синхронізацію credentials. Позитивна відповідь є окремою перевіркою, а не гарантією повної готовності системи.

## Перші п'ять хвилин

| Крок | Дія | Рішення або доказ |
| --- | --- | --- |
| 1 | Підтвердьте сповіщення та перевірте середовище, службу та час початку | Зафіксуйте мітки часу UTC та останню зміну випуску/конфігурації |
| 2 | Перевірте публічний UI та `/api/health`, потім безпосередній бекенд main | Публічний збій за справного прямого бекенда вказує на проблеми маршрутизації або frontend-а |
| 3 | Перевірте підключення до PostgreSQL та тиск з'єднань | Спрямовуйте збої бази даних до L1 перед перезапуском служб програми |
| 4 | Перевірте стан контейнерів/подів, CPU, пам'ять, диск та нещодавні помилки | Розділіть збій інфраструктури, перевантаження та специфічні помилки workflow |
| 5 | У режимі cluster перевірте **Налаштування > Екземпляри**, стан черг та докази лідера | Визначте втрату main, неактивні/неспівпадаючі worker-и або роботу, закріплену за main |
| 6 | Призначте критичність та почніть одну дію з пом'якшення з таблиці маршрутизації | Для P1/P2 негайно відкрийте інцидент та залучіть відповідного власника |
| 7 | Перевірте безпечний запуск робочого workflow та спостерігайте за відновленням | Підтвердьте скорочення віку черги, зменшення помилок і навантаження; встановіть час наступного оновлення |

Якщо випуск збігається зі збоєм, ознайомтеся з розділом [Невдале розгортання або регресія конфігурації](./operations-runbook.md#bad-deployment-or-configuration-regression). Перевірте сумісність схеми перед відкатом.

## Рівень критичності та реагування

Це вихідні цілі реагування. Застосовуйте політику інцидентів та бізнес-вплив конкретного розгортання, якщо вони є суворішими.

| Критичність | Приклади | Реагування |
| --- | --- | --- |
| P1 | Main недоступний для всіх користувачів; база даних недоступна або операції запису зазнають невдачі; масові помилки виконання; критичний вхідний потік недоступний у всіх workflow | Негайне пом'якшення, картка інциденту, чергування платформи та залежностей |
| P2 | Зростання затримки в черзі; втрата місткості worker-ів; загроза вичерпання пулу з'єднань; один workflow погіршує спільну місткість; повторні падіння через OOM | Негайний початок пом'якшення, ціль локалізації протягом 15 хвилин, картка інциденту |
| P3 | Ізольований збій workflow або постачальника; обмежений вплив за справної загальної місткості платформи | Власник workflow або компонента, відстежувана дія та примітка чергового |
| P4 | Інформаційний сигнал, очікуваний тренд навантаження, перевірене хибне спрацьовування | Взяти до відома, задокументувати та налаштувати моніторинг за потреби |

## Маршрутизація сигналів до L1

Використовуйте ці відносні якорі під час налаштування посилань на сповіщення. Якщо служба моніторингу вимагає абсолютної URL-адреси, додайте як префікс розташування вашої розміщеної операційної копії.

| Сигнал | Почніть звідси |
| --- | --- |
| UI/API недоступний, публічні помилки 5xx, збій перевірки стану процесу | [UI або API не працює](./operations-runbook.md#ui-or-api-down) |
| PostgreSQL недосяжний, з'єднання відхилено, помилка запису | [База даних не працює](./operations-runbook.md#postgresql-down-or-not-writable) |
| Забагато клієнтів, таймаут пулу, очікування блокувань, сплеск активних з'єднань | [З'єднання та блокування бази даних](./operations-runbook.md#active-db-connections-pool-saturation-and-locks) |
| Потрібен контрольований перезапуск бекенда або worker-ів | [Перезапуск служби](./operations-runbook.md#controlled-service-restart) |
| Сплеск кількості запусків, загальної тривалості, токенів, CPU або пам'яті | [Найбільш ресурсомісткі workflow](./operations-runbook.md#most-resource-consuming-workflows) |
| Зростання черги, запуски в очікуванні або схоже на зависання | [Затримка в черзі (backlog)](./operations-runbook.md#queue-backlog-or-apparently-stuck-runs) |
| Екземпляр офлайн або не узгоджений, неактивний worker, проблема з планувальником або розподілом | [Перевірки режиму cluster](./operations-runbook.md#cluster-mode-checks) |
| Втрата main, тоді як worker-и залишаються справними | [Головний екземпляр недоступний](./operations-runbook.md#main-instance-unavailable-while-workers-are-live) |
| Помилки Webhook, збої MCP/Portal, розриви з'єднання потокової передачі SSE | [Endpoint-и ingress та виконання](./operations-runbook.md#webhook-mcp-portal-or-streaming-failures) |
| OOM, CrashLoop, Pending, диск заповнений, збій Persistent Volume | [Проблема з контейнером, подом або сховищем](./operations-runbook.md#container-pod-oom-or-storage-issue) |
| Помилки постачальника Agent/LLM/MCP, код 429, збій credentials | [Збій моделі або інтеграції](./operations-runbook.md#model-credential-or-integration-failure) |
| Збої sandbox для Code, Playwright, skill або агента кодування | [Збій sandbox](./operations-runbook.md#sandbox-failure) |
| Відновлення не може досягти цілей; втрата бази даних або файлів | [Відновлення та реагування на аварії](./operations-runbook.md#recovery-and-disaster-response) |

## Ескалація

| Висновок | Залучити | Надати |
| --- | --- | --- |
| Зачеплено кілька інтерфейсів або workflow | Черговий платформи та керівник інциденту | Середовище, масштаб, час початку, заходи пом'якшення, наступне оновлення |
| База даних недоступна, перевантажена, заблокована або закінчилося місце на диску | Черговий бази даних | ID бази даних, кількість з'єднань, блокуючі PID, очищені помилки, стан диска |
| Збій пода/вузла, підключення сховища, місткість sandbox | Власник інфраструктури/сховища | Контекст, namespace, робоче навантаження, події пода, дефіцит ресурсів |
| Публічний маршрут не працює, тоді як прямий бекенд функціонує | Власник мережі/ingress | Зачеплені маршрути, коди стану, затримка, порівняння з бекендом |
| Окремий workflow створює надмірне навантаження або збоїть ізольовано | Власник відповідного workflow | ID workflow/запуску, джерело trigger, швидкість, часове вікно, тимчасові ліміти |
| Скоригована зміна розгортання або конфігурації | Власник випуску | Хеш (digest) запущеного образу, час розгортання, ревізія схеми, останній стабільний випуск |
| Квота, автентифікація або доступність постачальника | Власник credential або інтеграції | Постачальник, модель/служба, код стану, ID запиту за умови безпеки; без значень секретів |

Якщо вплив рівня P1/P2 триває після першого заходу пом'якшення, негайно ескалуйте з уже зібраними доказами. Не чекайте на повний аналіз першопричини.

## Очікувана поведінка під час збоїв

| Збій | Що може продовжувати роботу | Перша дія |
| --- | --- | --- |
| PostgreSQL недоступний | Статичний frontend може все ще завантажуватися | Відновіть шлях до бази даних; не перезапускайте кожен екземпляр програми |
| Main недоступний, worker-и справні | Дозволена фонова робота та планування можуть продовжуватися, якщо керує сумісний worker | Відновіть main з його постійним сховищем; публічні UI/API/MCP/Portal залишаються недоступними |
| Worker недоступний | Інші придатні екземпляри беруть завдання з черги під час їх перерозподілу | Перевірте розміщення, резервну місткість та відновлення перед поверненням трафіку |
| Перерваний запуск | Відновлювані запуски можуть перезапуститися з самого початку, один раз | Перевірте автоматичне відновлення та зовнішні побічні ефекти перед ручним повторенням |
| Перевантаження завданнями, закріпленими виключно за main | Worker-и можуть залишатися бездіяльними | Зменшіть вхідний потік або збільшіть місткість main; зміна ваги не переміщує закріплені завдання |
| Внутрішні сповіщення недоступні | Зовнішній моніторинг доступності/бази/інфраструктури може продовжувати функціонувати | Використовуйте моніторинг поза межами Heym; сповіщення Heym залежать від тієї самої бази та планувальника |
| Sandbox або постачальник недоступний | Workflow без цієї залежності можуть працювати | Ізолюйте зачеплені workflow та виправте залежність |

## Відновлення та закриття інциденту

1. Перевірте публічний доступ, доступ до бази даних, передбачену придатність екземплярів та безпечний робочий (smoke) workflow у робочому режимі. Тест у редакторі не підтверджує передачу завдань worker-ам.
2. Спостерігайте щонайменше 10 хвилин за стабільним рівнем помилок, затримкою, використанням ресурсів та зменшенням віку черги. Також спостерігайте за наступним очікуваним критичним графіком або узгодженою еквівалентною перевіркою.
3. Узгодьте невдалі, відновлені, пропущені, прострочені та очікуючі запуски з власниками workflow. Перевірте зовнішні побічні ефекти перед повторним відтворенням.
4. Поступово скасовуйте тимчасові паузи trigger, ліміти та вагові коефіцієнти worker-ів. Призначте відповідального та термін дії для кожного залишкового обмеження.
5. Оновіть інформацію про інцидент, зазначивши вплив, часову шкалу UTC, виконані дії, докази та залишкові ризики. Призначте аналіз першопричини (post-mortem) для P1/P2 та оновіть обидва документи, якщо процедура була відсутня.
