# Трасування OpenTelemetry

Heym може генерувати трейси [OpenTelemetry](https://opentelemetry.io/) для кожного запуску workflow, виконання вузла та виклику інструмента Agent. Кожен запуск створює кореневий span із дочірніми span'ами для кожного вузла та інструмента Agent, тож Ви можете побачити, який крок зазнав невдачі, скільки він тривав, що він викликав і що повернулося у відповідь. Span'и експортуються через OTLP/HTTP до будь-якого сумісного бекенду, наприклад Jaeger, Grafana Tempo, Honeycomb, Datadog, New Relic або Grafana Cloud.

Трасування **вимкнено за замовчуванням**. Коли воно вимкнене, немає жодних вимірюваних накладних витрат і жодні span'и не створюються.

## Увімкнення трасування

Встановіть наведені нижче змінні середовища на бекенді, а потім перезапустіть його:

Повний перелік змінних середовища дивіться в [Environment Variables](https://github.com/heymrun/heym/blob/main/ENVIRONMENT-VARIABLES.md).

| Змінна | За замовчуванням | Опис |
|----------|---------|-------------|
| `HEYM_OTEL_ENABLED` | `false` | Головний перемикач. Встановіть `true`, щоб увімкнути трасування. |
| `HEYM_OTEL_EXPORTER_OTLP_ENDPOINT` | `""` | Базовий endpoint OTLP/HTTP, наприклад `http://collector:4318`. Heym надсилає span'и на `<endpoint>/v1/traces`. |
| `HEYM_OTEL_EXPORTER_OTLP_HEADERS` | `""` | Заголовки `key=value`, розділені комами, для автентифікації експортера, наприклад `authorization=Bearer <token>`. |
| `HEYM_OTEL_SERVICE_NAME` | `heym` | Ресурсний атрибут `service.name`. |
| `HEYM_OTEL_TRACES_SAMPLER_RATIO` | `1.0` | Коефіцієнт head-семплінгу від `0.0` до `1.0`, застосовується з parent-based семплером. |
| `HEYM_OTEL_CAPTURE_NODE_IO` | `false` | Коли `true`, додає обрізані вхідні та вихідні payload'и вузла до span'ів вузлів. Вимкнено за замовчуванням задля приватності. |

Мінімальний приклад:

```bash
HEYM_OTEL_ENABLED=true
HEYM_OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

Ви можете підтвердити активну конфігурацію в застосунку в розділі **Settings → Observability** (відкрийте його зі свого аватара в заголовку). Ця панель доступна лише для читання й ніколи не показує секрети експортера.

## Що трасується

### Кореневий span workflow

Назва: `heym.workflow.execute`

| Атрибут | Опис |
|-----------|-------------|
| `heym.workflow.id` | UUID workflow. |
| `heym.node.count` | Кількість вузлів у workflow. |
| `heym.workflow.test_mode` | `true` для тестових запусків. |
| `heym.sub_workflow.depth` | Глибина вкладеності при виклику як sub-workflow. |
| `heym.workflow.status` | Фінальний статус запуску. Невдалий запуск встановлює статус span'а в `ERROR`. |

### Span вузла

Назва: `heym.node.execute`, створюється як дочірній до span'а workflow.

| Атрибут | Опис |
|-----------|-------------|
| `heym.node.id` | Ідентифікатор вузла. |
| `heym.node.type` | Тип вузла, наприклад `agent`, `llm`, `http`. |
| `heym.node.label` | Мітка вузла, що відображається на полотні. |
| `heym.node.status` | `success` або `error`. Помилки встановлюють статус span'а в `ERROR`. |
| `heym.node.duration_ms` | Час виконання вузла в мілісекундах. |
| `heym.llm.model` | Назва моделі для вузлів LLM і agent, коли доступна. |
| `heym.llm.prompt_tokens` / `heym.llm.completion_tokens` / `heym.llm.total_tokens` | Використання Token'ів для вузлів LLM і agent, коли доступне. |

Span'и вузлів коректно вкладаються під span workflow, навіть коли вузли виконуються паралельно, оскільки контекст workflow поширюється в робочі потоки.

### Span інструмента Agent

Назва: `heym.agent.tool.execute`, створюється під span'ом активного вузла Agent.

| Атрибут | Опис |
|-----------|-------------|
| `heym.agent.tool.name` | Назва інструмента, вибраного моделлю. |
| `heym.agent.tool.call_id` | Ідентифікатор виклику інструмента від провайдера, коли доступний. |
| `heym.agent.tool.source` | Джерело інструмента, наприклад `node_tool`, `mcp`, `skill` або `sub_workflow`. |
| `heym.agent.tool.mcp_server` | Мітка сервера MCP, коли застосовно. |
| `heym.agent.tool.iteration` | Ітерація циклу інструментів Agent. |
| `heym.agent.tool.args_bytes` | Розмір у UTF-8 серіалізованих аргументів інструмента. |
| `heym.agent.tool.result_bytes` | Розмір у UTF-8 серіалізованого результату інструмента. |
| `heym.agent.tool.status` | `success`, `error`, `pending`, `timeout` або `cancelled`. Помилки інструмента встановлюють статус span'а в `ERROR`. |

Сирі аргументи та результати інструментів за замовчуванням не додаються до span'ів.

## Безпека payload'ів інструментів Agent

Збережені payload'и спостережуваності Agent редагуються та обрізаються в коді (`4096` символів на рядок, глибина `6`, `32768` загальних символів на один запис трейсу LLM). Загальний бюджет трейсу розподіляється між записами інструментів, тож ранній великий результат не може приховати ідентичність і статус життєвого циклу пізніших викликів. Обмежені метадані завантаження `_generated_files` зарезервовані окремо від об'ємного виводу skill:

- Секції інструментів `request` / `response` трейсу LLM, включно з копіями `_hitl_pending`, записаними до сховища трейсів
- Записи `tool_calls` результату Agent, що відображаються в історії виконання
- Події результатів інструментів на панелі Live Debug, які повторно використовують той самий обмежений санітизований запис

Живе виконання інструментів, повідомлення інструментів, прив'язані до моделі, та стан відновлення HITL у пам'яті (`_hitl_pending.agent_state.messages` / `tool_arguments`) зберігають оригінальні значення, тож відновлення та точне зіставлення аргументів усе ще працюють. Санітизуються лише збережені копії спостережуваності.

## Поширення Trace Context

Heym дотримується стандарту [W3C Trace Context](https://www.w3.org/TR/trace-context/), щоб трасування залишалося пов'язаним через межі сервісів.

- **Вхідні webhooks:** коли вхідний запит містить заголовок `traceparent`, запуск workflow записується як дочірній елемент цього трасування. Це пов'язує запуски Heym із вихідною системою, яка їх ініціювала.
- **Вихідні HTTP:** вузол HTTP додає `traceparent` до запитів, які він виконує, щоб нижчі сервіси могли продовжити те саме трасування.
- **Під-workflow:** запуск під-workflow стає дочірнім для вузла, який його викликав, зберігаючи ієрархію викликів в одному трасуванні.

Triggers без вхідного контексту (такі як Cron, IMAP, RabbitMQ та WebSocket) розпочинають нове трасування для кожного запуску.

## Надійність

- Повільний або недоступний collector ніколи не блокує виконання workflow. Spans об'єднуються в пакети та експортуються у фоновому режимі.
- Якщо трасування не вдається ініціалізувати (наприклад, через неправильний endpoint), backend реєструє помилку та продовжує роботу з вимкненим трасуванням, а не завершується з помилкою запуску.
- Заголовки авторизації OTLP зчитуються лише з середовища. Вони ніколи не зберігаються в базі даних і ніколи не повертаються status API.
