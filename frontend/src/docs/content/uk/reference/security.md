# Безпека

Практики безпеки та конфігурація для платформи Heym.

## Політика паролів

Усі паролі — під час реєстрації та під час зміни пароля — повинні відповідати таким вимогам:

| Правило | Вимога |
|------|-------------|
| Мінімальна довжина | 8 символів |
| Великі літери | Щонайменше одна велика літера (A–Z) |
| Малі літери | Щонайменше одна мала літера (a–z) |
| Цифра | Щонайменше одна цифра (0–9) |

Ці правила застосовуються як на фронтенді, так і на бекенді (валідатор Pydantic). Запит із паролем, що не відповідає вимогам, відхиляється з відповіддю `422 Unprocessable Entity` до будь-якого запису в базу даних.

**Приклад дійсного пароля:** `MyWorkflow7!`

## Керування сесіями

- Access tokens зберігаються в **HttpOnly** cookies, а не в `localStorage`. Це запобігає читанню token з боку JavaScript (включно з XSS payload).
- Refresh token обмежений шляхом `/api/auth/refresh` і не може бути надісланий до інших endpoints.
- Кожен виклик `/api/auth/refresh` **ротує** refresh token: старий token негайно відкликається, а новий видається. Повторне використання вже використаного refresh token повертає `401`.

## Обмеження швидкості запитів

Для наведених нижче endpoints діє обмеження швидкості за IP:

| Endpoint | Ліміт | Тривалість блокування |
|----------|-------|--------------|
| `POST /api/auth/login` | 10 зап. / 60 с | 15 хв |
| `POST /api/auth/register` | 5 зап. / 60 с | 10 хв |
| `POST /register` (OAuth-клієнти) | 5 зап. / 60 с | 10 хв |
| Вхід до Portal | 3 спроби | 24 год |

Коли налаштовано `REDIS_URL`, ліміти швидкості спільні для всіх бекенд-воркерів. Без нього ліміти застосовуються окремо для кожного процесу воркера.

## Шифрування облікових даних

Усі API keys, webhook URLs і bearer tokens, що зберігаються на панелі [Credentials](../tabs/credentials-tab.md), шифруються в стані спокою за допомогою AES-256 (Fernet) перед записом у базу даних. Ключ формується зі змінної середовища `ENCRYPTION_KEY`. Скрипти `run.sh` і `deploy.sh` автоматично генерують надійне значення, коли воно порожнє; застосунок відмовляється запускатися, якщо `ENCRYPTION_KEY` порожній або залишений з відомим заповнювачем.

## MCP API Key

MCP API key використовується для автентифікації зовнішніх MCP-клієнтів, що підключаються до endpoint `/api/mcp/sse`. Коли встановлюється з'єднання SSE, видається короткоживучий (1 година) session token, який вбудовується в URL endpoint повідомлень замість справжнього API key, що запобігає появі ключа в журналах доступу сервера. Дивіться [MCP Tab](../tabs/mcp-tab.md) щодо налаштування.

## OAuth / PKCE

Сервер авторизації OAuth 2.0 (використовується для MCP-клієнтів) підтримує лише grant `authorization_code` з PKCE (`S256`). Форма згоди використовує CSRF tokens HMAC-SHA256, дійсні протягом 10 хвилин. Усі значення, що відображаються на сторінці згоди, екрануються в HTML.

## Execution tokens

[Execution tokens](./execution-tokens.md) — це обмежені за областю JWTs для виклику execute endpoint workflow із зовнішніх систем. На відміну від session tokens користувача, вони:

- **Обмежені одним workflow** — token відхиляється для будь-якого іншого workflow.
- **Незалежно відкликаються** — відкликання token не впливає на сесію користувача, який його видав.
- **Коротко- або довгострокові** — виберіть TTL від 60 секунд до 10 років.

Tokens підписуються тим самим секретом застосунку (`SECRET_KEY`) і перевіряються на кожному запиті: підпис, термін дії, відповідність claim `wid` і статус відкликання. Дивіться [Execution Tokens](./execution-tokens.md) щодо налаштування та довідки з API.

## Безпека вмісту

Використовуйте [Guardrails](./guardrails.md) на вузлах LLM і Agent, щоб блокувати небезпечні або такі, що порушують політику, повідомлення користувачів до того, як вони досягнуть моделі. Guardrails підтримують дев'ять категорій вмісту (насильство, мова ворожнечі, сексуальний вміст тощо) з налаштовуваними рівнями чутливості.

## Пісочниця для Python-інструментів

Визначені користувачем Python-інструменти на [Agent node](../nodes/agent-node.md) виконують недовірений код. За замовчуванням Heym запускає кожен інструмент у посиленому, одноразовому Docker-контейнері з:

- відсутністю доступу до мережі,
- файловою системою лише для читання з невеликим робочим каталогом `tmpfs`,
- користувачем без прав root з усіма відкинутими можливостями Linux і `no-new-privileges`,
- суворими обмеженнями CPU, пам'яті та PID, і
- **без монтування Docker socket**, тож інструмент не може дістатися до Docker-демона хоста.

Бекенд виконання контролюється змінною середовища `HEYM_PYTHON_TOOL_SANDBOX`:

| Значення | Поведінка |
|-------|----------|
| `auto` (за замовчуванням) | Запуск у посиленому Docker-контейнері. Якщо Docker недоступний, виконання **завершується відмовою безпеки** — воно не запускає недовірений код без ізоляції ОС. |
| `docker` | Те саме, що `auto`, але ніколи не використовує резервний варіант. |
| `subprocess` | Запуск у локальному внутрішньопроцесному subprocess, захищеному списком дозволених імпортів. Це **не межа безпеки** і призначене лише для довіреного коду або локальної розробки. `run.sh` вибирає його для нативної розробки. |

Встановіть `HEYM_PYTHON_TOOL_IMAGE`, щоб закріпити образ пісочниці; коли порожній, Heym автоматично визначає запущений образ бекенду. Внутрішньопроцесні обмеження (список дозволених імпортів плюс фільтрація атрибутів та інтроспекції) застосовуються як додатковий захист, але контейнер є справжньою межею ізоляції — зберігайте режим `auto` (або `docker`) за замовчуванням для багатокористувацьких і виробничих розгортань.

## Пісочниця Skill

Python skills, прикріплені до [Agent node](../nodes/agent-node.md), також виконують ненадійний код — skill може надійти дослівно всередині спільного workflow або шаблону з видимістю `everyone` — тому skills проходять через **той самий** перемикач `HEYM_PYTHON_TOOL_SANDBOX`, що й Python tools, і зазнають відмови за тим самим принципом fail-closed. Контейнер skill захищено ідентично (non-root, усі capabilities відкинуто, `no-new-privileges`, read-only root filesystem, обмеження CPU/memory/PID та **відсутність Docker socket**), але з двома навмисними відмінностями, оскільки skills законно їх потребують:

- **Мережевий вихідний трафік дозволено** (skills викликають API та встановлюють власні залежності через `uv`), і
- **змонтовано робочий простір із правом запису**, щоб skills могли генерувати вихідні файли та читати файли Heym Drive.

Робочий простір є спільним із тимчасовим сусіднім контейнером через той самий іменований Docker volume, який використовує Codex runner (`heym-codex-workspaces`, змонтований за шляхом `/app/data/codex-workspaces`). У сусідній контейнер монтується лише власний підкаталог цього запуску — через `volume-subpath` для кожного запуску — тож один skill ніколи не бачить даних робочого простору іншого запуску чи Codex. Стек Docker Compose завжди монтує цей volume; `docker run` для одного контейнера має включати `-v heym-codex-workspaces:/app/data/codex-workspaces` як для Python skills, так і для Codex. Якщо volume відсутній у режимі `auto`/`docker`, виконання skill **зазнає відмови за принципом fail-closed**, а не запускається в backend. Оскільки монтування підшляхів для кожного запуску потребує **Docker Engine 25.0 або новішого**, старіші engine мають або оновитися, або запускати довірені skills з `HEYM_PYTHON_TOOL_SANDBOX=subprocess`.

У контейнер передаються лише несекретні, портативні змінні середовища (налаштування proxy та CA-bundle, локаль); database URLs, `SECRET_KEY`/`ENCRYPTION_KEY`, API-ключі провайдерів та OAuth-секрети утримуються за допомогою allowlist. Шляхи до файлів skill перевіряються на перебування всередині робочого простору, а symlinks, розміщені у вихідному каталозі (включно із сентинелом `_hitl_request.json`), ніколи не розкриваються. За потреби перевизначте значення за замовчуванням за допомогою `HEYM_SKILL_IMAGE`, `HEYM_SKILL_NETWORK`, `HEYM_SKILL_MEMORY`, `HEYM_SKILL_CPUS`, `HEYM_SKILL_PIDS` та `HEYM_SKILL_USER`.

Як і у випадку з tools, режим `subprocess` запускає skill у процесі backend і **не є межею безпеки** — використовуйте його лише для довіреної однокористувацької роботи або локальної розробки (`run.sh` вибирає його для нативної розробки).

## Пісочниця Code Node

[Code node](../nodes/code-node.md) виконує довільний користувацький Python разом із довільними сторонніми залежностями, тому це найсуворіша з трьох пісочниць і єдина, що має **жодного шляху обходу**: вона не читає жодної змінної режиму пісочниці, не має режиму `subprocess` і зазнає відмови за принципом fail-closed, коли жоден Docker daemon недоступний. Вона ніколи не повертається до виконання користувацького коду в процесі backend.

Виконання — це один або два тимчасові контейнери, обидва захищені так само, як пісочниці tool і skill (non-root, усі capabilities відкинуто, `no-new-privileges`, read-only root filesystem, обмеження CPU/memory/PID та **відсутність Docker socket**):

- З порожнім `requirements.txt` **один контейнер із `--network none`** виконує код. Runner надходить у stdin payload контейнера, тож нічого взагалі не монтується.
- З залежностями перший контейнер встановлює їх із доступом до мережі в каталог `.deps` для кожного запуску, а другий контейнер монтує це піддерево **read-only** і виконує код. Контейнер виконання не має мережі, якщо опцію `codeAllowNetwork` вузла не увімкнено.

Залежності встановлюються через `uv`, повторюються через `pip` і ніколи не кешуються між запусками. Коли backend працює в контейнері, каталог для кожного запуску розміщується на тому самому volume `heym-codex-workspaces`, який використовує пісочниця skill, змонтованому через `volume-subpath` для кожного запуску, тож один запуск ніколи не бачить файлів іншого; така форма потребує **Docker Engine 25.0 або новішого**. Нативний backend (`./run.sh`) не має такого volume і не потребує його — його каталог для кожного запуску є локальним тимчасовим шляхом, прив'язаним безпосередньо до сусіднього контейнера. У будь-якому разі каталог видаляється після кожного виконання незалежно від результату.

У контейнери передаються лише несекретні, портативні змінні середовища — налаштування proxy, CA bundles та локаль, які потрібні для встановлення залежностей для доступу до PyPI через корпоративний proxy. Database URLs, `SECRET_KEY`/`ENCRYPTION_KEY`, API-ключі провайдерів та OAuth-секрети утримуються за допомогою allowlist, тож новий секрет backend відкидається за замовчуванням, а не витікає, доки хтось не оновить denylist. `HOME` backend ніколи не перевизначає власний шлях із правом запису пісочниці.

Кнопка **Format** використовує ту саму пісочницю. Ruff аналізує та переписує джерельний код, а не виконує його, але запуск його на хості backend надав би ненадійному файлу процес, який успадковує все середовище backend, тож він отримує власний тимчасовий контейнер `--network none` з тими самими обмеженнями та тим самим середовищем із allowlist. Він зазнає відмови за принципом fail-closed без Docker, а не форматує на хості.

Обмеження пісочниці є константами, а не змінними середовища — 512 MB пам'яті, один CPU, 256 процесів, 120-секундний тайм-аут встановлення та 60-секундний тайм-аут виконання. Образ визначається з наявного ланцюжка `HEYM_PYTHON_TOOL_IMAGE` / `HEYM_CODEX_DOCKER_IMAGE`; вузол не вводить власної конфігурації.
