# Єдиний вхід (Single Sign-On)

Heym може автентифікувати користувачів через будь-якого зовнішнього постачальника **OpenID Connect**. Адміністратор вводить URL видавця в розділі **Settings → SSO**, і Heym зчитує всі інші endpoint з документа виявлення цього постачальника.

Жоден постачальник не є жорстко закодованим. Keycloak, Okta, Entra ID, Auth0, Google та будь-який інший постачальник OIDC підключаються через ті самі поля, оскільки єдине, що повідомляється Heym, — це видавець.

Вхід за паролем і SSO працюють паралельно. Вхід за паролем можна вимкнути після перевірки SSO.

## Перш ніж почати

Налаштування SSO застосовуються до всього інстансу, тому змінювати їх можуть лише адміністратори інстансу. Адміністратори визначаються змінною середовища, а не зберігаються в базі даних:

```
HEYM_ADMIN_EMAILS=admin@example.com,ops@example.com
```

Порожнє значення не надає прав нікому. Перезапустіть backend після зміни. Облікові записи з цього списку також бачать вкладку **SSO** в Settings і зберігають доступ за паролем, навіть коли вхід за паролем вимкнено — див. [Вимкнення входу за паролем](#disabling-password-sign-in).

## Реєстрація Heym у Вашого постачальника

У Вашому постачальнику ідентифікації створіть **конфіденційний клієнт** (також званий реєстрацією застосунку) з такими параметрами:

| Параметр | Значення |
|---------|-------|
| Протокол | OpenID Connect |
| Тип надання | Authorization Code with PKCE |
| Автентифікація клієнта | Увімкнено — Heym використовує client secret |
| Redirect URI | Точне значення, показане на вкладці SSO у Heym |
| Scopes | `openid email profile` |

Heym обчислює redirect URI з `FRONTEND_URL` і показує його лише для читання у формі налаштувань із кнопкою копіювання. Він завжди закінчується на `/api/auth/sso/callback`. Скопіюйте його, а не вводьте вручну — невідповідний redirect URI є найпоширенішою причиною невдалого налаштування, і постачальники відхиляють його без пояснень.

Ваш постачальник повинен повертати підтверджену адресу електронної пошти. Див. [Зіставлення облікових записів](#account-mapping).

## Налаштування Heym

Відкрийте **Settings → SSO**. Вкладка з'являється лише для облікових записів із `HEYM_ADMIN_EMAILS`.

| Поле | Що воно робить |
|-------|--------------|
| **Enable single sign-on** | Показує кнопку входу на екрані входу. |
| **Issuer URL** | Базова URL постачальника, наприклад `https://idp.example.com/realms/your-realm`. Heym додає `/.well-known/openid-configuration` і зчитує решту звідти. |
| **Client ID** | Ідентифікатор клієнта від Вашого постачальника. |
| **Client secret** | Зберігається зашифрованим. Залиште поле порожнім, щоб зберегти збережене значення — Heym ніколи не повертає secret, який зберігає. |
| **Redirect URI** | Лише для читання. Скопіюйте це до списку дозволених у Вашого постачальника. |
| **Scopes** | `openid email profile` за замовчуванням. |
| **Sign-in button label** | Текст на кнопці екрана входу, наприклад "Sign in with Okta". |
| **Create an account on first sign-in** | Чи отримують невідомі користувачі обліковий запис Heym автоматично. |
| **Allowed email domains** | Розділені комами. Порожнє значення дозволяє будь-який домен, який автентифікує постачальник. |
| **Disable password sign-in** | Вимикає автентифікацію за паролем для всього інстансу. |

### Спочатку перевірте з'єднання

**Test connection** отримує документ виявлення та ключі підпису постачальника, а потім повідомляє знайдений token endpoint. Ви можете запустити його для видавця, який Ви ввели, але ще не зберегли, тож неправильна URL коштує одного кліку, а не збереження.

Тест лише *записує* успішний результат, коли перевірений видавець є тим, що вже збережений. Тест чернетки повідомляє Вам, чи розпізнається URL; він не дає права на конфігурацію, яка не збережена. Зміна видавця, client ID, scopes або secret очищає записаний результат з тієї ж причини.

## Як працює вхід

1. Хтось натискає кнопку входу на екрані входу.
2. Heym перенаправляє його до постачальника з `state`, `nonce` та PKCE challenge.
3. Він автентифікується у постачальника.
4. Постачальник перенаправляє назад до callback Heym з кодом авторизації.
5. Heym обмінює код на tokens і перевіряє ID token за опублікованими ключами постачальника, перевіряючи підпис, audience, issuer, термін дії та nonce.
6. Heym визначає обліковий запис і видає власну сесію, точно так само, як це робить вхід за паролем.

Усе після кроку 6 залишається незмінним: ті самі session cookies, той самий час життя token, ті самі дозволи.

## Зіставлення облікових записів

Heym визначає обліковий запис у такому порядку:

1. **`(issuer, subject)`** — ідентичність, яку постачальник засвідчив під час попереднього входу. Це авторитетне джерело, і воно зберігається навіть після зміни електронної пошти у постачальника.
2. **Підтверджена електронна пошта** — наявний обліковий запис Heym із цією адресою привласнюється, і subject постачальника записується на нього з цього моменту.
3. **Новий обліковий запис** — створюється, якщо **Create an account on first sign-in** увімкнено і домен дозволено.

Електронна пошта вважається підтвердженою лише тоді, коли ID token містить `email_verified: true`. Якщо ця claim має значення `false` або відсутня, вхід відхиляється. Привласнення наявного облікового запису — або створення нового — на підставі адреси, за яку постачальник не ручається, є шляхом до захоплення облікового запису, тому Heym цього не робить. Постачальника, який ніколи не видає `email_verified`, потрібно налаштувати відповідним чином.

Облікові записи, створені в такий спосіб, не мають пароля. Вони входять лише через постачальника.

## Вимкнення входу за паролем

Перемикач **Disable password sign-in** залишається недоступним, доки не виконано три умови:

1. SSO увімкнено.
2. Тест з'єднання пройдено, тож неправильний issuer не зможе зачинити двері за собою.
3. Принаймні один обліковий запис у `HEYM_ADMIN_EMAILS` справді має пароль.

Коли його увімкнено, автентифікація за паролем відхиляється на всіх трьох поверхнях, які створюють або приймають пароль: формі входу, **реєстрації** та сторінці згоди MCP OAuth. Реєстрація враховується, бо вона видає пароль; якби її залишили відкритою, це налаштування можна було б обійти будь-ким, хто має доступ до `/register`.

Облікові записи, перелічені в `HEYM_ADMIN_EMAILS`, звільнені від усіх трьох умов. Той, хто може редагувати файл середовища, вже може відновити інстанс, тож ця гарантія живе в коді, а не в пам'яті оператора.

### Чому існує третя умова

Адміністратор, чий обліковий запис Heym було створено *через* SSO, не має пароля взагалі. Звільнення дозволило б йому пройти повз браму, але йому нема чим увійти — тож інстанс не мав би шляху назад, якби провайдер вийшов з ладу. Heym відмовляється входити в такий стан і повідомляє про це.

Якщо Ви натрапили на це повідомлення, увійдіть через SSO та зареєструйте обліковий запис із паролем на одній зі своїх адрес адміністратора (реєстрація залишається відкритою для адрес адміністраторів саме з цієї причини), або додайте адресу, яка вже має пароль, до `HEYM_ADMIN_EMAILS`.

### Відновлення, коли провайдер недоступний

У порядку переваги:

1. **Увійдіть із паролем адміністратора для екстреного доступу.** Екран входу приховує форму пароля, коли вхід за паролем вимкнено, тож натисніть **Sign in with a password instead** під кнопкою SSO, щоб її показати. Форма не є обходом: кожна адреса поза `HEYM_ADMIN_EMAILS` все одно відхиляється, і їй повідомляють причину.
2. **Додайте себе до `HEYM_ADMIN_EMAILS`** у файлі середовища та перезапустіть backend. Обліковий запис, який уже має пароль, зможе тоді увійти.
3. **Знову увімкніть вхід за паролем безпосередньо в базі даних**, якщо жоден адміністратор не має пароля взагалі:

   ```sql
   UPDATE sso_settings SET password_login_disabled = false;
   ```

   Перезапуск не потрібен; налаштування зчитується на кожен запит.

Кінцеві користувачі Portal не зачеплені. Вони автентифікуються через окремий каталог — див. [Portal](./portal.md).

## Помилки входу

Невдалий вхід повертає на екран входу з читабельним повідомленням. Heym ніколи не показує необроблений текст помилки провайдера.

| Повідомлення | Причина |
|---------|-------|
| That sign-in attempt expired | Спроба тривала довше десяти хвилин, або браузер відкинув cookie транзакції. Спробуйте знову. |
| Could not reach the identity provider | Discovery або обмін token не вдався. Перевірте URL issuer і те, що провайдер доступний із backend. |
| The provider's response could not be verified | ID token не пройшов перевірку підпису, audience, issuer, терміну дії або nonce. Зазвичай це невідповідність client ID. |
| The provider did not return an email address | Відсутній scope `email`, або провайдер не надає цей claim. |
| Your email address is not verified | Провайдер надіслав `email_verified: false` або пропустив цей claim. |
| Your email domain is not allowed | Адреса поза **Allowed email domains**. |
| No Heym account exists for you | **Create an account on first sign-in** вимкнено, і жоден обліковий запис не збігається. Адміністратор має створити його. |
| Single sign-on is not configured | SSO вимкнено, або відсутній issuer, client ID чи secret. |

## Примітки щодо безпеки

- **Client secret шифрується під час зберігання** і ніколи не повертається жодним endpoint. Форма налаштувань повідомляє лише про те, чи його збережено.
- **PKCE verifier ніколи не залишає Heym.** Він зберігається в короткоживучому cookie `HttpOnly`, а не в параметрі `state`, який проходить через провайдера у відкритому вигляді.
- **Приймаються лише асиметричні підписи.** `none` та симетричні алгоритми відхиляються незалежно від того, що рекламує провайдер.
- **Місце призначення після входу перевіряється** як шлях того самого походження, тож callback не можна використати як відкрите перенаправлення.
- **Кожен вхід аудитується.** Успіхи, невдачі та відмови з'являються як рядки `auth.sso_login`, а зміни конфігурації — як `sso_settings.update` — див. [Audit Logging](./audit.md).

## Що не підтримується

- **SAML.** OIDC — єдиний протокол.
- **Кілька одночасних провайдерів.** Один інстанс підключається до одного провайдера.
- **Зіставлення груп або ролей** з claim провайдера.
- **Single logout.** Вихід із Heym не виводить Вас із провайдера.
