# Організація Workflow

Heym дозволяє організовувати workflow у папках, створювати підпапки та планувати видалення workflow. Огляд інтерфейсу наведено в розділі [Вкладка Workflows](../tabs/workflows-tab.md).

## Папки та підпапки

Папки утворюють дерево. Кожна папка має:

- **Name** – Відображувана назва
- **Parent** – `parent_id` посилається на іншу папку; `null` означає корінь
- **Workflows** – Workflow можна переміщувати до папок за допомогою `folder_id`

### API

| Endpoint | Призначення |
|----------|---------|
| `GET /folders` | Лише кореневі папки |
| `GET /folders/tree` | Повне дерево (дочірні елементи + workflow) |
| `GET /folders/{id}` | Окрема папка з вмістом |
| `POST /folders` | Створити папку (`parent_id` необов'язковий) |
| `PUT /folders/{id}` | Оновити назву або `parent_id` |
| `DELETE /folders/{id}` | Видалити папку (каскадно) |
| `PUT /folders/{folder_id}/workflows/{workflow_id}` | Перемістити workflow до папки |
| `DELETE /folders/workflows/{workflow_id}/folder` | Вилучити workflow з папки |
| `GET /folders/{id}/export` | Завантажити папку та всі підпапки як ZIP |

### Структура дерева

Відповідь дерева містить `children` та `workflows` для кожної папки. Спільні workflow можуть з'являтися в папці через `WorkflowShare.folder_id`.

## Спільний доступ до Workflow

Відкрийте **Share** у редакторі workflow, щоб запросити користувачів електронною поштою або надати спільний доступ [команді](./teams.md). Кожне запрошення та кожен спільний доступ для команди має дозвіл:

| Дозвіл | Що може робити співробітник |
|------------|------------------------------|
| **Read** | Відкривати workflow, переглядати його, переглядати історію виконань і запускати його. Редактор відкривається в режимі лише для читання: збереження вимкнено, а Canvas не можна змінювати. |
| **Write** | Усе, що дозволяє Read, а також редагування Canvas, налаштувань, документа аналізу та пам'яті агента. |

Дозвіл відображається поруч із кожним записом у діалозі Share і його можна будь-коли змінити з цього випадного списку, не видаляючи та не додаючи спільний доступ заново. Коли користувач отримує доступ до workflow кількома шляхами (прямий спільний доступ і одна або кілька команд), перемагає **найвищий** дозвіл. Спільні доступи, що існували до запровадження дозволів, мають **Write**, а клієнти API, які не вказують `permission`, також отримують **Write**.

Дії, доступні лише власнику, ніколи не залежать від дозволу: видалення workflow, відкат або очищення версій, очищення історії, керування спільними доступами та наведені нижче [налаштування, доступні лише власнику](#owner-only-settings) залишаються за власником навіть для співробітників із **Write**. Співробітник із **Read**, який надсилає редагування через API (`PUT /api/workflows/{id}`, нотатку аналізу, пам'ять агента, очищення кешу) або через AI Assistant, отримує `403` із повідомленням `You have read-only access to this workflow`.

Надання спільного доступу до workflow надає доступ до Canvas, історії виконань і документа аналізу. Це **не** надає автоматично спільного доступу до:

- **Облікових даних**, на які посилаються вузли у workflow
- **Під-workflow**, що викликаються вузлами [Execute](../nodes/execute-node.md) або агентами

Отримувачам потрібно надати ці облікові дані та дочірні workflow окремо (тим самим користувачам або командам). Надавайте спільний доступ до облікових даних із [вкладки Credentials](../tabs/credentials-tab.md); див. [Спільний доступ до облікових даних](./credentials-sharing.md). Надавайте спільний доступ до кожного під-workflow з його власного діалогу Share у редакторі.

### Налаштування, доступні лише власнику

Уся конфігурація **Run with cURL** залишається за власником після надання спільного доступу. Співробітники все одно відкривають діалог і копіюють згенеровану команду, але елементи керування доступні лише для читання.

Зміна будь-чого з цього користувачем, який не є власником, відхиляється з `403`:

- **Authentication** (`auth_type`) та **Header Key** (`auth_header_key`)
- Режим **Request Body** (`webhook_body_mode`) та **Request Method** (`http_method`)
- **Response Cache** (`cache_ttl_seconds`) та **Rate Limit** (`rate_limit_requests`, `rate_limit_window_seconds`)
- **SSE Streaming** (`sse_enabled`, `sse_node_config`)

**Header Value** (`auth_header_value`) поводиться інакше: він повністю прихований від співробітників, а запис співробітника ігнорується, а не відхиляється. Редактор відображає поле замаскованим, тож `403` там зламав би звичайне збереження, а не сигналізував би про атаку.

Authentication є причиною, чому цей блок доступний лише власнику: `Anonymous` дозволяє неавтентифікованим викликам запускати workflow, а запуск без користувача, який увійшов, розпізнає облікові дані та глобальні змінні як **власника**, а не виклику. Решта блоку — це опублікований контракт запиту та засоби контролю витрат власника, тож він переміщується разом із ним.

**On error, run workflow** (`error_workflow_id`) на панелі **Properties** рівня workflow доступний лише власнику з тієї самої причини: [error workflow](./features.md#error-workflow) запускається з обліковими даними та глобальними змінними невдалого запуску, які належать власнику для тригерних та анонімних запусків. Співробітники бачать це налаштування лише для читання, а додавання, заміна або очищення його користувачем, який не є власником, відхиляється з `403`.

Редагування Canvas, назви та опису не зачіпається.

### Токени виконання

Співробітник може створити токен виконання для workflow, до якого йому надано спільний доступ. Запуск приписується **тому, хто створив токен**, тож він використовує облікові дані та глобальні змінні цього користувача, а не власника. Лише справді анонімний виклик — `auth_type: anonymous` без виклику — виконується в контексті власника.

## Заплановано для видалення

Workflow можна запланувати для видалення замість негайного вилучення.

- **Поле**: `scheduled_for_deletion` (datetime, що допускає null)
- **Поведінка**: Коли встановлено, workflow переміщується до `folder_id = null` і з'являється в розділі "Scheduled for Deletion".
### API

| Endpoint | Призначення |
|----------|-------------|
| `PUT /workflows/{id}/schedule-deletion` | Встановити `scheduled_for_deletion`, очистити `folder_id` |
| `DELETE /workflows/{id}/schedule-deletion` | Очистити `scheduled_for_deletion` (відновити) |

### UI

- **Перетягнути до кошика** – Перетягніть workflow до області «Заплановано для видалення», щоб запланувати його видалення
- **Відновити** – Вилучити з розкладу видалення
- **Видалити негайно** – Значок кошика для остаточного видалення

### Логіка очищення

Завдання cron виконується щодня о **23:59** (у налаштованому часовому поясі). Workflow видаляється лише за умови, коли:

- **Усі вхідні вузли** (вузли без вхідних ребер, за винятком sticky/errorHandler) мають `active === false`

Якщо будь-який вхідний вузол усе ще активний, workflow залишається до наступного запуску.

## Інтерфейс панелі керування

- **Рядки тек** – Нова тека, рекурсивне дерево тек із розгортанням/згортанням. Кожна тека має
  необов'язковий опис під своєю назвою та значок із підрахунком workflow, які вона містить,
  включно з підтеками.
- **Дії з теками** – Нова підтека, Перейменувати, Змінити значок, Завантажити як ZIP і Видалити
  розташовані в рядку кожної теки; контекстне меню, що викликається правою кнопкою миші, пропонує
  той самий набір, а на телефонах відображається єдина кнопка меню.
- **Головна область** – Кореневі workflow (без теки, не заплановані) та Заплановано для видалення
- **Попередній перегляд під час перетягування до теки** – Перетягування workflow підсвічує точну теку
  або підтеку та показує її повний шлях у попередньому перегляді розміром із картку. Згорнута тека
  розгортається після короткого наведення.
- **Стабільний зворотний зв'язок під час перетягування** – Вихідна картка використовує привид
  перетягування, а активна цільова зона залишається вибраною під час прокручування або перетину
  елементів керування в межах однієї теки.
- **Перевірка призначення** – Поточна тека позначається як **Уже в теці** та не приймає
  зайвого переміщення.
- **Інші цільові зони** – Корінь і «Заплановано для видалення» підсвічуються, коли можуть прийняти
  перетягнутий workflow.
- **Перетягування ZIP** – Перетягніть ZIP-файл до області workflow, щоб імпортувати структуру тек
  на кореневому рівні
