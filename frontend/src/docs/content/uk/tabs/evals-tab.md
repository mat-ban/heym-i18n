# Вкладка Evals

Вкладка **Evals** — це окрема сторінка за адресою `/evals`. Вона дозволяє створювати набори оцінювання, визначати тестові випадки та запускати оцінювання для Ваших Workflow з [Agent](../nodes/agent-node.md). [Агентний набір](#agent-suites) запускає агента або зчитує його реальні запуски та перевіряє викликані інструменти, затримку, вартість у USD, токени та кількість викликів інструментів.

## Доступ

- Натисніть **Evals** на панелі вкладок dashboard
- Або перейдіть за адресою `/evals`
- Або скористайтеся **Ctrl+K** (Cmd+K) і виберіть "Evals" у командній палітрі

## Набори оцінювання

- **Новий набір** – Виберіть **Набір промптів**, щоб протестувати системний промпт на різних моделях, або **Агентний набір**, щоб перевірити реальні запуски агента (див. [Агентні набори](#agent-suites))
- **Вибір набору** – Показує набори промптів та агентів разом із типом поруч із кожною назвою; почніть вводити текст для пошуку
- **Створити набір** – Визначте набір із назвою та описом
- **Виберіть Workflow** – Виберіть, який Workflow оцінювати
- **Виберіть credential** – API key для запуску Workflow
- **System prompt** – Редагуйте system prompt рівня набору безпосередньо на лівій панелі
- **Optimize Prompt** – Попросіть LLM покращити поточний system prompt

## Тестові випадки

- Додавайте тестові випадки з вхідними prompt та очікуваними результатами
- Кожен випадок може мати власне очікуване значення для порівняння
- Редагуйте або видаляйте випадки з набору
- **Generate Test Data** – Використайте вибраний credential/модель, щоб автоматично створити тестові випадки з prompt набору

## Запуск оцінювань

- **Виберіть одну або кілька моделей** – Запустіть той самий набір для кількох моделей в одному оцінюванні
- **Метод оцінювання** – Виберіть `Exact Match`, `Contains` або `LLM-as-Judge`
- **Judge** – Для `LLM-as-Judge` за бажанням виберіть credential OpenAI, OpenAI compatible (Custom), Gemini (Google) або [Decision Model](../nodes/decision-node.md) і введіть модель judge (наприклад, `gpt-4o-mini` або `jev-latest`), щоб оцінювати за допомогою незалежного judge
- **Запусків на тест** – Повторіть кожен тестовий випадок кілька разів за один запуск
- **Запам'ятовані налаштування** – Набір відкривається з налаштуваннями свого найновішого запуску: облікові дані, моделі, метод оцінювання та суддя, температура, зусилля міркування та кількість запусків на тест. Відкриття попереднього запуску завантажує його налаштування, тому **Перезапустити оцінювання** повторює той самий тест
- **Temperature** – Задайте temperature моделі (`Exact Match` і `Contains`)
- **Зусилля міркування** – Встановіть зусилля міркування для міркуючих моделей, від Низького до Дуже високого та Макс так само, як у вузлах LLM та Agent (`Exact Match` і `Contains`)

### LLM-as-Judge

З judge кожна модель відповідає на тестовий вхід лише за допомогою prompt набору, після чого judge оцінює, наскільки близько відповідь збігається з очікуваним результатом, від 0 до 100:

- **Модель-judge** (OpenAI, OpenAI compatible або Gemini) читає питання, очікуваний результат і відповідь та повертає оцінку з однорядковим обґрунтуванням. Вона працює з temperature `0` або з reasoning effort `low` для reasoning-моделі, тож та сама відповідь отримує той самий вердикт.
- **Judge на основі decision model** оцінює відповідь за п'ятирівневою рубрикою, від *Completely off* до *Fully matches*. Оцінка — це зважена за ймовірністю позиція на цій рубриці, тож вона походить із розподілу, який обчислила модель, а не з числа, яке вона написала.

Картка при наведенні на клітинку показує обґрунтування судді або, для моделі рішень, рівень, оцінку та її впевненість. Затримка та токени описують тестовану модель; власні виклики судді з'являються в [Слідах](./traces-tab.md) під джерелом **Оцінювання**. Вибір судді виключає облікові дані Model Router, оскільки суддя має бути однією фіксованою моделлю. Обліковими даними для тестованих моделей може бути [Model Router](../reference/credentials.md#model-router-auto-model): його модель **Auto** обирає модель на кожен запит, так само як у workflow.

Без judge кожна модель відповідає та оцінює власну відповідь в одному запиті.

Temperature та reasoning effort приховані в цьому режимі, а запуск використовує фіксовані налаштування: temperature `0.7` для стандартних моделей і reasoning effort `medium` для reasoning-моделей (`low`, коли вони оцінюють власні відповіді).

## Результати

- Переглядайте pass/fail для кожного тестового випадку
- Досліджуйте фактичні та очікувані результати
- Порівнюйте результати кожної моделі пліч-о-пліч, коли запуск включає кілька моделей
- Переглядайте історію запусків для минулих оцінювань; запуск `LLM-as-Judge` показує свою модель judge у списку історії
- Відкривайте історичні запуски з панелі результатів і досліджуйте збережені знімки prompt/input/output
- Відкриття минулого запуску завантажує його метод оцінювання та judge на ліву панель, тож **Re-Run Evals** повторює те саме оцінювання
- **Export** завантажує запуск як JSON, включаючи `judge_credential_id` та `judge_model`

## Agent Suites

Агентний набір перевіряє вузол [Agent](../nodes/agent-node.md) на основі його запусків. Він зчитує їх зі [Слідів](./traces-tab.md), де кожен запуск уже фіксує свій час, токени, вартість і виклики інструментів, а також може запустити workflow замість вас.

Створіть набір через **Новий набір** → **Агентний набір** і пройдіть три кроки:

1. **Агент** – Виберіть workflow, а потім його вузол агента. У списку відображаються лише workflow з вузлом агента; workflow або агент, який ще не запускався, відображається, але його не можна вибрати. Налаштування обраного агента (модель, інструкції, інструменти та ліміти) відображаються праворуч, а нижче з'являється полотно його workflow у режимі лише для читання з виділеним агентом.
2. **Baseline** – Останні 10 запусків агента: затримка p50 і p95, вартість за запуск, токени за запуск і виклики інструментів за запуск, які інструменти він викликав і як часто, а також власні показники кожного запуску. Запуски, що завершилися помилкою, наведені у списку, але виключені з baseline.
3. **Перевірки** – Позначте кожен інструмент як **Must call**, **Must not call** або **Either**. Кожен вид виклику вказано з його типом: інструменти Python і вузлів, інструменти **MCP** з їхнім сервером, **підагенти** за міткою, **під-workflow** за назвою та **skills**. Додайте інструмент за типом і назвою, якщо він ще не запускався, та видаліть його за допомогою **X**. Встановіть верхні межі для затримки, вартості, загальної кількості токенів і викликів інструментів; кожна починається на 20% вище за p95 baseline і може бути вимкнена.

Збережений набір відкривається на вкладці **Результати**, поруч із якою розташовані **Baseline** та **Редагувати перевірки**:

- **Запустити workflow** – Виберіть кількість запусків (до 20); чотири виконуються одночасно. Вхідні дані заповнюються з найновішого запуску workflow і можуть бути відредаговані, причому кожен запуск використовує їх. Увімкніть **Генерувати вхідні дані** (іконка іскри), після чого оберіть облікові дані та модель, щоб модель згенерувала інший вхід для кожного запуску. Вона зчитує системні інструкції агента і тримається близько до введених значень: введення назви міста генерує інші назви міст. Кожен запуск виконує весь workflow як будь-який звичайний запуск і записується в Історії запусків із trigger `agent_suite`. Щоб пропустити пізніші кроки, такі як надсилання електронної пошти, відкрийте workflow за допомогою **Перейти до workflow** на панелі та спочатку вимкніть ці вузли. **Зупинити** припиняє виконання набору: нові запуски не починаються, а поточні скасовуються. Запуск набору, чий сервер зупинився, наприклад під час перезавантаження, через хвилину відображається як перерваний замість того, щоб залишатися заблокованим.
- **Результати** – За замовчуванням оцінюється найновіший запуск набору. Кожен запуск набору зберігається з датою у виборі запусків, де його можна відкрити або видалити; або перемкніться на останні 10, 20 чи 50 запусків агента, щоб включити й інші його запуски. Ви бачите відсоток проходження, як часто проходила кожна перевірка, затримку, вартість, токени та виклики інструментів поруч зі збереженим baseline, а також кожен запуск із причиною збою та посиланням на його слід.
- **Перейти до workflow** відкриває workflow агента в новій вкладці. У полі назви натискання **Esc** або **X** очищає текст.

Як інтерпретуються показники:

- **Затримка** — це час роботи моделі плюс час викликів інструментів цього запуску.
- **Вартість** використовує ті самі розцінки, що й Traces. Запуск моделі без встановленої ціни пропускає перевірку вартості замість того, щоб завершуватися збоєм.
- Запуск вважається **успішним**, коли він завершився без помилок і кожна перевірка пройдена.
- Набір зчитує виключно ваші власні сліди, за тим самим правилом, що й вкладка Traces.
- **Використовувати останні запуски як baseline** у **Редагувати перевірки** замінює збережений baseline найновішими запусками агента.

Baseline набору походить з одного з трьох джерел. **Редагувати перевірки** показує, яке джерело активне поруч зі **Збережений baseline**:

- найновіші запуски агента (за замовчуванням і те, що бере опція **Використовувати останні запуски як baseline**),
- один завершений запуск набору,
- вручну введені числа.

Останні два налаштовуються з [Chat](./chat-tab.md#working-with-evals) або через API:

- `PATCH /api/evals/agent-suites/{id}` приймає `baseline: {"source": "suite_run", "run_id": "…"}` або `{"source": "manual", "values": {"latency_p95_ms": 3000, "cost_avg_usd": 0.01}}`.
- `POST /api/evals/agent-suites/{id}/runs` приймає `inputs_list`: один об'єкт входу на запуск, до 20.

### З Chat та MCP

[Chat](./chat-tab.md#working-with-evals) та інструмент MCP `heym_chat` можуть створювати, змінювати та запускати набори промптів і агентів:

- Вони самі формулюють тестові випадки та вхідні дані для запусків.
- Запитують, які облікові дані використовувати перед створенням набору промптів, якщо тільки одні не є однозначно відповідними.
- Посилаються на кожен набір, який згадують на цій сторінці.

## Ідеї для матриці бенчмарків

Коли Ви будуєте матрицю бенчмарків для agent Workflow, включайте HITL-сценарії як повноцінні випадки, а не розглядайте їх як крайові випадки.

- Охопіть усі три рішення щодо перевірки: `accepted`, `edited` та `refused`
- Включіть кілька джерел trigger, як-от запуски з редактора, portal, curl/webhook і запуски за cron
- Додайте сценарії повторної перевірки, де один запуск agent призупиняється більше ніж один раз
- Перевірте гілки сповіщень, підключені до виходу `review` agent
- Перевірте подальшу поведінку після відмови, особливо якщо наступні nodes розгалужуються за `$agent.decision`
