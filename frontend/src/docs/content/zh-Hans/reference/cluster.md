# 负载均衡

将第二个 Heym 实例指向同一个 PostgreSQL 数据库，它便会作为 worker 加入。此后，后台工作流运行会按照你设定的百分比在多个实例之间分担，因此提供 UI 和 API 服务的机器不再是唯一运行所有工作流的机器。

实例之间从不互相通信。Postgres 承载工作负载，因此 worker 无需开放端口、无需证书，也无需回连主实例的路由——只需数据库访问权限。

## 角色

一个实例是 **main**，由环境变量固定。它提供 UI、API、MCP 和聊天门户服务，并拥有文件存储和已安装插件。其他所有实例都是 **worker**：它仅访问数据库并执行后台运行。

```
HEYM_CLUSTER_ENABLED=true
HEYM_INSTANCE_ROLE=main       # or: worker
HEYM_INSTANCE_NAME=EU Main    # display label, editable later from Settings
HEYM_INSTANCE_ID=eu-main      # optional; derived from the name when empty
```

main 角色与 leader 选举是分开的。Heym 已经在整个集群中选举出一个 leader，负责 cron、告警评估和崩溃恢复；如果 main 宕机，领导权会在几秒内转移到某个 worker，定时运行会继续触发。main 角色不会转移，因为文件存储无法随之转移。

## 哪些内容可以离开主实例

放置位置在运行开始前根据工作流的节点决定。当运行中的任何节点——包括它调用的子工作流内部的节点——触及仅存在于某一台机器上的内容时，该运行会留在 main 上：

| 节点 | 为何留在 main 上 |
|---|---|
| Codex、OpenCode Go | 编码代理工作区保留在本地磁盘上，以便后续操作可以在其中恢复 |
| 附加了 skill 的 Agent | Skill 代码会读写 Heym Drive |
| Drive、Converter、Google Drive | 它们读写生成的文件 |
| File Upload trigger | 上传内容落在 main 的磁盘上 |
| Send Email | 企业 SMTP 中继通常会将一个源地址加入允许列表 |
| Plugin 节点 | 插件安装在某个实例的磁盘上 |

**其他所有内容都会被分发**——包括 Code 节点、Playwright 和 Agent Python 工具。每个实例都运行相同的镜像并拥有自己的 Docker socket，因此沙箱并不是将运行留在 main 上的理由，而这些是产品中最消耗 CPU 的节点。

如果某个工作流的子工作流由表达式选择，则无法提前检查，因此它会留在 main 上。

## 选择百分比

权重是在 **Settings → Instances** 下设置的整数。它们是**当前可承接工作的实例之间的份额**，而不是 100 的百分比：调度器会除以该池自身的总和。

一旦某个实例退出，这种区别就会显现。当 `Main 41, Worker A 26, Worker B 33` 时，关闭 Worker B 后池为 67，因此 Main 实际获得 41/67 = **61%**，Worker A 获得 26/67 = **39%**。面板会在表格下方打印有效分配，正是出于这个原因；保存也绝不会因为数字加起来不等于 100 而被阻止——只有没有任何已启用实例拥有权重的分配才会被拒绝。

还有两点很容易弄错。

**百分比不是机器算力的份额。** 它只覆盖经过队列的运行。提供 UI 和 API 服务、流式处理编辑器和门户运行，以及处理文件上传，都是 main 的工作，且都不计入其中。main 实际承担的工作比它的数字所表示的更多。

**main 的百分比是上限，而不是下限。** 只能在 main 上执行的运行会从其配额中扣除，因此一旦该配额用完，剩余可分配的运行就会落到 worker 上。将 main 的数字设低是安全的——必须在那里运行的工作仍会在那里运行。将其设高则会使 worker 资源匮乏。

因此，当 main 较强而 worker 较小时，应从接近 60/40 开始，而不是按机器的原始比例，然后在 Traces 标签页中比较实际运行时长并进行调整。

权重会在当前在线且已启用的实例之间重新归一化。当 `main=70, A=15, B=15` 时，如果 A 离线，分配会变为 main 与 B 之间的 70/85 和 15/85，并在 A 恢复后回到 70/15/15。

**恢复的实例不会补回它错过的运行。** 处于 Offline、Disabled 或版本不匹配状态的时间不会计入它，因此一个整夜不可用的 worker 会以池的当前位置重新加入，并且从它的第一次运行起分配就再次显示为 70/30——它不会在追赶上来之前吸收所有运行。一个全程可用的 worker 仍会追赶，这正是使 main 的百分比成为上限的原因。

### 新实例以零加入

从未被赋予权重的实例会从 0 开始，这将使它处于 Live、Enabled 却接收不到任何内容的状态。**自动为新实例分配份额**——默认开启，位于实例表格下方——可以解决这个问题：在 leader 的下一次处理中，新加入者会获得池中的均等份额，现有权重会按彼此之间的比例缩小，因此原本有意设置的 70/30 之后仍大致显示为 70/30。总和始终保持恰好 100。

此操作**每个实例只运行一次**。自动处理和你的手动编辑都会将该实例标记为已配置，因此你亲自设置的实例绝不会在你不知情的情况下被更改——包括你刻意设为 0 的实例。如果你更希望每台新机器都等待你手动配置，请关闭该设置。

只有已启用、在线且兼容的实例才会参与。将份额交给一台无法执行任何内容的机器，会使该份额被搁置。
### 当百分比无法解决问题时

设置面板会报告过去 24 小时的运行中有多少只能在 main 上执行。如果这个数字很高——例如 Codex 密集型或 Drive 密集型的工作负载——那么无论权重如何设置，worker 都会处于空闲状态，解决方案是使用更大的 main 实例，而不是增加更多实例。

## 为 Cluster 调整 PostgreSQL 规模

连接数随实例数扩展，而不仅仅是用户数。每个实例运行多个 uvicorn 进程，每个进程持有一个连接池以及四个 `LISTEN` 连接（取消、队列唤醒、运行结果、聊天流）。打开的聊天流共享同一个聊天连接，因此不会增加数据库连接。一个三实例 Cluster 在默认的 `max_connections = 100` 下就会耗尽连接，Heym 随后将无法访问自己的数据库。

大致按 `instances x processes x (async pool + sync pool + 4)` 来估算，并将 `max_connections` 设置在该值之上。

与其只提高上限，不如缩小连接池。单个部署默认每个进程 10+20 个异步连接和 5+10 个同步连接，这对单台机器来说很宽裕，但对 Cluster 来说远远过多：

| 变量 | 单实例 | Cluster |
|---|---|---|
| `HEYM_DB_POOL_SIZE` | 10 | 3 |
| `HEYM_DB_MAX_OVERFLOW` | 20 | 5 |
| `HEYM_DB_SYNC_POOL_SIZE` | 5 | 2 |
| `HEYM_DB_SYNC_MAX_OVERFLOW` | 10 | 3 |

示例 compose 文件设置了这些值以及 `max_connections = 300`。这将两实例 Cluster 的连接上限从 768 降至 192，三实例也仍然低于 300。

## Cluster 无法为你强制满足的要求

**每个实例必须使用相同的 `SECRET_KEY` 和 `ENCRYPTION_KEY`。** 使用不同 `ENCRYPTION_KEY` 的 worker 无法解密凭据，所有使用凭据的运行都会失败，并报出一个毫无帮助的错误。Heym 在每次心跳时比较两个密钥的摘要，同时比较应用版本和数据库修订版本，并将不匹配的实例标记为 **Mismatch**，使其完全不接收任何工作。在你修复之前，负载会回退到 main。

这也决定了升级顺序。先升级 main 会将所有 worker 标记为不兼容；工作会回到 main，每个 worker 在升级后重新加入。这种方式更慢、可见，且可回滚。

**仅将入口流量指向 main 实例。** 将用户流量轮询分发到各实例会导致文件上传发送到一台机器，而下载请求发送到另一台。代码中没有任何机制阻止这种情况，因为 worker 运行相同的镜像，会响应它收到的任何请求。

**每个实例都需要 `FRONTEND_URL`，并设置为相同的公共地址。** 因人工审核而暂停的运行会在执行它的实例上生成审核链接，而不是在 main 上，Codex 后续链接以及生成文件的下载 URL 也是如此。未设置该变量的 worker 会基于自己的本地地址构建这些链接，收到链接的人将无法打开。

**Worker 实例具有不同的出站 IP。** 任何对来源地址进行 allowlist 的 API 都会看到新的地址。Send Email 正是出于这个原因在 main 上运行；对于 HTTP 节点，要么为 Cluster 提供单一的 NAT 出口地址，要么将每个实例都加入 allowlist。

## 在另一台机器上添加 worker

仓库根目录下的 `docker-compose.worker.yml` 可在其自己的主机上运行一个 worker。它没有数据库也没有 UI：它连接到 main 实例的 PostgreSQL，并承担其份额的后台运行。

在其旁边填写一个 `.env`——镜像 tag、数据库主机和凭据、两个密钥以及一个实例 id——然后启动它。Compose 会在所有必需值设置完毕之前拒绝启动，而不是以一个占位值启动，然后在后续以难以阅读的方式失败。

镜像 tag 必须是 main 所运行的版本，两个密钥必须完全复制。任一不同都会使 worker 显示为 Mismatch，并且不会接收任何工作。

## 解读 Instances 表格

| 列 | 含义 |
|---|---|
| Name | 可编辑的标签；它会标记到该实例执行的每次运行上 |
| Role | 来自环境变量的 `main` 或 `worker` |
| Status | 心跳新鲜时为 **Live**，静默 30 秒后为 **Offline**，当版本、数据库修订版本或密钥与 main 不同时为 **Mismatch** |
| ms | 从该实例到数据库的往返时间，由实例自身测量 |
| On | 在不停止 worker 的情况下将其移出轮换——正在执行的运行会完成，不再分配新的运行。main 实例锁定为开启：文件、插件和编码 agent 工作无论开关如何都在其上运行 |
| Weight | 其在可分配运行中的份额 |

## Cluster 中的并发限制

Workflow 的[并发限制](./webhooks.md#concurrency-limit-and-queued-runs)在 PostgreSQL 中计数，因此它适用于每个实例和每个进程：两个实例运行同一 workflow 的数量绝不会超过限制允许的范围。等待插槽的运行在启动时遵循与其他任何运行相同的放置规则，因此必须留在 main 上的运行仍会留在那里。执行这些运行的队列 worker 现在会在每次安装时启动，包括单个实例，在该实例上它仅认领由其自身实例排队的运行。这意味着单个实例也会在每个进程中保持队列唤醒 `LISTEN` 连接，因此请像规划 cluster 实例一样规划其连接配额。

## 运行历史

执行历史中的每次运行都会标明执行它的实例，两个历史对话框都可以筛选到单个实例。筛选器按实例的 id 进行匹配，但显示其名称，因此重命名实例不会改写旧运行的记录。

在单实例安装中不会出现任何相关内容：字段为空，不显示标签，也不提供筛选器。
## 故障行为

**如果 worker 在运行中途死亡**，其心跳会变为过期状态，leader 现有的恢复扫描会在一个存活实例上重新运行该执行。它此前认领的队列行会被单独处理：一旦该行不再存在活跃执行，且经过两分钟的宽限期后，leader 会将该行标记为失败，并唤醒正在等待结果的各方。仅凭时间长短绝不会触发该机制，因此合法长时间运行的执行不会被干扰；并且该行会被标记为失败而非重新入队，因为恢复机制已经负责重跑，重新入队会导致同一 workflow 运行两次。

**如果 main 宕机**，cron 会继续从某个 worker 触发，可分布式运行的执行也会继续执行。需要 main 的运行会排队等待，并在 main 恢复后清空——但仅限于未触发宽限窗口内（`HEYM_CRON_MISFIRE_GRACE_SECONDS`，默认 600 秒）。更早的内容会被关闭为已跳过，并记录原因，而不是一次性重放数小时的积压。

main 宕机期间，UI、API、MCP 和编辑器均不可用，因为入口点指向 main。
