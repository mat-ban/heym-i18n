# 負載平衡

將第二個 Heym 實例指向同一個 PostgreSQL 資料庫，它就會以 worker 的身分加入。背景 Workflow 執行接著會依你設定的百分比在執行個體之間分配，因此提供 UI 與 API 的機器不會同時是唯一執行所有 Workflow 的機器。

執行個體之間從不互相通訊。Postgres 負責承載工作，因此 worker 不需要開放連接埠、不需要憑證，也不需要連回主執行個體的路由——只需要資料庫存取權。

## 角色

其中一個執行個體是 **main**，由環境變數固定。它提供 UI、API、MCP 與聊天入口網站，並擁有檔案儲存與已安裝的外掛。其他每個執行個體都是 **worker**：它只連線到資料庫並執行背景運行。

```
HEYM_CLUSTER_ENABLED=true
HEYM_INSTANCE_ROLE=main       # or: worker
HEYM_INSTANCE_NAME=EU Main    # display label, editable later from Settings
HEYM_INSTANCE_ID=eu-main      # optional; derived from the name when empty
```

main 角色與 leader 選舉是分開的。Heym 已經會在整個叢集中選出一個 leader 來負責 cron、警示評估與當機復原；如果 main 掛掉，領導權會在幾秒內轉移到某個 worker，排程運行會繼續觸發。main 角色不會轉移，因為檔案儲存無法隨之轉移。

## 哪些工作可以離開主執行個體

放置位置會在運行開始前，依據 Workflow 的節點決定。當運行中的任何節點——包括它所呼叫的子 Workflow 內的節點——碰觸到只存在於單一機器的東西時，該運行就會留在 main：

| 節點 | 為何留在 main |
|---|---|
| Codex、OpenCode Go | 編碼代理工作區留在本機磁碟，以便後續操作能在其中接續 |
| 附加了 skill 的 Agent | Skill 程式碼會讀寫 Heym Drive |
| Drive、Converter、Google Drive | 它們會讀寫產生的檔案 |
| File Upload Trigger | 上傳的檔案會落在 main 的磁碟上 |
| Send Email | 企業 SMTP 中繼通常會將單一來源位址加入允許清單 |
| Plugin 節點 | 外掛安裝在單一執行個體的磁碟上 |

**其他所有工作都會被分配**——包括 Code 節點、Playwright 與 Agent Python 工具。每個執行個體都執行相同的映像檔，並擁有自己的 Docker socket，因此沙箱並不是將運行留在 main 的理由，而那些是產品中最耗 CPU 的節點。

若某個 Workflow 的子 Workflow 是由表達式選擇，就無法事先檢查，因此它會留在 main。

## 選擇百分比

權重是整數，設定於 **Settings → Instances** 之下。它們是**目前可承接工作的執行個體之間的份額**，而不是 100 的百分比：排程器會除以該池自身的總和。

一旦有執行個體退出，這個差異就會立刻顯現。在 `Main 41、Worker A 26、Worker B 33` 的情況下，關閉 Worker B 後會留下總和 67 的池，因此 Main 實際上會收到 41/67 = **61%**，而 Worker A 收到 26/67 = **39%**。面板會在表格下方印出實際分配，正是為了這個原因；而且儲存永遠不會因為數字加總不等於 100 而被阻擋——只有當沒有任何已啟用的執行個體擁有權重時，該分配才會被拒絕。

還有兩件事很容易弄錯。

**百分比不是機器效能的份額。** 它只涵蓋經過佇列的運行。提供 UI 與 API、串流編輯器與入口網站的運行，以及處理檔案上傳，全都是 main 的工作，而且完全不會被計入。Main 實際做的事比它的數字所顯示的更多。

**Main 的百分比是上限，不是下限。** 只能在 main 上執行的運行會計入它的配額，因此一旦該配額用完，剩餘可分配的運行就會落到 worker 上。將 main 的數字設低是安全的——必須在那裡執行的工作仍然會執行。將它設高則會讓 worker 挨餓。

因此，在 main 較強、worker 較小的情況下，起始值應接近 60/40，而不是機器的原始比例，然後在 Traces 分頁中比較實際運行時長並據此調整。

權重會依目前上線且已啟用的執行個體重新正規化。在 `main=70、A=15、B=15` 的情況下，如果 A 離線，分配會變成 main 與 B 之間的 70/85 與 15/85，並在 A 回來時恢復為 70/15/15。

**回來的執行個體不會被補回它錯過的運行。** 處於 Offline、Disabled 或版本不符狀態的時間不會計入它，因此一個整晚無法使用的 worker 會以該池目前的位置重新加入，分配從它的第一次運行起就再次顯示為 70/30——它不會吸收每一次運行直到追上進度。一個全程都可用的 worker 仍然會追上進度，這正是讓 main 的百分比成為上限的原因。

### 新執行個體以零加入

從未被賦予權重的執行個體會從 0 開始，這會讓它處於 Live、Enabled 卻什麼都收不到的狀態。**自動賦予新執行個體份額**——預設開啟，位於執行個體表格下方——可修正這個問題：在 leader 下一次巡行時，新加入者會獲得該池的均等份額，而現有權重會依彼此之間的比例縮減，因此刻意設定的 70/30 之後仍會大致顯示為 70/30。總和會精確維持在 100。

這會**每個執行個體執行一次**。自動巡行與你自己的編輯都會將該執行個體標記為已設定，因此你自己設定的執行個體永遠不會在你背後被變更——包括你刻意設為 0 的執行個體。如果你希望每台新機器都等你來設定，請關閉此設定。

只有已啟用、上線且相容的執行個體會參與。將份額交給無法執行任何工作的機器，會讓那份份額被擱置。
### 當百分比幫不上忙時

設定面板會回報過去 24 小時的執行中，有多少只能在 main 上執行。如果這個數字很高——例如以 Codex 或 Drive 為主的工作負載——那麼無論權重怎麼設定，worker 都會閒置，此時的解法是加大 main 執行個體的規格，而不是增加更多執行個體。

## 為 Cluster 調整 PostgreSQL 的規模

連線數會隨執行個體數量而增加，不只是隨使用者數。每個執行個體會執行多個 uvicorn 程序，而每個程序會持有一個連線池，外加四個 `LISTEN` 連線（取消、佇列喚醒、執行結果、聊天串流）。開啟中的聊天串流會共用那一個聊天連線，因此不會增加資料庫連線。三個執行個體的 Cluster 在預設的 `max_connections = 100` 下就會用盡，Heym 接著便無法連上自己的資料庫。

大致估算方式為 `instances x processes x (async pool + sync pool + 4)`，並將 `max_connections` 設在高於此值。

請縮小連線池，而不是只調高上限。單一部署預設每個程序有 10+20 個非同步連線與 5+10 個同步連線，這對單一機器來說相當充裕，但對 Cluster 而言則遠遠過多：

| 變數 | 單一執行個體 | Cluster |
|---|---|---|
| `HEYM_DB_POOL_SIZE` | 10 | 3 |
| `HEYM_DB_MAX_OVERFLOW` | 20 | 5 |
| `HEYM_DB_SYNC_POOL_SIZE` | 5 | 2 |
| `HEYM_DB_SYNC_MAX_OVERFLOW` | 10 | 3 |

範例 compose 檔案設定了這些值以及 `max_connections = 300`。這讓兩個執行個體的 Cluster 從 768 個連線的上限降到 192，而三個執行個體仍低於 300。

## Cluster 無法替你強制執行的需求

**每個執行個體都必須使用相同的 `SECRET_KEY` 與 `ENCRYPTION_KEY`。** 使用不同 `ENCRYPTION_KEY` 的 worker 無法解密認證資料，而每次使用認證資料的執行都會失敗，並出現一個毫無幫助的錯誤訊息。Heym 會在每次心跳時比對兩個金鑰的摘要，以及應用程式版本與資料庫修訂版本，並將不相符的執行個體標記為 **Mismatch**，使其完全不會收到任何工作。在你修正之前，負載會退回由 main 承接。

這也定義了升級順序。先升級 main 會將所有 worker 標記為不相容；工作會回到 main，而每個 worker 在升級後會重新加入。這個過程較慢、可視，且可回復。

**將 ingress 僅指向 main 執行個體。** 若將使用者流量以輪詢方式分散到各執行個體，會導致檔案上傳送到其中一台機器，而下載卻由另一台處理。程式碼中沒有任何機制能防止這點，因為 worker 執行的是相同的映像檔，並且會回應它收到的任何請求。

**每個執行個體都需要 `FRONTEND_URL`，並設為相同的公開位址。** 因人工審查而暫停的執行，會在其執行的執行個體上產生審查連結，而非在 main 上；Codex 後續追蹤連結以及產生檔案的下載 URL 也是如此。未設定此變數的 worker 會以其自身的本地位址來建構這些連結，而收到連結的人將無法開啟。

**Worker 執行個體具有不同的對外 IP。** 任何會將來源位址加入允許清單的 API 都會看到這個新 IP。Send Email 正是基於這個原因而在 main 上執行；至於 HTTP 節點，請為 Cluster 提供單一的 NAT 出口位址，或將每個執行個體都加入允許清單。

## 在另一台機器上新增 worker

儲存庫根目錄中的 `docker-compose.worker.yml` 可在其專屬主機上執行一個 worker。它沒有資料庫，也沒有 UI：它會連上 main 執行個體的 PostgreSQL，並分擔一部分的背景執行。

在它旁邊填入一個 `.env`——映像檔標籤、資料庫主機與認證資料、兩個金鑰，以及一個執行個體 id——然後啟動它。Compose 會拒絕啟動，直到每個必填值都已設定，而不是以一個預留值啟動，之後才以難以解讀的方式失敗。

映像檔標籤必須是 main 所執行的版本，且兩個金鑰都必須完全複製。任一項不同都會使該 worker 顯示為 Mismatch，且不會收到任何工作。

## 解讀 Instances 表格

| 欄位 | 意義 |
|---|---|
| Name | 可編輯的標籤；它會標記在此執行個體所執行的每一次執行上 |
| Role | 來自環境的 `main` 或 `worker` |
| Status | 有最新心跳時為 **Live**，靜默超過 30 秒後為 **Offline**，當版本、資料庫修訂版本或金鑰與 main 不同時為 **Mismatch** |
| ms | 從該執行個體到資料庫的來回時間，由該執行個體自行測量 |
| On | 將 worker 移出輪替而不停止它——執行中的執行會完成，不會再指派新的執行。main 執行個體會鎖定為開啟：無論切換狀態為何，檔案、外掛與 coding-agent 工作都會在那裡執行 |
| Weight | 它可分得的工作執行比例 |

## 執行歷史記錄

執行歷史記錄中的每一次執行都會標明執行它的執行個體，而兩個歷史記錄對話框都可以篩選至單一執行個體。篩選是以執行個體的 id 進行比對，但顯示其名稱，因此重新命名執行個體不會改寫舊執行所顯示的內容。

這些內容在單一執行個體的安裝中都不會出現：欄位是空的、不會顯示任何標籤，也不會提供任何篩選。
## 失敗行為

**若 worker 在執行途中終止**，其 heartbeat 會變成過期狀態，而 leader 既有的復原清掃機制會在存活的執行個體上重新執行該次執行。該 worker 先前所佔用的佇列資料列則會另行處理：一旦該資料列已無任何進行中的執行，且兩分鐘的寬限期已過，leader 便會將該資料列標記為失敗，並喚醒正在等待結果的對象。單憑存在時間本身永遠不會是觸發條件，因此合法且長時間執行的作業不會受到干擾；而該資料列會被標記為失敗而非重新排入佇列，因為復原機制已負責重新執行，重新排入佇列將導致同一個 Workflow 執行兩次。

**若 main 中斷**，cron 仍會從某個 worker 持續觸發，可分散執行的作業也會繼續執行。需要 main 的執行會排隊等待，並在 main 恢復時消化完畢——但僅限於未觸發寬限視窗內（`HEYM_CRON_MISFIRE_GRACE_SECONDS`，預設為 600 秒）。任何更舊的執行都會以略過作結，並記錄原因，而不是一次重播數小時的積壓作業。

main 中斷期間，UI、API、MCP 與編輯器均無法使用，因為 ingress 指向該處。
